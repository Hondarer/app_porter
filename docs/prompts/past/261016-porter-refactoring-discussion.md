## 現状から確認できたリファクタリング余地

### R-01 設定解析の整数変換を共通化する

[config_load_global.c](../../../prod/libsrc/porter/protocol/config_load_global.c) と [config_load_service.c](../../../prod/libsrc/porter/protocol/config_load_service.c) に、同内容の `parse_u32_field` と `parse_u16_field` があります。  
service 側には、それらを利用する `parse_u8_field` もあります。  
既存の [config_parse_common.h](../../../prod/include_internal/porter/protocol/config_parse_common.h) は、JSONC の読み込みと値の取り出しを共通化しています。

整数変換の規則を既存の共通処理の近くに集約する案を推奨します。  
変更箇所が限定され、重複する値域検査の修正漏れを減らせます。  
ヘッダー内の関数と独立した `.c` のどちらに配置するかは、直接ソースを取り込む既存テストの構成も確認して最終仕様で決めます。

負数、上限超過、文字列と JSON 整数の扱い、戻り値、既定値は保持する必要があります。  
同時に設定ファイルを一度だけ解析する変更を加えると、読み込み時点やエラーの優先順位まで変わるため、別の判断が必要です。  
[potr_service_open_from_config.c](../../../prod/libsrc/porter/api/potr_service_open_from_config.c) は global と service のロードを順に呼んでいます。

### R-02 開始失敗時と通常終了時の資源所有権を明確にする

[potr_service_open.c](../../../prod/libsrc/porter/api/potr_service_open.c) の `ctx_cleanup` は、ウィンドウ、バッファー、ソケット、ピア テーブルなどを解放します。  
[potr_service_close.c](../../../prod/libsrc/porter/api/potr_service_close.c) も、TCP と UDP それぞれの停止手順の後に、同種の資源を解放します。  
開始失敗と通常終了で解放対象が重なっていますが、初期化の進行状態とスレッド停止の前提は異なります。

資源ごとの生成元、使用スレッド、停止条件、秘密情報の消去、解放元を一覧化した後、停止済み資源の解放だけを共通化する案です。  
通常終了の FIN 送信、FIN_ACK 待機、送信キューの排出、スレッド停止順序を、そのまま失敗時の解放処理へ統合する案は推奨しません。  
二重解放や漏えいの存在は、この調査では確定していません。

部分初期化での各失敗点、TCP の複数パス、N:1 のピア資源、秘密バッファーの消去順序を検証する必要があります。  
R-01 より影響が広いため、所有権の整理とテスト観点を確定してから着手する候補です。

### R-03 TCP の接続手順を接続管理ループから分離する

[potr_connect_thread.c](../../../prod/libsrc/porter/thread/potr_connect_thread.c) には、接続タイムアウト、最初のパケットの読み込み、セッション比較、connect/accept のループ、再接続、スレッド開始・停止があります。  
調査時点では 926 行でした。  
分割の根拠は行数ではなく、接続成立までの手順と、接続後を含む繰り返し管理の責務が同居している点です。

最初のパケットの検証と接続準備を、入力と結果が明確な内部処理へ切り出す案です。  
既存の [potr_connected_threads.c](../../../prod/libsrc/porter/thread/potr_connected_threads.c) は接続後のスレッド起動と失敗時の後始末をすでに分離しているため、この責務を重複して作りません。

複数パスの同時接続、古いセッションの扱い、先読みパケットの引き渡し、コールバックの発火順、ロック取得順を保持する必要があります。  
R-02 と連続して変更する場合でも、資源解放の整理と接続手順の移動は別段階で検証する案です。

### R-04 ソケット準備を通信種別ごとに整理する

[api_open_paths.c](../../../prod/libsrc/porter/api/api_open_paths.c) は、UDP unicast/multicast/broadcast、双方向 UDP、N:1、TCP のソケット準備と送信先設定を含みます。  
調査時点では 846 行でした。

通信種別の選択処理を残し、UDP 系と TCP 系の準備を内部ファイルへ分ける案です。  
すべてを関数ポインターの表へ置き換えることは、現時点では必要性が確認できていません。  
アドレス解決、bind、listen、マルチキャスト設定、部分失敗時のソケット所有権の違いを保つことを優先します。

新規ディレクトリが必要な場合は各階層に makefw のテンプレート `makefile` を置きます。  
`ADD_SRCS` への相対パス列挙で走査方式を変更しません。  
OS 依存処理を porter へ追加する方針は、[プラットフォーム抽象化規範](../../platform-abstraction-guideline.md) と整合しません。  
共通層の変更が必要になった場合の扱いは Q-003 で確認します。

### R-05 受信スレッドに残る監視処理の境界を整理する

[potr_recv_thread.c](../../../prod/libsrc/porter/thread/potr_recv_thread.c) は 943 行ですが、検証、受信スロット、セッション、FIN、受信ウィンドウ、配送は `thread_recv_*` に分割済みです。  
一方、同ファイルの `n1_check_health_timeout` などには、受信待機時の監視とピアの接続状態更新が残っています。

受信ループから監視処理への呼び出し境界を明確にする案です。  
ヘルス チェック専用スレッドへ処理を移すと、状態を更新するスレッドやロック条件が変わるため、単なるファイル移動と同じ扱いにはできません。  
既存分割との重複を避け、まず呼び出し元、共有状態、通知タイミングを整理する必要があります。  
R-01〜R-04 より優先度を下げることを推奨しますが、採用は未決定です。
