## 作業 4: unicast の処理件数の改善

### 受入の基準

Linux (WSL) の同じホストのループバックで、`porter-bench` の `unicast` (`p1`) と `tcp` (`p5`、片方向) を、送信スレッド 1 つで、交互に測ります。次の 6 条件のうち、待ち合わせを指定した 5,000 byte を除く 5 条件で、`unicast` ÷ `tcp` の処理件数の比が 0.5 以上であることを、受入の基準とします。あわせて、6 条件のすべてで、対策の前の比を、対策の後に下げないこととします。

Table: 受入の 6 条件と、対策の前の比

| メッセージ長 | 送信の指定 | 対策の前の比 (2026-11-21) |
| --- | --- | --- |
| 64 byte | 指定なし | 1.03 |
| 1,000 byte | 指定なし | 0.69 |
| 5,000 byte | 指定なし | 0.23 |
| 64 byte | 待ち合わせを指定 | 0.86 |
| 1,000 byte | 待ち合わせを指定 | 0.88 |
| 5,000 byte | 待ち合わせを指定 | 0.34 |

「下げない」の判定は、測定のばらつきの範囲 (同じ版を繰り返し測った値の幅) を超えて下がっていないこと、とします。ばらつきの幅は、段階 1 の測定で求めます。

> [!NOTE]
> 待ち合わせを指定した 5,000 byte は、この案件の変更の後も約 0.48 の見込みです。この条件の差は、1 メッセージを分けた複数のパケットを 1 個ずつ送ることによるもので、1 回の呼び出しでまとめて送る方法 (Linux の `sendmmsg()`) の実験では、比が 0.8 以上になりました。まとめて送る方法は、`app/cplat` への関数の追加と、送信スレッドの UDP の送出の作り直しを伴うため、この案件では実装せず、残課題として別の案件で設計します。

### 段階 1: 計測と主因の特定

製品のコードは変更しません。測定は、`bin/porter_bench_ab.py` の交互の実行と、`docs/performance-measurement.md` の手順に従います。

1. 現在の版で、6 条件の比を測り直します (各回 5 測定の中央値を、交互に 3 回)。
2. 5,000 byte と 64 byte の条件で、`unicast` と `tcp` のそれぞれについて、次を記録します。
    - OS の呼び出しの種類ごとの回数と時間 (`strace -c -f`)。1 メッセージあたりの回数に直します。
    - スレッドごとの、自発的と非自発的なコンテキスト スイッチの回数 (`/proc/<pid>/task/<tid>/status`) と、CPU の時間 (ユーザーとカーネル)。
    - CPU の時間が多いスレッドの、実行中のスタックの標本 (`gdb` を実行中のプロセスに接続して、数回採ります)。
3. 記録から、頭打ち (毎秒およそ 7 万から 8.5 万パケット) を決めている処理を特定します。候補は、パケットごとの `sendto` と `recvfrom`、読み出し可能の待機への戻り、スレッドの間の起床、ロックの待ちです。
4. 主因ごとに、対策の候補と、見込める効果、変更の範囲、通信の動作への影響を整理します。

> [!NOTE]
> この環境には `perf` がないため、`strace`、`/proc`、`gdb` を使います。`strace` は実行を遅くするため、処理件数の測定とは別の実行で使い、回数だけを見ます。主因の候補は、作業ツリーの複製でその処理だけを外した版を作り、処理件数を比べて確かめます。

計測用の一時的なコード (時間の記録の追加など) が必要な場合は、作業ツリーの複製 (セッションの一時領域) で行い、リポジトリには入れません。

### 段階 2: 対策の方式の合意

段階 1 の結果を全体管理文書に記録し、対策の方式を、検討用 Markdown の追加の Q でユーザーに確認します。合意の後、この最終仕様を改版し、改版の承認を受けてから、段階 3 に進みます。

方式の検討では、次の制約を守ります。

- 通信の形式 (ワイヤー プロトコル) と、公開 API の契約を変えません。変える必要がある場合は、その方式を採るかどうかを、追加の Q で確認します。
- `app/cplat` の net カテゴリに関数を足す場合は、Linux と Windows の両方の実装、`framework/testfw` の mock、単体テストを、同じ変更に含めます。Windows に相当する OS の機能がない場合は、1 個ずつの呼び出しの繰り返しで、同じ契約を満たします。
- 複数のパケットを 1 回の呼び出しで送る場合は、一部だけが成功したときの扱い、通番、保持範囲、送出上限の更新の順序、再送、経路ごとの送出の結果を、方式の中で定めます。

### 段階 1 の結果

主因は、1 対 1 の片方向の UDP の送信側で、送信スレッドが DATA パケットを 1 個送出するたびに、ヘルス チェックのスレッドを起こしていることです。1 パケットごとに、ロック、条件変数の通知、相手のスレッドの起床が入り、送信スレッドが CPU を使い切っていました。

### 段階 3: 実装と確認

#### 変更の内容

`prod/libsrc/porter/thread/potr_send_thread.c` の `flush_packed()` から、DATA の送出の後にヘルス チェックのスレッドを起こす処理 (`potr_internal_health_thread_wake()` の呼び出し) を外します。

- 有効な DATA の送出の時刻 (`last_valid_data_send_ms`) の記録は、変えません。
- ヘルス チェックのスレッドは、「最後に PING または有効な DATA を送った時刻 + `health_interval_ms`」まで眠り、目を覚ますたびに期限を計算し直します。DATA の送出は期限を後ろへ動かすだけのため、PING を送る時点は変わりません。
- 受信側と再接続の経路にある、ほかの起床 (`thread_recv_dispatch.c`、`potr_recv_thread.c`、`thread_recv_health.c`) は、変えません。
- 通信の形式、公開 API、`app/cplat` は、変えません。機能仕様 (`docs/functional-spec/`) も、利用側から見た動作が変わらないため、変えません。

> [!NOTE]
> 変わるのは、VERBOSE のトレース (DATA の送出による PING の抑止の記録) が出る時点と回数だけです。

#### 単体テスト

`test/src/libporter/potrSendThreadTest` に、`unicast` の DATA の送出で、ヘルス チェックのスレッドを起こさず、有効な DATA の送出の時刻を記録することを確かめるテストを加えます。

#### 確認

- `app/porter` の `make` と `make test`、対象の範囲の `.warn`。
- 受入の基準の 6 条件の測定 (ほかの負荷のない状態で、各回 5 測定の中央値を、変更の前の版、変更の後の版、`tcp` で交互に 3 回)。
- 欠落、切断、再送、フロー制御の動作が変わらないことの確認 (`porter-bench` の `p2`、`p6`、`p7` の、変更の前後の比較)。
- ヘルス チェックの動作の確認 (`unicast` で、DATA を送っている間は PING を送らず、送出が止まってから `health_interval_ms` の後に PING を送ること。既存の単体テストと、`porter-test` またはトレースによる実機の確認)。
- Windows は、CI のビルドとテストで確認します (変更が OS に依存しない数行のため)。

## 作業 5: SIGSEGV の再現の試験

### 前提

異常終了は、2026-11-22 の測定で 1 回だけ起きました。ユーザーによると、当時、OS のメモリ不足が発生していました。その後の 500 回以上の実行では、再発していません。

### 試験の方法

- `libporter`、`libcplat`、`porter-bench` を、通常の構成 (`RelWithDebInfo`) でビルドします。ビルドは、作業ツリーの複製 (セッションの一時領域) で行い、リポジトリのビルドの成果物と makefile は変更しません。試験の間、この実行ファイルと共有ライブラリは置き換えません。
- 複製の `porter-bench` には、受信者の切断と、その後の接続を出力する変更だけを加えます (切断と再接続が起きた実行を数えるため)。ライブラリのソースは変更しません。
- 次のコマンドを、切断と再接続が起きた実行が 100 回以上になるまで、繰り返します。

    ```bash
    porter-bench --cond p6 --receivers 3 --runs 1 --config window_size=64 --config udp_receive_buffer_size=-1 --config flow_control_monitored_receiver_count=1
    ```

- 実行ごとに、終了コード、切断と再接続の有無を記録します。

> [!NOTE]
> アドレス サニタイザーとスレッド サニタイザーは、使いません。この環境には、どちらの実行時ライブラリも導入されていません。

### 終了の条件

- 異常終了がなく、切断と再接続が起きた実行が 100 回に達した場合は、実行の条件と回数を記録し、対策元の項目を解消 (クローズ) とします。
- 異常終了があった場合は、位置と原因を調べ、修正の内容をユーザーに確認します。
