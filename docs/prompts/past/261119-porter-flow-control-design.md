# porter のフロー制御の導入 最終仕様

ファイル名: `261119-porter-flow-control-design.md`

版: 7

## 目的と範囲

受信側の利用側コールバックが受信の速さに追い付かないとき、受信側の要求で送信側が DATA の送出を止める仕組み (フロー制御) を porter に導入します。  
あわせて、待ち合わせを指定しない送信が、送信キューに空きがないときに容量不足を返すようにします。  
また、UDP の連続送信が受信側の OS の受信バッファーをあふれさせないように、受信側が OS の受信バッファーの大きさに基づいて、送信側の送出を抑えます。

### 対象の通信種別

| 通信種別 | フロー制御 | OS の受信バッファーに基づく送出上限 |
| --- | --- | --- |
| `unicast` | 対象 | 対象 (既定で有効) |
| `multicast`、`broadcast` | 対象 | 対象 (既定で有効。送出上限を知らせるのは、送信者が選んだ監視対象の受信者だけ) |
| `unicast_bidir`、`unicast_bidir_n1` | 対象 (双方向のそれぞれに働く) | 対象 (既定で有効。双方向のそれぞれに働く) |
| `tcp`、`tcp_bidir` | 対象 | 対象外 (下位の通信が受信バッファーを守る) |
| `unicast_raw`、`multicast_raw`、`broadcast_raw` | 対象外 (フロー制御の設定を無視する) | 対象外 |

Table: 通信種別ごとのフロー制御の適用

「フロー制御」の列は、容量 (`flow_control_capacity`) を設定した受信側に働く、通知キューの占有量に基づく動作です。「OS の受信バッファーに基づく送出上限」の列は、容量の設定によらず働く動作です。

待ち合わせを指定しない送信の容量不足の返却は、すべての通信種別に適用します。

### 用語

| 用語 | 意味 |
| --- | --- |
| 通知キュー | 受信スレッドが通知を登録し、通知スレッドが利用側コールバックを実行する待ち行列。ハンドルに 1 本 |
| 占有量 | 通知キューに登録済みで、コールバックからまだ復帰していない DATA のバイト数の合計 |
| 容量 | 占有量の割合を計算する基準値 [byte]。0 はフロー制御の無効を表す |
| 抑制 | 送信側が新しい DATA の送出を止めている状態 |
| 抑制の要求 / 解除 | 受信側が送信側へ送る 2 種類の合図 |
| 送出上限 | 受信側が送信側へ知らせる通番。送信側は、この通番以上の新しい DATA を送出しない |
| OS の受信バッファー | 受信側のソケットが、受信スレッドに読み出されるまでパケットを保持する OS の領域 |
| 受信バッファーの幅 | OS の受信バッファーに収まると見積もった DATA パケットの数 |
| 相手 | 占有量を数える単位。N 対 1 サーバーではピアごと、それ以外ではハンドルの通信相手 1 つ |
| 余裕 | `multicast` と `broadcast` の送信者が、受信者ごとに求める値。「受信者の送出上限 − 送信者が次に割り当てる通番」。小さいほど、その受信者は遅い |
| 監視対象 | `multicast` と `broadcast` で、送信者が選んだ、送出上限を知らせる受信者。余裕が小さいほうから選ぶ |

## 受信側の動作

### 占有量の計数

- 占有量は、`POTR_EVENT_DATA` の通知で利用側へ渡すデータ長 (フラグメントの結合と圧縮の展開を終えた後の長さ) の合計です。
- 通知キューへの登録時に加算し、その通知のコールバックから復帰した時点で減算します。
- CONNECTED、DISCONNECTED、経路の接続と切断、ERROR の通知は、占有量に含めません。
- 占有量は相手ごとに数えます。N 対 1 サーバーでは、ピアが切断されて解放された後も、そのピアの通知がすべて消費されるまで占有量を保持します。
- 通知キューはハンドルに 1 本のままとし、コールバックを登録順に実行する動作は変えません。

### 抑制の要求と解除

受信側は、相手ごとに「要求中」と「要求なし」の 2 状態を持ちます。

| 現在の状態 | 条件 | 動作 | 次の状態 |
| --- | --- | --- | --- |
| 要求なし | 占有量が「容量 × 要求のしきい値」を超えた | 抑制の要求を即時に送出する | 要求中 |
| 要求なし | 相手が送出上限まで送り終えた時点で、占有量が「容量 × 解除のしきい値」以上である | 抑制の要求を即時に送出する | 要求中 |
| 要求中 | 再送周期が経過した | 抑制の要求を再送する | 要求中 |
| 要求中 | 占有量が「容量 × 解除のしきい値」を下回った | 解除 (新しい送出上限を載せる) を即時に 1 回送出する | 要求なし |

Table: 受信側の状態遷移

- 要求の送出は、しきい値を超えた DATA を登録した受信スレッドが、その場で行います。
- 解除の送出は、占有量を減算して解除のしきい値を下回ったことを検出した通知スレッドが、コールバックからの復帰の直後に、その場で行います。受信スレッドの周期処理を待ちません。
- 要求の再送は、受信スレッドの周期処理で行います。フロー制御が有効な受信側では、受信スレッドの待ち時間の上限を再送周期にします。
- 状態の遷移とパケットの送出は、相手ごとの排他の下で一組として行います。受信スレッドによる要求と通知スレッドによる解除が、状態の遷移と異なる順序で送出されることを防ぐためです。
- `multicast` と `broadcast` の受信者は、要求の再送の間隔を、再送周期の 100% から 150% の範囲でばらつかせます (受信報告と同じ方法)。最初の要求はばらつかせません。

> [!NOTE]
> 受信側は、占有量が解除のしきい値を下回ったことを、減算の時点で検出できます。送信側の再開を遅らせないために、解除は検出した通知スレッドが即時に送出します。パケットの封緘と送出は、送信スレッド、受信スレッド、ヘルス チェック スレッドがすでに並行して行っており、通知スレッドからの送出でも同じ排他を使います。

> [!NOTE]
> 解除は 1 回だけ送出し、再送しません。UDP で解除が失われた場合、または経路上で要求と解除の順序が入れ替わった場合は、送信側の要求の有効期限 (既定 1,000 ms) で抑制が取り消されます。

### 送出上限の通知

受信側は、抑制の要求と解除に加えて、「この通番まで送ってよい」という送出上限を送信側へ知らせます。送信側は送出上限に達したら自分で止まるため、抑制の要求が届くまでの遅れや喪失があっても、占有量が要求のしきい値の付近で止まります。

送出上限は、次の式で計算します。

```text
占有量による許可数 = 占有量が「容量 × 要求のしきい値」を超えている場合は 0
                     それ以外は (「容量 × 要求のしきい値」 − 占有量) ÷ max_payload (切り捨て) + 1
許可数             = 「占有量による許可数」と「受信バッファーの幅」の小さいほう
送出上限           = 次に受信する通番 + 許可数
```

- 容量が 0 (フロー制御が無効) の受信側では、「占有量による許可数」を使わず、許可数を「受信バッファーの幅」とします。
- OS の受信バッファーに基づく送出上限が対象外または無効の受信側では、「受信バッファーの幅」を使わず、許可数を「占有量による許可数」とします。
- どちらも使わない受信側 (容量が 0 で、OS の受信バッファーに基づく送出上限も対象外または無効) は、フロー制御パケットを送出しません。
- 「受信バッファーの幅」の計算は、「OS の受信バッファーに基づく送出上限」の節に記載します。

- `max_payload` は、受信側の実効値です。
- 「次に受信する通番」は、順序どおりに受信を終えた DATA パケットの次の通番です。
- 送出上限は、すべてのフロー制御パケットに載せます。
- `multicast` と `broadcast` の受信者は、送出上限を受信報告にも載せます。また、下の表の 1 と 3 を行うのは、監視対象に指定されている間だけです。「監視対象 (1 対 N の通信種別)」の節に記載します。

受信側は、次の時点でフロー制御パケットを送出します。1 から 3 は状態の値を「解除」として 1 回だけ送出し、再送しません。容量が 0 の受信側は、1 と 3 だけを行い、占有量の条件は常に満たすものとして扱います。

| 番号 | 時点 | 条件 |
| --- | --- | --- |
| 1 | 相手にまだ送出上限を知らせていない | 相手を新しい通信として採用した後の、最初に送出できる時点 |
| 2 | 解除 | 「受信側の状態遷移」の表のとおり |
| 3 | 送出上限の更新 | 「要求なし」の状態で、前回知らせた範囲の半分以上を受信し、占有量が「容量 × 解除のしきい値」を下回っている |
| 4 | 抑制の要求と、その再送 | 「受信側の状態遷移」の表のとおり |

Table: 送出上限を送出する時点

- 「前回知らせた範囲」は、前回の送出の時点の「次に受信する通番」から、そのとき知らせた送出上限までです。
- 3 と、状態遷移の「相手が送出上限まで送り終えた」の判定は、順序どおりに受信した DATA パケットを 1 個処理するたびに行います。フラグメントの途中のパケットも含みます。
- 1 の「最初に送出できる時点」は、UDP では相手の PING または DATA を受理した時点、TCP では最初の DATA を受理した時点です。送出できなかった場合 (証明書方式のハンドシェイクの途中、送出の失敗) は、次の DATA の受理または周期処理で送出し直します。
- 次に受信する通番が前回知らせた時点より前へ戻った場合と、相手のセッションが変わった場合は、まだ知らせていない状態に戻して、1 から送出し直します。
- 相手が送出上限まで送り終えた時点で、占有量が解除のしきい値を下回っている場合は、3 の更新を送出します。解除のしきい値以上の場合は、抑制の要求へ遷移します。相手が上限で止まっている間に受信側が何も送出しない状態を作らないためです。
- 送出上限の更新の頻度は、許可数の半分のパケットにつき 1 個です。OS の受信バッファーに基づく送出上限が有効な受信側では、「受信バッファーの幅 ÷ 2」パケットにつき 1 個になります (OS の受信バッファーが既定の Linux で、約 21 パケットにつき 1 個)。
- OS の受信バッファーに基づく送出上限を使わない受信側では、占有量が小さい場合で「容量 × 要求のしきい値 ÷ `max_payload` ÷ 2」パケットにつき 1 個です (容量 2 MB、要求のしきい値 80%、`max_payload` 1,400 で約 570 パケットにつき 1 個)。占有量が解除のしきい値に近い場合は、「容量 × (要求のしきい値 − 解除のしきい値) ÷ `max_payload` ÷ 2」パケットにつき 1 個まで増えます (同じ構成で、解除のしきい値が 50% の場合、約 210 パケットにつき 1 個)。

> [!NOTE]
> 送出上限を通番で表すのは、同じ通知が重複して届いても、古い通知が失われても、送信側の判定が変わらないためです。バイト数の加算で表す方式は、通知の喪失と重複で送信側と受信側の数え方がずれます。

> [!IMPORTANT]
> 送出上限は、容量の超過を完全には防ぎません。次の場合は、従来どおり抑制の要求が働き、それでも容量を超えた場合は切断になります。
>
> - 圧縮した DATA: 展開後の大きさが `max_payload` を超えるため、許可数の計算より多くの占有量になります。
> - 最初の送出上限が届く前の送出: 送信側は、送出上限を受けるまで制限なく送出します。
> - 1 対 N で、判定の条件に満たない台数の受信者だけが遅い場合: 送信側は止まりません。
> - 1 対 N で、監視対象に選ばれていない受信者: 送信側は、その受信者の送出上限を使いません。

### OS の受信バッファーに基づく送出上限

UDP では、送信側が連続して送出すると、受信スレッドが読み出すより速くパケットが届き、受信側の OS の受信バッファーがあふれます。あふれた DATA の数が、送信側の再送用の保持範囲 (`window_size`) を超えると、再送できずに切断になります。  
これを防ぐため、受信側は、OS の受信バッファーに収まる数を「受信バッファーの幅」として見積もり、送出上限の許可数をこの幅で抑えます。送信側は、受信スレッドが読み出しを終えた通番から先に、この幅を超える DATA を送出しません。

適用する受信側は、`unicast`、`multicast`、`broadcast`、`unicast_bidir`、`unicast_bidir_n1` (サーバーとクライアントの両方) です。容量 (`flow_control_capacity`) の設定によらず、既定で有効です。`multicast` と `broadcast` では、受信報告を送る構成 (実効 `health_interval_ms` が 0 でない) の受信者に限って働きます。`flow_control_receive_buffer_percent` で、使う割合の変更と無効化ができます。

受信バッファーの幅は、次の式で計算します。

```text
パケット長           = ヘッダー長 (72) + max_payload + 認証タグ長 (16)
1 パケットの見積もり = 2 × パケット長 + 2,048
受信バッファーの幅   = OS の受信バッファーの大きさ × flow_control_receive_buffer_percent ÷ 100
                       ÷ 1 パケットの見積もり (切り捨て)
```

- 「OS の受信バッファーの大きさ」は、サービスを開くときに、受信に使うソケットから取得した値 (`SO_RCVBUF`) です。経路が複数ある場合は、最も小さい値を使います。
- 「認証タグ長」は、暗号化の有無によらず加えます。
- N 対 1 サーバーでは、すべてのピアが 1 つのソケットを共有するため、幅を接続中のピア数で割ります (切り捨て)。
- 幅が 4 未満になる場合は、4 とします。
- ソケットから大きさを取得できなかった場合は、警告を診断出力に記録し、そのハンドルでは OS の受信バッファーに基づく送出上限を使いません。

| 構成 | OS の受信バッファーの大きさ | 受信バッファーの幅 | 送出上限の更新 |
| --- | --- | --- | --- |
| Linux の既定、`max_payload` 1,400 | 212,992 byte | 42 パケット | 約 21 パケットにつき 1 個 |
| Windows の既定、`max_payload` 1,400 | 65,536 byte | 13 パケット | 約 6 パケットにつき 1 個 |
| Linux の既定、N 対 1 サーバーでピアが 4 つ | 212,992 byte | ピアごとに 10 パケット | ピアごとに約 5 パケットにつき 1 個 |

Table: 受信バッファーの幅の例

> [!NOTE]
> 「1 パケットの見積もり」は、パケット 1 個が OS の受信バッファーを使う量の、安全側の見積もりです。Linux は、受信したパケットを、データの長さではなく、管理情報を含む確保済みの領域の大きさで数えます。領域は 2 のべき乗の大きさで確保されるため、最大でデータの長さの約 2 倍に管理情報を加えた量になります。同じホストの Linux の実測では、1,000 byte の DATA が、既定の OS の受信バッファーに約 90 個収まり、幅が約 57 パケットの場合は欠落がなく、約 114 パケットの場合はあふれました。  
> Windows でパケット 1 個が使う量は、この案件では実測していません。Linux と同じ式を使い、OS をまたぐ確認で結果を確かめます。

> [!NOTE]
> 送出上限の更新を減らすには、OS の受信バッファーを大きくします。幅は OS の受信バッファーの大きさに比例します。

> [!IMPORTANT]
> OS の受信バッファーに基づく送出上限は、あふれを完全には防ぎません。次の場合は、従来どおり欠落が起き、保持範囲を超えると切断になります。
>
> - 最初の送出上限が届く前の送出: 送信側は、送出上限を受けるまで制限なく送出します。
> - 送出上限の通知が続けて失われた場合: 送信側は、有効期限の後に送出上限を破棄し、次の通知が届くまで制限なく送出します。
> - `multicast` と `broadcast` で、監視対象に選ばれていない受信者と、外れ値として判定から外れる受信者。
> - `multicast` と `broadcast` で、受信者が急に遅くなった場合: 次の受信報告で監視対象に選ばれるまで (既定で最長 4.5 秒)、その受信者は守られません。
> - N 対 1 サーバーで、幅の下限 (4) が働く数のピアが、同時に連続して送信した場合。
> - 再送、PING など、DATA 以外のパケットが多い場合。

### 監視対象 (1 対 N の通信種別)

`multicast` と `broadcast` では、受信者の全員が送出上限を知らせると、送信者が受けるフロー制御パケットの数が、受信者の台数に比例します。これを避けるため、送出上限を知らせる受信者を、送信者が選んだ監視対象に限ります。

監視対象は、遅い受信者 (余裕が小さい受信者) から選びます。送信者は、監視対象の送出上限を「1 対 N の判定」に使います。この判定は、しきい値に満たない台数の遅い受信者を無視するため、極端に遅い少数の受信者 (外れ値) に全体の送出が合わせられることはありません。

抑制の要求と解除は、監視対象かどうかによらず、容量を設定した受信者の全員が送ります。

#### 受信報告に載せる送出上限

受信者は、受信報告のヘッダーに、その時点の自身の送出上限を載せます。

| 欄 | 内容 |
| --- | --- |
| `seq_num` | 送出上限の有無。`1` = `ack_num` に送出上限がある、`0` = ない |
| `ack_num` | 送出上限 (「送出上限の通知」の式で計算した値)。`seq_num` が `0` の場合は `0` |

Table: 受信報告に載せる送出上限

- 送出上限がない (`seq_num` が `0`) のは、送信者をまだ採用していない受信者と、フロー制御パケットを送出しない受信者 (容量が 0 で、OS の受信バッファーに基づく送出上限も無効または使えない) です。
- 受信報告のパケットの数と大きさは変わりません。
- 送信者は、受信報告に載った送出上限を、監視対象を選ぶための順位付けだけに使います。送出を止める判定には使いません (受信報告の周期が長く、値が古いためです)。

#### 監視対象の選び方

送信者は、受信報告を受けるたびに、その受信者の余裕を記録します。

```text
余裕 = 受信報告に載った送出上限 − 送信者が次に割り当てる DATA の通番 (循環を考慮した差)
```

- 送出上限がない受信報告を受けた場合は、その受信者の余裕の記録を消します。余裕の記録がない受信者は、監視対象の候補にしません。
- 監視対象でない受信者から抑制の要求を受けた場合は、その受信者の余裕を 0 として記録します (受信報告を待たずに候補にするためです)。次の受信報告で上書きします。
- 順位付けに使う余裕は、監視対象の受信者についても、受信報告から求めた値だけです。フロー制御パケットの送出上限からは求めません (更新の直後の値になり、受信報告から求めた値より常に大きくなるためです)。

送信者は、余裕の記録がある活動中の受信者のうち、余裕が小さいほうから「監視する数」の受信者を、監視対象にします。選び直しは、余裕の記録の更新と、活動中の受信者の増減のたびに行います。

```text
割合による数 = 活動中の受信者数 × flow_control_monitored_receiver_percent ÷ 100 (切り上げ)
しきい値     = 「1 対 N の判定」が成り立つ最小の「止める状態」の受信者数
               (有効な条件のうち、小さいほう。両方が無効の場合は 0)
監視する数   = 「flow_control_monitored_receiver_count」「割合による数」「しきい値」のうち、最も大きい値
               ただし、「監視する数の上限」と、候補の受信者数を超えない
監視する数の上限 = 64 と「(max_payload − 2) ÷ 16 (切り捨て)」の小さいほう
```

- 「しきい値」が 0 (1 対 N の判定の条件が両方とも無効) の場合は、監視する数を 0 とします。送信者は送出上限で止まらないため、監視対象を選びません。
- 「しきい値」より少ない数を設定した場合に「しきい値」の台数を監視するのは、監視対象が「しきい値」より少ないと、止める条件が成り立たないためです。
- 「監視する数の上限」は、監視対象の一覧を 1 個のパケットで知らせるための上限です。`max_payload` は送信者の実効値です (既定の 1,400 では 64)。

| `flow_control_receiver_count` | `flow_control_monitored_receiver_count` | 活動中の受信者数 | 監視する数 | 送信者が合わせる相手 |
| --- | --- | --- | --- | --- |
| 2 (既定) | 4 (既定) | 3 | 3 (全員) | 遅いほうから 2 番目 |
| 2 (既定) | 4 (既定) | 100 | 4 | 遅いほうから 2 番目 |
| 2 (既定) | 1 | 100 | 2 | 遅いほうから 2 番目 |
| 10 | 20 | 100 | 20 | 遅いほうから 10 番目 |

Table: 監視する数の例

> [!NOTE]
> 送出を決めるのは、監視対象のうち、遅いほうから「しきい値」番目の受信者 1 台です。それより速い監視対象は、受信者の速さの順位が入れ替わったときに、次の「しきい値」番目の受信者の送出上限が、すでに届いているようにするための予備です。

> [!IMPORTANT]
> 「しきい値」が「監視する数の上限」を超える構成 (割合の条件を使い、受信者が多い場合など) では、止める条件が送出上限だけでは成り立たず、送出上限は働きません。抑制の要求による判定は、従来どおり働きます。

#### 監視対象の一覧の通知

送信者は、監視対象の一覧を、フロー制御パケット (状態の値が `3`) で受信者へ知らせます。

- 宛先は、DATA と同じ (マルチキャスト グループまたはブロードキャスト) です。全経路へ送出します。
- 送出するのは、監視対象が変わった時点と、`flow_control_request_interval_ms` の周期です。監視対象が 0 台の間は、送出しません。
- 受信者は、採用している送信者から届いた最新の一覧に、自身のセッション識別子が含まれている間、監視対象として動作します。
- 受信者は、一覧を `flow_control_request_lifetime_ms` の間受け取らなかった場合、監視対象でなくなったものとして扱います。送信者の停止と、一覧の喪失が続いた場合に、送出上限を送り続けないためです。
- 送信者のセッションが変わった場合は、一覧を受け取っていない状態に戻します。

#### 受信者の動作

- 監視対象になった受信者は、「送出上限を送出する時点」の表の 1 (まだ送出上限を知らせていない) から始めます。以後、監視対象である間、3 (送出上限の更新) を行います。
- 監視対象でない受信者は、1 と 3 を行いません。送出上限を知らせていないものとして扱い、「相手が送出上限まで送り終えた」の判定も行いません。容量を設定している場合は、占有量のしきい値による抑制の要求と解除 (2 と 4) だけを行います。
- 監視対象でなくなった受信者は、送出上限を知らせていない状態に戻します。

#### 送信者の動作

- 送信者は、監視対象の受信者から受けた送出上限だけを保持します。監視対象でない受信者のフロー制御パケットに載っている送出上限は、使いません。
- 受信者が監視対象から外れた時点で、その受信者の送出上限を破棄します。
- 抑制の要求と解除は、監視対象かどうかによらず、従来どおり受理します。
- 「1 対 N の判定」は変わりません。送出上限に達した監視対象の受信者は、「止める状態」の受信者として数えます。

> [!NOTE]
> 受信者が再起動すると、古いセッションの項目が `health_timeout_ms` の間、活動中の受信者として残ります。古い項目が監視対象に選ばれている場合、その間、監視対象の 1 台分が働きません。古い項目の送出上限は、送信者が止まった時点から有効期限が過ぎると破棄されるため、送出が止まったままにはなりません。

> [!NOTE]
> 送信者が受けるフロー制御パケットは、平常時は、DATA 1 パケットあたり「監視する数 ÷ (受信バッファーの幅 ÷ 2)」個です (OS の受信バッファーが既定の Linux の受信者で、監視する数が 4 の場合、約 0.19 個)。監視する数を割合で指定すると、この数は受信者の台数に比例します。

### 容量を超えた場合の切断

DATA を通知キューへ登録すると占有量が容量を超える場合、受信側は次のとおり動作します。

1. その DATA を破棄します。
2. その相手との通信を切断として扱い、`POTR_EVENT_DISCONNECTED` を通知キューへ登録します。登録済みの DATA は破棄せず、登録順に利用側へ渡します。
3. 受信の状態 (受信ウィンドウの保持内容、フラグメント途中の状態、リオーダー待ち) を破棄します。再送不能の通知 (REJECT) を受けたときと同じ処理を使います。
4. N 対 1 サーバーでは、容量を超えたピアだけを切断します。TCP では、その相手との全経路の接続を切断します。

切断の後、占有量が「容量 × 解除のしきい値」を下回るまで、その相手からの受信を再開しません。

| 通信種別 | 再開しない間の動作 |
| --- | --- |
| 片方向 UDP | その送信者からの DATA と PING を破棄し、新しい通信として採用しない。抑制の要求の再送を続ける |
| 双方向 UDP (1 対 1) | 相手からの DATA と PING を破棄し、新しい通信として採用しない |
| N 対 1 サーバー | 切断したピアと同じセッション識別子のパケットを破棄し、新しいピアとして登録しない |
| TCP (待ち受け側) | 相手からの接続を受け付けた直後に閉じる |
| TCP (接続を開始する側) | 再接続を試行しない |

Table: 容量超過による切断の後、受信を再開しない間の動作

占有量が下回った後は、従来の切断と同じく、次に届いたパケットまたは接続から受信を再開します。

> [!NOTE]
> 切断の後に抑制の要求を送り続けるのは、片方向 UDP だけです。片方向 UDP の送信者は受信者の切断を知らずに送出を続けるためです。双方向 UDP と TCP では、切断によって相手側も切断を検知し (死活監視のタイムアウトまたは接続の切断)、相手の送信要求が `POTR_ERR_DISCONNECTED` になって送出が止まります。N 対 1 サーバーは、切断したピアの宛先と鍵を解放するため、要求を送出できません。

> [!IMPORTANT]
> 容量は、メモリ使用量の厳密な上限ではありません。占有量は DATA のバイト数だけを数え、通知ごとの管理情報と、データを伴わない通知は含みません。N 対 1 サーバーでは、目安が「容量 × 接続中のピア数」になります。

## 抑制の要求と解除のパケット

### 形式

パケット種別フラグに `POTR_FLAG_FLOW_CONTROL` (`0x0800`) を追加します。

| 項目 | 内容 |
| --- | --- |
| `flags` | `POTR_FLAG_FLOW_CONTROL`。暗号化時は `POTR_FLAG_ENCRYPTED` を併用 |
| セッション識別子 | 送出する側 (受信側) 自身のセッション識別子。片方向 UDP では受信報告と同じ |
| `seq_num`、`ack_num` | `0` |
| ペイロード | 先頭 1 バイトが状態 (`1` = 抑制の要求、`2` = 解除、`3` = 監視対象の一覧)。状態が `1` と `2` の場合は 5 バイトで、続く 4 バイトが送出上限 (`uint32`、ネットワーク バイト オーダー)。状態が `3` の場合は下の「監視対象の一覧のパケット」のとおり。状態に対する長さが合わないパケットと、状態がその他の値のパケットは破棄する |
| 暗号化 | 有効時はペイロードを暗号化し、ヘッダー全体を AAD として認証タグを付加する。鍵は、片方向 UDP では受信報告と同じ鍵、双方向 UDP と TCP では PING と同じ鍵 |
| 送出経路 | 受信側が保持する全経路。片方向 UDP では NACK・受信報告と同じ宛先 (送信者へのユニキャスト) |
| リプレイ対策 | 暗号化時は、同じ向きの既存パケットと同じ記録で `tx_counter` を照合する |

Table: フロー制御パケットの形式

- 通番は消費せず、送信ウィンドウに登録しません。再送の対象外です。
- 証明書方式でハンドシェイクが完了していない間は、送出しません。
- 対象外の通信種別 (RAW モード) がこのパケットを受信した場合は、破棄します。

監視対象の一覧のパケット (状態が `3`) は、`multicast` と `broadcast` の送信者が受信者へ送ります。ほかのフロー制御パケットと、次の点が異なります。

| 項目 | 内容 |
| --- | --- |
| セッション識別子 | 送信者自身のセッション識別子 (DATA、PING と同じ) |
| ペイロード | 「2 + 16 × 台数」バイト。先頭 1 バイトが状態 (`3`)、次の 1 バイトが台数 (1 以上、「監視する数の上限」以下)、続いて台数分の受信者のセッション識別子。1 台分は 16 バイトで、ヘッダーと同じ並び (`session_tv_sec` 8 バイト、`session_id` 4 バイト、`session_tv_nsec` 4 バイト、いずれもネットワーク バイト オーダー) |
| 暗号化 | PING と同じ鍵 (一対多の証明書方式ではグループ鍵) |
| 送出経路 | 送信者が保持する全経路。宛先は DATA と同じ |
| リプレイ対策 | 暗号化時は、PING と同じ記録で `tx_counter` を照合する |

Table: 監視対象の一覧のパケットの形式

- 受理するのは、`multicast` と `broadcast` の受信者だけです。採用している送信者のセッション識別子と一致しないパケットは破棄します。その他の通信種別と、送信者がこのパケットを受信した場合は、破棄します。

### プロトコル バージョン

`POTR_PROTOCOL_VERSION` を `2` から `3` へ上げます。版 2 の porter と版 3 の porter は、互いのパケットを版の不一致として破棄するため、通信できません。対向側を同時に更新する必要があります。

### 喪失からの回復

- 送信側は、抑制の要求を受けるたびに、その相手の要求の期限を「受信時刻 + 有効期限」に更新します。
- 期限を過ぎた要求は、解除を受けた場合と同じく取り消します。
- 1 対 1 の通信種別と N 対 1 サーバーでは、相手のセッションが変わった場合と、相手を切断と判定した場合にも、その相手の要求を取り消します。
- 片方向 UDP の送信側は、受信者ごとの管理表の項目に要求の期限を持ちます。受信者が再起動した場合、古い項目の要求は有効期限で取り消されます。
- 送信側は、送出上限に達して止まった時点から有効期限が経過しても、次のフロー制御パケットが届かない場合、その送出上限を破棄して送出を再開します。送出上限の通知が失われた場合と、受信側が停止した場合に、送出が止まったままになることを防ぐためです。
- 受信側は、相手が送出上限まで送り終えた時点で、更新または抑制の要求を必ず送出します。抑制の要求は周期的に再送するため、動作中の受信側に対して送信側が有効期限で再開するのは、通知が続けて失われた場合に限られます。
- 要求を取り消す条件 (相手のセッションの変更、相手の切断) では、その相手の送出上限も破棄します。送信側自身の通番が 0 から始まり直す場合 (TCP の再接続など) も破棄します。

## 送信側の動作

### 抑制の判定

| 通信種別 | 抑制する条件 |
| --- | --- |
| `unicast`、`unicast_bidir`、`tcp`、`tcp_bidir` | 相手が「止める状態」である |
| `unicast_bidir_n1` のサーバー | ピアごとに判定する。そのピアが「止める状態」である |
| `multicast`、`broadcast` | 下の「1 対 N の判定」による |

Table: 抑制する条件

相手が「止める状態」であるとは、次のいずれかを満たすことです。

- その相手からの有効な (期限内の) 要求がある。
- その相手から受けた送出上限に達している (次に割り当てる DATA の通番が、送出上限以上である)。

送出上限の扱いは次のとおりです。

- 送信側は、フロー制御パケットを受けるたびに、状態の値によらず、その相手の送出上限を上書きします。保持する単位は、要求の期限と同じです (片方向 UDP は受信者ごとの管理表の項目、N 対 1 サーバーはピア、それ以外はハンドル)。
- 通番の比較は、循環を考慮した差で行います。
- 送出上限を受けていない相手と、破棄した後の相手には、上限がないものとして扱います。
- 送出上限の判定は、送信キューからエントリを取り出す前に行います。1 個の外側パケットに複数のエントリを詰めるため、送出上限を最大で 1 パケット分超えることがあります。
- `multicast` と `broadcast` では、「1 対 N の判定」の「要求している受信者」を、「止める状態」の受信者と読み替えます。「止める状態」の受信者は、活動中の受信者としても数えます。
- `multicast` と `broadcast` の送信者が保持するのは、監視対象の受信者の送出上限だけです (「監視対象 (1 対 N の通信種別)」の節)。
- TCP で複数のパケットをまとめて送出する場合は、まとめる数を、送出上限までに送出できる数で抑えます。
- 相手の新しいセッションを採用したときは、その相手の要求と送出上限を取り消します。

送信側は、受けた要求と送出上限に常に従います。従わない設定はありません。  
フロー制御パケットを送出するかどうかは受信側の設定 (`flow_control_capacity`、`flow_control_receive_buffer_percent`) で決まるため、送信側は、自身の設定によらず要求と送出上限に従います。

### 対 N の判定

`multicast` と `broadcast` の送信者は、次の 2 つの条件のどちらかを満たす間、抑制します。どちらも満たさなくなったら解除します。

- 割合の条件: 「要求中の受信者数 ÷ 活動中の受信者数 × 100」が、割合の設定値以上である
- 台数の条件: 要求中の受信者数が、実効の台数以上である

それぞれの値は次のとおりです。

- 活動中の受信者は、受信報告によって活動中と判定している受信者と、有効な要求を送ってきている受信者です。後者は、受信報告の有無にかかわらず数えます。
- 要求中の受信者は、有効な要求を送ってきている受信者です。
- 実効の台数は、台数の設定値と活動中の受信者数の小さい方です。
- 無効にした条件 (値が 0) は、判定に使いません。両方が無効の場合、1 対 N の送信者は抑制しません。
- 活動中の受信者数が 0 の場合は、抑制しません。

| 台数の設定値 | 活動中の受信者数 | 実効の台数 | 抑制する条件 |
| --- | --- | --- | --- |
| 2 (既定) | 1 | 1 | 1 台が要求中 |
| 2 (既定) | 10 | 2 | 2 台以上が要求中 |
| 5 | 3 | 3 | 3 台すべてが要求中 |

Table: 実効の台数の例

判定は、要求または解除の受理、要求の期限の経過、活動中の受信者の増減のたびに行います。

> [!NOTE]
> 有効な要求を活動中として数える扱いは、フロー制御の判定だけに使います。経路の優先グループの判定と死活監視のタイムアウトは、従来どおり受信報告と PING だけで行います。

> [!NOTE]
> 受信者が再起動すると、古いセッションの項目が `health_timeout_ms` の間、活動中の受信者数に残ります。この間は、割合の分母が実際より大きくなります。

### 抑制中の送出

- 抑制中は、送信キューから新しい DATA を取り出しません。取り出し済みで送出の途中にあるパケットは、送出を完了します。
- 再送 (NACK への応答)、PING、REJECT、FIN、FIN_ACK、ハンドシェイク、鍵配布は、抑制中も継続します。
- 抑制の継続時間に上限はありません。
- 抑制の開始と解除は、診断出力 (INFO) に記録します。利用側への通知イベントは追加しません。

### N 対 1 サーバーの送出

- 送信スレッドは、抑制中のピア宛のエントリを送信キューに残したまま、抑制していないピア宛のエントリを先に送出します。
- 同じピア宛のエントリの順序は変えません。1 件のメッセージの断片が、同じピア宛の他のメッセージと混ざることはありません。
- 抑制が解除されたピア宛のエントリは、送信キュー内の登録順に送出します。
- 抑制中のピアが切断された場合、そのピア宛のエントリは従来どおり破棄します。
- 保留したエントリは、送信キューの完了待ちの番号だけを先に進め、送信キューの容量は送出するまで占有し続けます。後続のほかのピア宛の `POTR_SEND_BLOCKING` の送信を、保留が止めないようにするためです。保留されたピア宛の `POTR_SEND_BLOCKING` の送信は、そのピア宛の保留がなくなるまで待ちます。

### close

- close の開始後は抑制を無視し、送信キューに残っている DATA を送出してから FIN を送出します。N 対 1 サーバーの保留中のエントリも同じです。
- この DATA が受信側で容量を超えた場合、超えた分は受信側で破棄され、受信側の利用側へ切断が通知されます。close は、受付済みのメッセージが相手へ届くことを保証しません。

## 送信要求の受け付け

`potr_service_send()` の動作を、次のとおり変更します。

| 指定 | 送信キューに全断片分の空きがある | 空きがない |
| --- | --- | --- |
| 待ち合わせを指定しない | 登録して `POTR_OK` を返す (変更なし) | 1 つも登録せず、待たずに `POTR_ERR_FULL` を返す (変更。従来は空きを待つ) |
| `POTR_SEND_BLOCKING` を指定 | 登録し、送出の完了を待つ (変更なし) | 空きを待って登録し、送出の完了を待つ (変更なし) |

Table: 送信要求の受け付け

- 空きの判定と登録は、1 件のメッセージの全断片について不可分に行います。一部の断片だけが登録されることはありません。
- N 対 1 サーバーの全ピア宛 (`POTR_PEER_ALL`) の送信は、全ピア分を登録できる空きがなければ、どのピア宛も登録せずに `POTR_ERR_FULL` を返します。
- 断片の数が送信キューの容量 (`send_queue_depth`) を超えるメッセージは、待ち合わせを指定しない送信では常に `POTR_ERR_FULL` になります。
- この動作は、抑制の有無と通信種別によらず適用します。

N 対 1 サーバーで、宛先のピアが抑制中の場合は、次のとおりです。

| 指定 | 動作 |
| --- | --- |
| 待ち合わせを指定しない | 送信キューの空きの有無にかかわらず、登録せずに `POTR_ERR_FULL` を返す |
| `POTR_SEND_BLOCKING` を指定 | 抑制の解除 (または close、ピアの切断) まで待ってから登録する |

Table: 抑制中のピア宛の送信要求

全ピア宛の送信は、接続中のピアに抑制中のものが 1 つでもあれば、同じ扱いにします。

「抑制中」には、ピアから受けた送出上限に達している場合を含みます。OS の受信バッファーに基づく送出上限は既定で有効のため、N 対 1 サーバーが 1 つのピアへ連続して送信すると、容量を設定していない構成でも、待ち合わせを指定しない送信が `POTR_ERR_FULL` を返すことがあります。

> [!IMPORTANT]
> 待ち合わせを指定しない送信が満杯時に待つことを前提にした利用側は、動作が変わります。`POTR_ERR_FULL` を受けた利用側は、間隔をおいて再試行するか、メッセージを破棄するかを自身で決めます。porter は、受け付けなかったメッセージを保持しません。

## 構成

### 設定項目

`global` とサービスごとの設定の両方に、同じ名前で追加します。公開している構造体 (`potr_global_config`、`potr_service_def`) にも、同じ名前の `uint32_t` のメンバーを追加します。

| キー | 既定値 | 意味 | 使う側 |
| --- | --- | --- | --- |
| `flow_control_capacity` | 0 (無効) | 通知キューの容量 [byte]。0 でフロー制御は無効 | 受信側 |
| `flow_control_suppress_percent` | 80 | 抑制を要求するしきい値 [%] | 受信側 |
| `flow_control_resume_percent` | 50 | 解除するしきい値 [%] | 受信側 |
| `flow_control_request_interval_ms` | 200 | 抑制の要求の再送周期 [ms] | 受信側 |
| `flow_control_request_lifetime_ms` | 1,000 | 抑制の要求の有効期限 [ms] | 送信側 |
| `flow_control_receiver_percent` | 0 (無効) | 1 対 N の割合の条件 [%] | `multicast`、`broadcast` の送信側 |
| `flow_control_receiver_count` | 2 | 1 対 N の台数の条件 [台] | `multicast`、`broadcast` の送信側 |
| `flow_control_monitored_receiver_percent` | 0 (無効) | 監視する受信者の割合 [%] | `multicast`、`broadcast` の送信側 |
| `flow_control_monitored_receiver_count` | 4 | 監視する受信者の台数 [台] | `multicast`、`broadcast` の送信側 |
| `flow_control_receive_buffer_percent` | 100 | OS の受信バッファーの大きさのうち、受信バッファーの幅の計算に使う割合 [%] | `unicast`、`multicast`、`broadcast`、`unicast_bidir`、`unicast_bidir_n1` の受信側 |

Table: フロー制御の設定項目

既定値は `POTR_DEFAULT_FLOW_CONTROL_*` の定数として `porter_const.h` に定義します。

### 値の決まり方

- `global` の値は、そのまま使います。構成ファイルで省略した項目には、上の表の既定値を適用します。
- 構造体 (`potr_global_config`) を直接指定する利用側のために、0 を取れない 5 項目 (2 つのしきい値、再送周期、有効期限、`flow_control_receive_buffer_percent`) は、`global` の値が 0 の場合に既定値を使います。構造体を 0 で初期化した既存の利用側が、構成の検査でエラーにならないようにするためです。
- サービス側の `0` と省略は、「`global` の値を使用」です。
- サービス側で「無効」にする場合は、専用の値を指定します。構成ファイルでは `-1`、構造体では `POTR_FLOW_CONTROL_DISABLED` (`UINT32_MAX`) です。
- 専用の値を指定できるのは、`flow_control_capacity`、`flow_control_receiver_percent`、`flow_control_receiver_count`、`flow_control_monitored_receiver_percent`、`flow_control_monitored_receiver_count` のサービス側の値と、`flow_control_receive_buffer_percent` の `global` とサービス側の値です。
- `flow_control_receive_buffer_percent` は、既定で有効で、0 が「既定値を使用」(サービス側では「`global` の値を使用」) を表すため、`global` でも専用の値で無効にできるようにします。
- `flow_control_monitored_receiver_percent` と `flow_control_monitored_receiver_count` の 0 (無効) は、その設定を「監視する数」の計算に使わないことを表します。両方が無効の場合、監視する数は「しきい値」の台数になります。
- 構成ファイルの `-1` は、上の項目に限って受け付けます。その他の符号なし整数の項目の扱い (負号付きの値を受け付けない) は変えません。

```jsonc
{
  "global": {
    // 全サービスの受信側で、容量 4 MiB のフロー制御を有効にする
    "flow_control_capacity": 4194304
  },
  "services": {
    "1001": {
      "type": "multicast",
      // このサービスは割合だけで判定する (半数以上が要求したら抑制)
      "flow_control_receiver_percent": 50,
      "flow_control_receiver_count": -1
    },
    "1002": {
      "type": "unicast",
      // このサービスはフロー制御を使わない
      "flow_control_capacity": -1
    },
    "1003": {
      "type": "unicast",
      // このサービスの受信側は、OS の受信バッファーに基づく送出上限を使わない
      "flow_control_receive_buffer_percent": -1
    }
  }
}
```

### 構成の検査

サービスを開くときに、実効値 (サービス側の値を `global` の値に重ねた結果) を検査します。次のいずれかに該当する場合は、`POTR_ERR_INVALID_ARGUMENT` を返します。

| 条件 | 適用する場合 |
| --- | --- |
| 専用の値 (`POTR_FLOW_CONTROL_DISABLED`) を、指定できない項目または `global` に指定している | 常に |
| `flow_control_suppress_percent` が 1 から 100 の範囲にない | 常に |
| `flow_control_resume_percent` が 1 以上、`flow_control_suppress_percent` 未満の範囲にない | 常に |
| `flow_control_request_interval_ms` が 0 である | 常に |
| `flow_control_request_lifetime_ms` が `flow_control_request_interval_ms` 以下である | 常に |
| `flow_control_request_interval_ms` または `flow_control_request_lifetime_ms` が、待機時間の設定値の上限 (`POTR_WAIT_MS_MAX`、2,147,483,646) を超える | 常に |
| `flow_control_receiver_percent` が 100 を超える | 常に |
| `flow_control_monitored_receiver_percent` が 100 を超える | 常に |
| `flow_control_monitored_receiver_count` が 64 を超える | 常に |
| `flow_control_receive_buffer_percent` が、専用の値でなく、1 から 100 の範囲にない | 常に |
| 要求のしきい値から容量までの余裕 (`flow_control_capacity` − `flow_control_capacity` × `flow_control_suppress_percent` ÷ 100) が `max_message_size` 未満である | 容量が 0 でない場合 |
| 実効 `health_interval_ms` が 0 である | `multicast`、`broadcast` の受信側で、容量が 0 でない場合 |

Table: フロー制御の構成の検査

### 容量の余裕

送出上限により、送信側は占有量が要求のしきい値に達する付近で止まります。要求のしきい値から容量までの余裕「容量 × (100 − `flow_control_suppress_percent`) ÷ 100」は、送出上限で抑えられない次の量を受け止めるために使います。

| 余裕で受け止める量 | 目安 |
| --- | --- |
| 圧縮した DATA の展開による増加 | 展開後の大きさと `max_payload` の差 |
| 最初の送出上限が届く前に送出された DATA | 接続の直後に送信側がまとめて送出する量 |
| 送出上限を 1 パケット分超える送出と、フラグメントの途中にある DATA | `max_message_size` 程度 |

Table: 容量の余裕で受け止める量

この指針は `docs/config.md` に記載します。

> [!NOTE]
> 送出上限を導入する前の実装では、容量 2 MB、`send_queue_depth` 1,024 (既定) の構成で、抑制の解除の直後に送信キューの内容がまとめて送出され、TCP で占有量が容量を超えて切断になりました。送出上限は、この集中送出を防ぐために導入します。  
> UDP では、同じ集中送出が受信側の OS の受信バッファー (Linux の既定は約 208 KB) をあふれさせ、欠落から再送不能の切断になることがあります。これはフロー制御の導入前からある動作です。再送を行う UDP の通信種別では、OS の受信バッファーに基づく送出上限で防ぎます。`multicast` と `broadcast` で、監視対象に選ばれない受信者や、外れ値として判定から外れる受信者を守る必要がある場合は、監視する数としきい値を見直すか、`send_queue_depth` を小さくするか、OS の受信バッファーを大きくして避けます。

> [!NOTE]
> 余裕が `max_message_size` 未満の構成をエラーにするのは、フラグメントの途中にあった最大長のメッセージ 1 件が、送出上限で止まった後に完成するだけで、容量を超えるためです。既定の要求のしきい値 (80%) では、容量が `max_message_size` の 5 倍以上であることに相当します。要求のしきい値を 100% にした構成は、余裕が 0 になるため、容量が 0 でない限りエラーになります。

> [!NOTE]
> 再送周期と有効期限は、送信側と受信側で同じ値を構成することを前提とします。受信側の再送周期が送信側の有効期限以上の構成では、要求の再送の間に抑制が外れます。この組み合わせは、片側の構成からは検査できません。
