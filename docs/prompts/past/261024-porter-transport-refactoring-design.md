# porter のソケット準備・TCP 接続前処理・受信監視の分離仕様

検討 ID: porter-transport-refactoring-20261024

版: 1

状態: 実装・局所検証・成果物の受入承認を完了

## BL-003 → BL-002 → BL-004 の順で分離する

ソケット準備、TCP 接続成立前の処理、受信監視を、それぞれ独立して検証できる内部ファイルへ分離します。  
各段階で対象のビルドと局所テストを終えてから、次の段階へ進みます。  
対象は `app/porter` の実装、私有ヘッダー、関連モック・テストと設計文書です。

公開 API・ABI、通信形式、設定値の意味、戻り値、通知順序、ロック順序とソケット所有権を保持します。  
BL-001 の共通解放、部分起動失敗の回収、スレッド停止後の資源解放も維持します。  
外部契約の変更が必要と判明した場合は、具体的な変更案を個別に確認してから反映します。

## BL-003 は方式の選択と UDP・TCP の準備を分ける

配置先は `prod/libsrc/porter/api/` です。  
`api_open_paths.c` には `api_open_paths_by_type` の switch と `api_setup_dest_addr` を残します。  
方式別の処理を次の私有ファイルへ移し、対応するヘッダーに宣言と内部契約を記載します。

- `api_open_paths_udp.c/.h`: unicast、multicast、broadcast、双方向 unicast、N:1 の準備と UDP ソケット生成
- `api_open_paths_tcp.c/.h`: TCP 受信側の listen 準備と送信側の接続先・送信元準備
- `api_open_paths_common.c/.h`: IPv4 の解決・解析と結果コードの変換

UDP の方式別入口は `api_open_paths_unicast`、`api_open_paths_multicast`、`api_open_paths_broadcast`、`api_open_paths_unicast_bidir`、`api_open_paths_unicast_bidir_n1` とし、TCP の入口は `api_open_paths_tcp` とします。  
引数と戻り値は移動元の方式別関数に合わせます。  
共通の解決・解析は、文字列と `uint32_t` の出力先を受け取り、既存の結果コードを返します。  
内部関数名には api の接頭辞を付け、方式選択のための関数ポインター表は追加しません。

ソケットがコンテキストへ格納される位置、失敗時にその場で閉じる位置、上位の共通解放へ委ねる位置を維持します。  
アドレス解決失敗とソケット操作失敗の分類、最初に返すエラー、途中まで準備したパスの扱いも変えません。  
IPv4 の処理を UDP と TCP の双方に複製せず、宛先設定からも同じ共通処理を使います。

## BL-002 は共有状態の採用を管理ループに残す

配置先は `prod/libsrc/porter/thread/` です。  
`potr_connect_thread.c` から接続成立前の処理を `thread_connect_prepare.c/.h` へ分離します。  
私有関数には `thread_connect_` の接頭辞を付けます。

- タイムアウト付き接続: コンテキストとパス番号を受け取り、接続済みソケットまたは無効値を返します。
- 接続元の選別: 既存の接続元アドレス・ポートの検査を、共有状態を更新しない判定として分離します。
- 最初のパケットの読み取り: ソケット、バッファー、容量、受信長の出力先とタイムアウトを受け取り、既存の結果コードを返します。
- セッション比較: コンテキストと解析済みパケットを受け取り、新規・同一・旧セッションの比較結果を返します。

パケット解析には既存の `potr_internal_packet_parse` を再利用します。  
管理ループは、読み取り、解析、ロック取得、サービス ID・認証検査、セッション比較、共有状態への採用を現在の順で呼び出します。  
解析済みパケットの生成処理を複製したり、既存の解析関数を包むだけの層を追加したりしません。

受信側のロックは `session_establish_mutex`、`tcp_recv_mutex` の順で取得します。  
セッション比較は、呼び出し元が両方を保持する読み取り専用処理とします。  
認証の呼び出し位置、既存セッションの停止、接続の採用、接続数更新、通知と接続後スレッドの起動・停止は管理ループに残します。  
既存の `potr_connected_threads.c` と受信認証処理を再利用します。

接続ヘルパーは新規ソケットを所有し、失敗時は閉じ、成功時に呼び出し元へ返します。  
共有状態への格納は管理ループが担当します。  
停止要求の監視、待機の刻み、タイムアウト 0 の接続方式、非ブロッキング設定の扱い、EOF・I/O エラー・長さ超過の分類を維持します。  
今回の分離に伴う別のタイムアウト規則や再試行規則は導入しません。

## BL-004 は受信監視を同じスレッド上の内部処理にまとめる

`prod/libsrc/porter/thread/thread_recv_health.c/.h` に、N:1 のタイムアウト監視、1:1 のタイムアウト監視、TCP 受信状態の変化に伴う PING 起床判断を移します。  
私有入口は `thread_recv_health_check_peers`、`thread_recv_health_check_service`、`thread_recv_health_wake_tcp` とし、移動元と同じコンテキスト、受信スロット、パス番号・状態変化の入力を使用します。

`potr_recv_thread.c` は、poll タイムアウト時と TCP 状態変化時の現在の位置から監視関数を呼びます。  
監視は同じ受信スレッドで実行し、新しいスレッドやタイマーは追加しません。  
パケット受信・認証とパケット別処理は既存の担当箇所に残します。

N:1 の監視は `peers_mutex` の保持範囲とロック解放後の health 起床を維持します。  
タイムアウト無効時の処理順序、期限との比較、パス単位とサービス・ピア単位の状態初期化、通知順序、PING 状態の消去、受信ウィンドウの初期化を保持します。  
TCP の PING 判断は、health が稼働している場合の起床と、即時送信の分岐を維持します。  
`thread_recv_session`、`thread_recv_slot`、`thread_recv_window`、`thread_recv_dispatch` の既存処理を再利用します。

## 新しい内部ファイルは既存のビルドとテスト構成へ組み込む

新しいソースと私有ヘッダーは、既存の api・thread ディレクトリ内に置きます。  
既存 makefile のソース探索を使い、`ADD_SRCS` に相対パスを列挙する構成は追加しません。  
公開ヘッダーには分離した内部関数を宣言しません。

単体テストは `test/src/libporter/` 配下の既存構成に合わせ、次の担当で追加・更新します。  
各ソースの実体を検証する `TEST_SRCS` は 1 つのテストに置き、呼び出し元のテストでは内部関数のモックを使用します。  
私有ヘッダー用の `INCDIR` に元の api・thread ディレクトリを指定します。

- `apiOpenPathsTest`: 方式選択、未対応方式、宛先設定と結果の伝達
- `apiOpenPathsUdpTest`、`apiOpenPathsTcpTest`、`apiOpenPathsCommonTest`: 方式別の正常準備、アドレス不正、操作失敗、途中失敗時の所有権
- `threadConnectPrepareTest`: 接続成功・失敗、停止要求、待機期限、EOF・I/O エラー・長さ境界、接続元の選別、セッションの新旧と同一
- `threadRecvHealthTest`: 監視無効、期限直前・一致・経過、パスとピアの状態更新、通知と起床、TCP の即時 PING 分岐
- `potrConnectThreadTest`、`potrRecvThreadTest`: 呼び出し境界と既存 start/stop・部分失敗回収の回帰

依存呼び出しの制御には既存の `Mock_porter`、`mock_cplat`、`mock_libc` を使います。  
分離した通常 C 関数に必要なモックは、既存の弱いラッパー方式に合わせて追加します。  
実ソースとモックを同じ検証対象で重複定義しない構成を維持します。

## 各段階の局所検証で動作の保持を確かめる

BL-003、BL-002、BL-004 ごとに porter の製品・モックをビルドし、変更した内部処理と呼び出し元のテストを実行します。  
資源解放とスレッド管理への影響に応じて、`apiContextCleanupTest`、`potrServiceOpenTest`、`potrConnectedThreadsTest`、`potrPathEventTest` などを選びます。  
内容のある対象範囲の `.warn` を確認し、変更起因の失敗と警告を修正して再検証します。  
同じ差分の成功結果は再利用します。

実通信では `porterSendRecvTest` から、unicast と N:1 の最終 DATA 送信後の close、および暗号化 TCP 双方向通信の既存ケースを実行します。  
監視の変更については、関連する既存の health・パス状態のケースを選び、実行フィルターと件数を記録します。  
Linux 限定の `tcpMultipathTest` は Windows の成功件数に含めません。

利用可能な Windows/MSVC 環境の局所検証で受入れを判断し、Linux/GCC のビルド・実通信が未実施の場合は明記します。  
複数 app やワークスペース全体のテストが必要になった場合は、コストを説明して個別に確認します。

新規 C/C++ ソースは適用規範に従って整形し、既存ソースは変更範囲を確認します。  
Markdown はファイルごとに `text_style_jp.py --dry-run` の変換内容を確認してから `--in-place` を実行します。  
宣言側の Doxygen を整え、`make -C app/porter doxy` と警告確認を行います。

## 恒久的な責務は正本と宣言側に残す

`app/porter/docs/architecture.md` に、方式選択と方式固有準備、接続管理と接続前処理、受信ループと監視処理の担当を反映します。  
`sequence-tcp.md` には、接続前処理からロック取得・認証・共有状態の採用へ進む順序とソケット所有権を反映します。  
`sequence-health.md` には、同じ受信スレッドによる監視と N:1 のロック解放後の起床を反映します。  
これらの文書は既存の配置先を使用します。  
私有ヘッダーには入力・出力、比較時のロック保持条件、ソケット所有権を記載します。

## 受入条件は責務の分離と既存動作の保持で判定する

- 方式別準備が UDP・TCP に分かれ、IPv4 の共通処理が重複していないこと
- 接続前処理を単独検証でき、共有状態の採用・ロック管理・通知・スレッド管理が既存ループに残っていること
- N:1・1:1 の監視と TCP の起床判断が内部ファイルへまとまり、同じ受信スレッドから呼ばれること
- 公開契約と BL-001 の資源管理を保持し、局所ビルド・テスト・警告・Doxygen の確認を終えていること
- 正本文書と宣言側の契約が実装に一致し、実施した検証と未確認 OS を区別して報告していること

完了時は既存の残課題一覧から解消した BL-002〜004 を除外します。  
新たに判明して今回は対策しなかった残課題があれば、事象、影響、見送り理由と恒久対応案を記録します。  
未対応の残課題がなければ、その旨を完了報告に記載します。  
成果物と検証結果を提示した後に受入承認を確認します。  
ステージング、コミット、プッシュは今回の作業に含めません。
