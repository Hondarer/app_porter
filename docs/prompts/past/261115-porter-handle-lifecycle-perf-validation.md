# porter ハンドル寿命管理の追加性能評価の検証記録

この文書は、ハンドル寿命管理の改修 (専用通知スレッド、通知キュー、ハンドル制御情報の保持) について、改修時に未確認だった性能を測定した結果を記録します。  
数値は同一マシン上のループバック通信の値であり、ネットワークを介した実運用の性能を保証するものではありません。  
条件ごとの数値は [CSV](261115-porter-handle-lifecycle-perf.csv) にあります。

## 対象版と環境

| 区分 | 内容 |
| --- | --- |
| 改修前版 | porter `9e55a0c`、cplat `9f3c304`、cjson `c759dc9` (親リポジトリ `f2d8dfde` の固定版) |
| 現行版 | porter `6e9002c`、cplat `fd903dc1` (本案件の TCP 修正を含む)、親リポジトリ `a55fa2ca` 固定の cjson |
| 外部ライブラリ | zlib と OpenSSL は、両版とも現行の固定版のビルド済みライブラリ (改修前版は OpenSSL に依存しない) |
| Windows | Windows 11 の実機、MSVC 14.50 |
| Linux | 同じ物理マシン上の WSL2 (NAT モード)、Oracle Linux Server 8.10、GCC 8.5.0、glibc 2.28 |

Table: 対象版と測定環境

両 OS は同じ物理マシンを共有するため、測定は条件群ごとに Windows と Linux で交互に行い、片方の測定中はもう片方を待機させました。  
WSL の NAT モードでは WSL 内の待ち受けに Windows の localhost から接続できるため、基準ポートを OS ごとに分けました (Windows 39000、Linux 29000)。

## ビルドと測定方法

測定プログラムはリポジトリに置かず、公開 API だけを使う C++17 のプログラムを両版で共用しました。版の差は `BENCH_PORTER_OLD` の条件付きコンパイルで吸収しました。  
両版とも makefw は使わず、porter、cplat、cjson の `prod/libsrc/` を直接コンパイルして静的に結合しました。

| 対象 | Windows/MSVC | Linux/GCC |
| --- | --- | --- |
| 製品の C | `/std:c17 /O2 /MD /DNDEBUG /W4` と静的結合用の定義 | `-O2 -DNDEBUG -fno-omit-frame-pointer -g -fPIC -fvisibility=hidden` と makefw 相当の C17 指定 |
| 測定プログラム | `/std:c++17 /O2 /MD /DNDEBUG /EHsc` | `-std=c++17 -O2 -DNDEBUG -fno-omit-frame-pointer` |
| zlib | 改修前版は同梱パッケージから接頭辞なしの静的ライブラリ、現行版は `zlib_app` 接頭辞付きの静的ライブラリ | 両版とも `libzlib_app.so`。改修前版の cplat には名前対応ヘッダーを強制インクルード |
| OpenSSL (現行版) | DLL のインポート ライブラリ (Windows 用の静的ライブラリがないため) | `libssl.a`、`libcrypto.a` |

Table: OS ごとのビルド方法

各条件は 1 プロセス内で 5 回実行し、各実行の先頭のウォーム アップ (1000 件、P4 は 10 サイクル) を結果から除きました。  
1 回の実行内で中央値・p95・p99 を求め、5 回分の最小・中央値・最大を CSV に記録しています。本文の値は 5 回の中央値です。  
通知遅延は、送信直前の単調時計の値を本文に書き、受信コールバックの入口で差を取りました。  
メモリは、Windows が `GetProcessMemoryInfo` の `WorkingSetSize` と `PrivateUsage`、Linux が `/proc/self/status` の `VmRSS` と `RssAnon` で、各実行の開始時点からの増加量を記録しました。

| ID | 項目 | 負荷 |
| --- | --- | --- |
| P1 | UDP の遅延分布 | 64 / 5000 バイト、通常・圧縮・ブロッキング・圧縮とブロッキング、1 / 4 スレッド。各スレッド 10000 件、同時未完了はスレッドあたり 16 件まで |
| P2 | N:1 返信 | クライアント 4 本が 64 / 5000 バイトの要求を各 5000 件送り、サーバーが返信 (コールバック内 `cb`、外部スレッド `ext`) |
| P3 | 低速コールバック | 受信コールバックが 1 件ごとに 1[ms] 待機。5000 バイトを 10000 件、間隔なしで送信 |
| P4 | open/close 反復 | open、接続、1 件の送受信、close を 1000 サイクル。UDP と TCP (片方向) |
| P5 | TCP の遅延分布 | P1 と同じ組み合わせを TCP (片方向) で実施。現行版だけ TCP 双方向 64 バイトを追加 |

Table: 測定条件

> [!NOTE]
> P1 の 5000 バイト・通常・4 スレッドは、Linux で既定負荷が 900 秒以内に終わらなかったため、件数を 1000 件 (ウォーム アップ 100 件) に減らした追加条件を両 OS で測りました。
> P4 は、Windows のスレッド数の取得が重いため、保持量の傾きの標本を 10 サイクルごと (と 100 サイクルごとのチェックポイント) に取っています。close の計測区間には影響しません。

## TCP 終了時エラーの切り分けと修正

元案件の予備測定で記録された TCP の終了時エラーを、次の 3 つに切り分けました。

| 事象 | 発生する版と OS | 扱い |
| --- | --- | --- |
| TCP 双方向で片端を close した後、もう片端の close が 5[s] 後に `POTR_ERR_TIMEOUT` になる | 両版、Windows | 製品不具合として本案件で修正 |
| TCP の送信バッファーが満杯のとき DATA を黙って捨て (`send buffer full, packet skipped`)、受信と close が待ちきれない | 改修前版、Windows | 元案件で修正済みの既存不具合。改修前版の P5 の 5000 バイト・圧縮なし 4 条件は比較不能 |
| TCP 双方向の close が受信スレッドの join で停止する | 改修前版、Linux | 改修前版の既存不具合。現行版では再現しない |

Table: TCP の終了時エラーの切り分け

1 つ目の原因は 3 点でした。cplat の単一ソケット待機が `POLLHUP` を待機解除と扱わず、Windows の `WSAPoll` が相手の正常切断で `POLLHUP` だけを返すと、受信スレッドが切断に気付きませんでした。  
porter は相手の FIN に FIN_ACK を返した後も経路を維持し、close の FIN_ACK 待ちは経路の切断で起こされませんでした。  
修正は cplat `fd903dc1` と porter `6e9002c` です。相手の FIN を受理した経路は受信スレッドを終了し、close は相手の FIN の受理後に DATA を書いていなければ FIN を送らずに `POTR_OK` を返します。

修正後の局所テストは、両 OS とも失敗 0 件、内容のある `.warn` は 0 件でした。

| テスト | Windows | Linux |
| --- | --- | --- |
| cplat `socketTest` | 33 件成功 | 47 件成功 |
| `potrRecvThreadTest` / `potrServiceCloseTest` / `potrConnectThreadTest` / `potrSendThreadTest` | 10 / 10 / 7 / 15 件成功 | 10 / 10 / 7 / 15 件成功 |
| 結合試験 `porterSendRecvTest` | 36 件成功を 5 回 | 49 件成功を 3 回 |

Table: 修正後の局所テストの結果

結合試験の件数の差は、`tcpMultipathTest.cc` などに `PLATFORM_LINUX` の条件でだけ登録されるテストがあるためです。  
両版に共通する TCP の約 40[ms] の停止 (TCP_NODELAY がないことによる Nagle と遅延 ACK の組み合わせ) は、版の差と分けて扱い、[残課題 BL-001](261115-porter-handle-lifecycle-perf-backlog.md#bl-001-tcp-の送信ソケットに-tcp_nodelay-がなく約-40ms-の停止が生じる) に記録しました。

コールバック内返信は、両 OS とも現行版の外部スレッド返信より往復時間が短く、Linux では改修前版の外部スレッド返信とほぼ同じ値でした。  
外部スレッド返信を改修前後で比べると、Windows は現行版が速く、Linux は 64 バイトで往復時間が約 1.5 倍、処理件数が約 0.69 倍になりました。  
5000 バイトの p99 が約 0.23〜0.25[s] になるのは、両版とも UDP の受信バッファーがあふれて再送で回復する時間を含むためです。全条件で受信欠落はありませんでした。

## 低速コールバック (P3)

| OS | 版 | 欠落 (10000 件中) | 通知遅延 p50 / p99 / 最大 | 私有量のピーク増加 | 1[s] 後の私有量の増加 |
| --- | --- | --- | --- | --- | --- |
| Windows | 改修前版 | 5 回とも 10000 | - | 約 32[KiB] | 0 |
| Windows | 現行版 | 4 回が 10000、1 回が 0 | 欠落なしの回: 8.9 / 17.5 / 17.7[s] | 欠落なしの回: 約 46[MiB] | 欠落なしの回: 約 46[MiB] |
| Linux | 改修前版 | 5 回とも 10000 | - | 0 | 0 |
| Linux | 現行版 | 5 回とも 0 | 4.5 / 8.9 / 9.0[s] | 約 37.7[MiB] | 約 37.7[MiB] |

Table: P3 の欠落、通知遅延、メモリ

改修前版は、コールバックが受信スレッドを止めるため受信ウィンドウが満杯になり、回復できない欠落 (REJECT) の後は測定区間の全件が届きませんでした。  
現行版は受信スレッドを止めずに通知キューへ保持するため、欠落がなかった回は全件を届けましたが、通知遅延は最大で約 9〜18[s]、保持メモリは約 38〜46[MiB] に達しました。  
全通知の消費後 1[s] の時点でも私有量は減っていません。通知ノードを再利用する設計と、ヒープが解放した領域を OS へ返さないことによると考えます。close 後の回収量は測っていません。

Windows の現行版で 4 回が全件欠落した原因は、受信ウィンドウの基準通番が回復できない欠落の後に進まなくなる停止です。ログでは基準通番が 831 のまま、受信通番だけが 43913 まで進んでいました。  
この停止は改修前版でも同じ形で起きており、ハンドル寿命管理の改修とは別の問題として [残課題 BL-002](261115-porter-handle-lifecycle-perf-backlog.md#bl-002-udp-の受信ウィンドウが回復不能な欠落の後に進まなくなる) に記録しました。

| OS | 通信種別 | close p50 / p99 [ms] 改修前版 | 同 現行版 | 私有量の傾き [バイト/サイクル] 改修前版 / 現行版 |
| --- | --- | --- | --- | --- |
| Windows | UDP | 0.66 / 1.00 | 0.81 / 1.36 | 25 / 388 |
| Windows | TCP | 1.65 / 16.98 | 1.39 / 16.66 | 40 / 308 |
| Linux | UDP | 0.50 / 0.83 | 0.52 / 0.79 | 0 / 0 (検出不能) |
| Linux | TCP | 1.43 / 44.8 | 42.9 / 45.3 | 0 / 0 (検出不能) |

Table: P4 の close の所要時間と保持量の傾き

通信資源は回収されています。両 OS、両版、両通信種別で、ハンドル数とスレッド数の傾きは 0 でした。  
現行版は 1 サイクルで 2 ハンドルを open するため、Windows の値からハンドルあたり約 150〜190 バイトの制御情報を保持していると見積もれます。これは、古いハンドルを識別する制御情報を累計 open 数に比例して保持する設計と一致します。  
Linux の `VmRSS` と `RssAnon` はページ単位で、解放済みの領域が再利用されるため、1 サイクルあたり数百バイトの保持は検出できませんでした。  
Linux の現行版の TCP で close が毎回約 43[ms] かかるのは、close が FIN_ACK を待つため、BL-001 の停止が毎回表れることによります。

改修前版に対する現行版の変化 (中央値) は、条件によって大きく異なりました。主な傾向を次に示します。全条件の値は CSV にあります。

ブロッキング送信では、両 OS とも処理件数の差は数 % 以内でした。  
小さいメッセージの非ブロッキング送信では、通知スレッドへの受け渡しの負担が相対的に大きく、処理件数が 2〜3 割低下しました。  
圧縮を指定した非ブロッキング送信、特に 4 スレッドで、処理件数の低下と通知遅延 p99 の増加が大きくなりました (p99 は最大で約 8 倍)。原因は特定していません。[残課題 BL-003](261115-porter-handle-lifecycle-perf-backlog.md#bl-003-小さいメッセージと圧縮送信で処理件数が低下し通知遅延が増える) に記録しました。  
Linux の P5 は、ブロッキングと 4 スレッドの多くの条件で通知遅延 p99 が約 42〜44[ms] となり、版の差より BL-001 の停止が支配的です。

### UDP の受信バッファーがあふれる条件

5000 バイト・通常 (圧縮なし、非ブロッキング) の P1 は、両版とも UDP の受信バッファーがあふれて再送で回復する状態になり、処理件数は 1 秒あたり数百件、通知遅延 p99 は数秒でした。

- Windows の既定負荷 (4 スレッド): 改修前版 631 件/秒、現行版 605 件/秒、所要時間は 406 秒と 507 秒です。
- Linux の既定負荷 (4 スレッド): 両版とも 900 秒で打ち切りました。打ち切り時点の受信通番は改修前版が約 14,163、現行版が約 175,815 で、受信ウィンドウの警告は改修前版 37,104 行、現行版 33,801 行でした。
- 件数を減らした追加条件では、処理件数の 5 回の値が実行ごとに 2 桁以上ばらつきました (Linux の改修前版で 103〜23,704 件/秒、現行版で 62〜5,664 件/秒)。版の差より実行ごとの差が大きく、版の比較には適しません。

Linux の UDP 受信バッファーは、既定値・最大値とも 212,992 バイトです。同時未完了の 5000 バイト × 16 件 × 4 スレッドは、この値を大きく超えます。

## 測定の限界

- 同じ物理マシン上のループバック通信で、Linux は WSL2 の仮想マシンです。CPU とキャッシュを共有するため、測定を交互にしても他の常駐プロセスの影響は除けていません。
- 改修前版の Windows の P5 5000 バイト・圧縮なし 4 条件は、改修前版の既存不具合で完了せず、比較していません。改修前版の TCP 双方向は Linux で停止するため、測っていません。
- Linux では、制御情報の保持量 (1 サイクルあたり数百バイト) を検出できませんでした。
- メモリ確保回数とコピー量は、今回の測定プログラムでは計測していません。元案件の UDP 24 条件の記録を参照してください。
- 同時未完了の制限はスレッドあたり 16 件で、元案件の測定 (全体で 16 件) とは負荷が異なります。最大送信能力の測定ではありません。

## 結果の判断材料

ハンドル寿命管理の改修による追加コストは、次のとおりです。

- 通常送信の API 呼び出し時間は、両 OS とも版の差が小さいです。
- 非ブロッキング送信の処理件数は、小さいメッセージで 2〜3 割、圧縮かつ複数スレッドで最大 7 割低下します。
- 通知遅延は、通知スレッドを経由する分だけ増えます (64 バイト・通常・1 スレッドの p50 で、Windows は約 14[µs]、Linux は約 23[µs] の増加)。
- コールバック内返信は、外部スレッド返信より往復時間が短く、新しい返信経路として性能上の不利はありません。
- 低速コールバックでは、改修前版の全件欠落に対して現行版は全件を届けられます。その代わり、受信量に比例してメモリを保持し、通知遅延が秒単位に伸びます。
- open/close の反復では通信資源を回収し、ハンドルあたり約 150〜190 バイトの制御情報を保持します。
