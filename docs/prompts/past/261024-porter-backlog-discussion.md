## BL-001 の初期調査で確認した解放経路

以下は 2026-10-24 の実装を静的に照合した結果です。  
障害の動的再現、ビルド、テストはまだ実施していません。

- コンテキスト本体、送受信ウィンドウ、共通バッファーは `potr_service_open.c` が生成します。開始失敗時は `ctx_cleanup`、通常終了時は `potr_service_close.c` が解放します。
- UDP ソケット、TCP listen ソケット、N:1 ピアテーブルは `api_open_paths.c` が準備します。TCP 接続ソケットは接続管理スレッドも更新し、通常終了時は `potr_internal_connect_thread_stop` が各パスの停止・待機とソケットの解放を担います。
- N:1 のピア別ウィンドウ、断片バッファー、ロックは `potr_peer_table.c` が管理します。通常終了では使用する全スレッドの停止後にテーブルを解放します。コンテキスト側でもウィンドウは確保されるため、ピア側と区別した所有権一覧が必要です。
- TCP の同期資源は `start_threads_tcp` が生成しますが、失敗時の `destroy_tcp_sync_primitives` には `health_mutex[]` と `health_wakeup[]` の破棄がありません。通常終了側には両方の破棄があります。
- `potr_internal_connect_thread_start` はパスごとにスレッドを生成します。途中の生成に失敗すると、それ以前に起動したスレッドを停止せずに戻り、呼び出し側は同期資源とコンテキストを解放します。最初の生成で失敗した場合も、受信者用の先読みバッファーと `session_establish_mutex` の回収経路を確認する必要があります。現行 stop は稼働スレッドがない場合に早期 return するため、そのまま呼ぶだけでは十分ではありません。
- UDP の `potr_internal_health_thread_start` はロックと条件変数を生成しますが、スレッド生成失敗時にこれらを破棄せずに戻ります。send スレッドの開始・停止とキューには別の巻き戻し処理があるため、共通解放へ移す際に二重解放を避ける必要があります。
- 通常終了の `dispose_secret_buffers` は共通バッファーと設定コピー内の鍵を消去します。開始失敗の `ctx_cleanup` は受信用の一部バッファーを消去しますが、`frag_buf`、`compress_buf`、`crypto_buf`、`recv_buf` と設定コピー内の鍵は消去していません。

根拠ファイルは [開始処理](../../../prod/libsrc/porter/api/potr_service_open.c)、[終了処理](../../../prod/libsrc/porter/api/potr_service_close.c)、[接続管理](../../../prod/libsrc/porter/thread/potr_connect_thread.c)、[ヘルス監視](../../../prod/libsrc/porter/thread/potr_health_thread.c)、[ピア資源管理](../../../prod/libsrc/porter/potr_peer_table.c) です。

既存の `potrConnectedThreadsTest` は接続後のスレッド開始を mock で検証しています。  
`porterSendRecvTest` には通常終了時の最終 DATA 配信、N:1 終了、暗号化 TCP 双方向通信などのケースがあります。  
部分初期化の失敗と解放順序には、生成失敗を注入する局所テストの追加を提案します。  
資源の所有者と停止後の解放条件は `app/porter/docs/architecture.md`、開始失敗と通常終了の境界は `app/porter/docs/sequence-lifecycle.md` への反映を検討します。
