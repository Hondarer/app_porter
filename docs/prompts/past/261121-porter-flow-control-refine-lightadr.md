## LADR-001 遅い送受信者の救済より全体の健全な動作を優先する

決定者: Tetsuo Honda  
最終更新日: 2026-11-21

### 背景と課題

フロー制御の案件 (`261119-porter-flow-control`) の残課題には、遅い相手にどこまで合わせるかの判断が必要な項目 (BL-006、BL-007、BL-009、BL-011) があります。対策の方針を決める基準が必要でした。

### 得られた事実

- `multicast` と `broadcast` の既定の構成では、受信者が同じ速さでも、連続送信で欠落と切断が起きます (`261119-porter-flow-control-backlog.md` の BL-006。3 回の実行で 3 回とも発生)。
- しきい値 (`flow_control_receiver_count`) を 1 にすると、全受信者が全件を受信しますが、送信者は最も遅い受信者に合わせます (同じ文書の BL-006 の再現条件と恒久対応案)。
- N 対 1 サーバーの全ピア宛の送信は、抑制中のピアが 1 つでもあると、どのピアにも送られません (`261119-porter-flow-control-design.md` の「送信要求の受け付け」)。

### 決定

複数台との通信で、何らかの原因でスループットが下がった一定割合の送受信者は、救済を優先しません。システム全体が健全に動作することを優先します。

## LADR-002 スループットを高く維持する

決定者: Tetsuo Honda  
最終更新日: 2026-11-21

### 背景と課題

フロー制御の案件の残課題には、送出上限の通知によって処理件数が下がる項目 (BL-007) があります。信頼性のための仕組みと、スループットのどちらを優先するかの基準が必要でした。

### 得られた事実

- N 対 1 サーバー (クライアント 4 つ) で、OS の受信バッファーに基づく送出上限を有効にすると、処理件数が 15.8% 下がります (`261119-porter-flow-control-backlog.md` の BL-007。2026-11-21 の Linux での測定)。
- `unicast` では、有効と無効の差は −0.6% から +3.5% です (同じ測定)。
- `unicast` と `tcp` の処理件数を同じ条件で比べた測定は、フロー制御の案件では行っていません。

### 決定

スループットを高く維持することを目指します。porter の UDP は、TCP に比べて高スループットで高信頼であることを特徴とします。

## LADR-003 フロー制御でバッファーのあふれを回避する

決定者: Tetsuo Honda  
最終更新日: 2026-11-21

### 背景と課題

フロー制御の案件の最終仕様は、OS の受信バッファーのあふれを防げない場合を、制約として残しています。これらを現状どおりとするか、対策するかの基準が必要でした。

### 得られた事実

## LADR-005 1 対 N で救済しない受信者の判定

決定者: Tetsuo Honda  
最終更新日: 2026-11-21

### 背景と課題

`multicast` と `broadcast` で、救済しない受信者 (スループットが下がった受信者) と、守る受信者 (一時的に遅れただけの健全な受信者) を見分ける方法と、救済しない受信者の数の上限、救済しないと判定した受信者の扱いを決める必要がありました。

### 得られた事実

- 現在は、上限に達した監視対象が「しきい値」(既定 2 台) 以上になるまで、送信者は止まりません。このため、健全な受信者が 1 台だけ一瞬遅れた場合も、救済しない受信者として扱われます。
- 受信者が同じ速さでも、最も遅い受信者が入れ替わりながら欠落し、保持範囲を超えると切断になります (BL-006。3 回の実行で 3 回とも発生)。
- しきい値を 1 にすると全受信者が守られますが、常に遅い受信者が 1 台いるだけで、全体がその受信者の速さになります。
- 上限を超える数の受信者が遅い場合は、送信者がその受信者に合わせて遅くなります。
- 現在の既定は、台数の条件が 2 (1 台までを無視)、割合の条件が無効です。このため、受信者が 100 台でも、無視できるのは 1 台です。
- 送信者が待たなくなった受信者は、OS の受信バッファーがあふれて欠落し、NACK で再送を求めます。欠落が保持範囲を超えると、送信者が REJECT を返し、受信者は切断になり、次のパケットから受信をやり直します。この動作は、現在の「外れ値」の受信者と同じです。
- 遅い受信者の NACK と再送は、送信者と経路の負荷になります。この負荷が健全な受信者のスループットをどの程度下げるかは、測定していません。

### 決定

止まった時間で見分けます。送信者は、監視対象のどれか 1 台が上限に達したら止まります。猶予時間を超えて止め続けた受信者は、救済しない受信者として判定から外します。救済しない受信者の数の上限は、「1 台」と「活動中の受信者数の 10% (切り捨て)」の大きいほうとします。救済しないと判定した受信者には特別な扱いをせず、欠落と NACK、保持範囲を超えた場合の切断に任せます。健全な受信者への影響は、受入の確認で測定します。

## LADR-007 N 対 1 サーバーの受信バッファーの幅の配分

決定者: Tetsuo Honda  
最終更新日: 2026-11-21

### 背景と課題

N 対 1 サーバーが、OS の受信バッファーの幅をピアの間でどう分けるかと、送信中のピアが多く下限が働く場合のあふれの防ぎ方を決める必要がありました。

### 得られた事実

- 現在は、すべてのピアが 1 つのソケットを共有するため、幅を「接続中のピア数」で割っています。ピアが 4 つの場合、幅はピアごとに 10 パケットになり、送出上限の更新が約 5 パケットにつき 1 個に増えます。この更新の分だけ、処理件数が約 16% 下がりました (BL-007)。
- 接続しているだけで送信していないピアにも、幅を割り当てています。
- 幅をピア数で割った結果が 4 未満の場合は、4 とします。この場合、全ピアへの許可の合計が、OS の受信バッファーに収まる数を超えます (OS の受信バッファーが既定の Linux で、送信中のピアが 11 以上の場合)。
- 現在は、下限が働く場合も、全ピアに 4 パケットずつ許可します。同時に送信されるとあふれ、再送で回復します。

### 決定

幅は、送信中のピア数で割ります。「送信中のピア」は、直近の一定時間に DATA を受信したピアです。ピアごとの幅が下限 (4 パケット) になる場合は、サーバーが、許可の合計が全体の幅に収まるように、許可を出すピアを順番に切り替えます。許可のないピアは、順番が来るまで止まります。

## LADR-008 OS の受信バッファーの拡大の要求

porter が UDP の受信に使うソケットを開くときに、OS の受信バッファーの拡大を要求するかを決める必要がありました。

## LADR-009 送出上限を知らせる経路の追加

決定者: Tetsuo Honda  
最終更新日: 2026-11-21

### 背景と課題

送出上限の更新の専用パケットの数と、`unicast` で更新が続けて失われた場合の回復の経路を決める必要がありました。

### 得られた事実

- 送出上限の更新は、専用のフロー制御パケットで送っています。双方向の通信で両方向に DATA が流れている場合、逆方向の DATA のヘッダーに送出上限を載せれば、専用のパケットを送らずに済みます。
- DATA パケットのヘッダーの `ack_num` (4 byte) は、現在は 0 固定で、受信時に無視しています。ここに送出上限を載せても、パケットの大きさは変わりません。「載せている」ことを示すフラグを 1 つ追加します。
- プロトコルの変更になります。フロー制御の導入で、プロトコル バージョンは 3 になっています。片方向の通信種別には、逆方向の DATA がないため、効果がありません。
- `multicast` と `broadcast` の受信者は、周期的に送る受信報告に送出上限を載せますが、`unicast` の受信者は載せません。
- `unicast` では、送出上限の更新のパケットが続けて失われると、送信者は、有効期限 (既定 1 秒) の後に送出上限を破棄して、次の通知が届くまで制限なく送出します (BL-012)。
- 受信報告の欄 (`seq_num`、`ack_num`) は、すでに定義されています。載せても、パケットの数と大きさは変わりません。

### 決定

双方向の通信種別 (`unicast_bidir`、`unicast_bidir_n1`) で、逆方向へ送る DATA パケットのヘッダーに送出上限を載せます。逆方向の DATA で知らせた分は、専用のパケットを送りません。`unicast` の受信報告にも送出上限を載せ、送信者は、受信報告の送出上限を、更新の喪失からの回復に使います。

## LADR-012 あふれを防ぐ対象と、防げなかった場合への対策

決定者: Tetsuo Honda  
最終更新日: 2026-11-21

### 背景と課題

フロー制御によるあふれの回避を高信頼として扱う (LADR-003) うえで、防ぐ対象の範囲と、前の案件の最終仕様が防げないとした場合への対策を決める必要がありました。

### 得られた事実

- 前の案件の最終仕様は、OS の受信バッファーのあふれを防げない場合として、次の 8 件を挙げています。最初の送出上限が届く前の送出、送出上限の通知が続けて失われた場合、`multicast` と `broadcast` の監視対象に選ばれていない受信者と急に遅くなった受信者、同じく外れ値として判定から外れる受信者、同じく受信報告を送らない構成の受信者、N 対 1 サーバーで幅の下限が働く数のピアが同時に連続して送信した場合、DATA 以外のパケットが多い場合、圧縮した DATA。
- 現在の送信側は、送出上限を受けるまで、制限なく送出します。接続の直後に連続して送信すると、最初の通知が届く前に、受信側の OS の受信バッファーがあふれます。
- 送出上限を使わない受信側 (フロー制御と、OS の受信バッファーに基づく送出上限の両方が無効) は、現在は何も通知しません。
- 現在の送信側は、有効期限 (既定 1 秒) の後に送出上限を破棄し、次の通知が届くまで制限なく送出します。この間は、あふれを防げません。破棄するのは、相手が停止した場合に、送信が止まったままにならないようにするためです。相手の停止は、死活監視 (PING と受信報告のタイムアウト) でも検出できます。
- 現在は、次の受信報告 (既定で最長 4.5 秒後) が届くまで、監視対象の外の受信者は監視対象に加わらず、守られません (BL-009)。
- OS の受信バッファーの中の量を、受信者が直接知る共通の手段はありません。受信者が、送信者の最新の通番と、処理を終えた通番の差を見る方法の精度は、未確認です。
- 受信報告を送らない受信者は、送信者から見えないため、現在は対象外です。
- 幅は、DATA パケットだけが OS の受信バッファーを使う前提で計算しています。1 パケットの見積もりは安全側で、同じホストの Linux の実測では、1,000 byte の DATA が約 90 個収まるのに対して、幅は 42 パケットです。Windows でパケット 1 個が使う量は、実測していません。
- 受信側は、許可数を「1 パケットが `max_payload` byte」として計算します。圧縮した DATA は、展開後の大きさが `max_payload` を超えるため、許可した数のパケットで、計算より多くの容量を使います。現在は、要求のしきい値から容量までの余裕で受け止め、超えた場合は切断になります。

### 決定

健全な送受信者が受けるあふれを、すべて防ぐ対象にします。方針 1 で救済しないと判定した送受信者だけを、対象から外します。防げなかった場合への対策は、次のとおりです。

- 送信側は、最初の通知を受けるまで、初期の幅までで止まります。受信側は、最初のパケットを受理した時点で、送出上限または「使わない」を通知します。
- 送信側は、止まっている間、相手へ送出上限を問い合わせます。制限なしにはしません。
- `multicast` と `broadcast` で、監視対象の外の受信者が遅れ始めたことの合図は、受信者の NACK と、受信者が読み出しの遅れを自身で検出した時点で送る臨時の受信報告の両方にします。臨時の受信報告の検出の方法は、実装の前に試作で確かめます。
- 受信報告を送らない構成の受信者は、対象外のままとします。あふれを防ぐには受信報告が必要であることを、文書に記載します。
- DATA 以外のパケットの分の新たな余白は設けません。Windows の実測で、見積もりが安全側であることを確かめ、足りない場合は、見積もりの式を見直します。
- 受信側は、観測した展開後の大きさで、許可数を計算します。

## LADR-014 1 対 N で送出上限を知らせる受信者の数

## LADR-015 N 対 1 サーバーの順番の許可の詳細

決定者: エージェント (LADR-013 に基づく設計の詳細。ユーザーへ報告し、最終仕様の改版と成果物の承認で確認を受ける)  
最終更新日: 2026-11-22

### 背景と課題

最終仕様 (版 1) の「N 対 1 サーバー」の「幅の配分」は、ピアごとの幅が 4 未満になる場合に、許可を順番に出すと定めています。実装の段階で、次の 3 点が、最終仕様から決まらないことが分かりました。

- 順番を待っているピアが、まだ最初の通知を受けていない場合に、何を知らせるか (初期の幅との関係)。
- 受信バッファーの幅の下限 (4 パケット) を、全体の幅とピアごとの幅のどちらに適用するか。
- 順番を待っているピアへ、逆方向の DATA を送出するときに、送出上限を載せるか。

### 得られた事実

- サーバーは、クライアントが初期の幅の基準にしている通番を、知る手段がありません。サーバーが知っているのは、そのピアから次に受信する通番だけです。
- 現在の実装は、全体の幅を接続中のピア数で割った後に、下限の 4 を適用しています。このままでは、ピアごとの幅が 4 未満にならず、順番の許可に入りません。
- 逆方向の DATA への相乗りは、DATA の送出のたびに、その時点の許可数で送出上限を計算します。順番の許可のピアに、DATA のたびに 4 を足すと、許可が延び続け、順番になりません。
- 容量を設定した受信側は、占有量がしきい値を超えている間、許可数 0 (送出上限 = 次に受信する通番) を知らせます。この動作は、前の案件から実装済みです。

### 決定

- 幅の下限は、全体の幅に適用します。ピアごとの幅には適用しません。
- 順番の許可の間、許可を持つピアの許可数は、受けた許可の残りです。待っているピアと、送信中でないピアの許可数は、0 です (送出上限 = 次に受信する通番)。最初の通知、問い合わせへの応答、逆方向の DATA への相乗りは、この値で行います。
- 「待っているピアの送出上限は、進めません」は、「相手がすでに送出した範囲を超える許可を出さない」という意味で実装します。
- 未通知のピアが送出する初期の幅の分は、同時に許可を持てるピアの数には数えません。
- 通常の配分と順番の許可が切り替わる時点で、すでに知らせた送出上限は戻しません。

## LADR-017 受信報告には許可数の上限を載せる

## LADR-021 N 対 1 サーバーの順番の許可を、未使用の許可の合計で管理する

決定者: Tetsuo Honda (最終仕様の版 5 の承認)  
最終更新日: 2026-11-22

### 背景と課題

最終仕様 (版 4) と LADR-015 は、N 対 1 サーバーのピアごとの幅が 4 未満になる場合に、同時に許可を持つピアの数を「全体の幅 ÷ 4」までに制限していました。この形では、送信をやめたピアが許可を持ったまま枠を占め、待っているピアが許可を受けられませんでした。

### 得られた事実

- 同じホストの `p2` で、クライアント 22 の処理件数は、送出上限を使わない場合の約 18% (16,484 と 93,477 件/秒) でした。許可を持つピアの平均 21 のうち、平均 14 が、10 ms 以上 DATA を送っていませんでした (2026-11-22 の Linux での測定)。
- 未使用の許可の合計で管理し、許可を使い切った時点で配る形にすると、クライアント 22 と 32 で、送出上限を使わない場合の約 7 割になりました。
- レビューで、新しく配った許可が直ちに期限切れになる経路と、DATA を送っていないピアが許可を持ち続ける経路が見つかりました。期限の起点を「最後の DATA の受理と、送出上限を進める通知の送出の、新しいほう」にし、送信側も DATA を送出していない場合に最初の送出上限の受理から許可を縮めることで、両方を直しました。
- 通知や DATA が失われた場合には、合計から外したピアが、初期の幅を超えて送出する筋書きが残ります。パケットの形式を変えずに、完全には防げません。

### 決定

順番の許可は、全ピアの未使用の許可の合計が全体の幅を超えない範囲で出します。送信が途切れたピアの許可は、有効期限の後に合計から外します。通知や DATA が失われた場合のあふれは、再送で回復するものとして許容します (LADR-002、LADR-003 の優先順位による)。順番の許可の間の約 3 割の処理件数の低下は、特性として最終仕様に記載します。

## LADR-022 案件の前からある切断と再接続の不具合を、この案件で直す

決定者: Tetsuo Honda (最終仕様の版 5 の承認)  
最終更新日: 2026-11-22

### 背景と課題

`p2` のクライアント 64 の測定が、まれに終わらなくなりました。原因は、フロー制御ではなく、案件の前からある 2 つの不具合でした。

### 得られた事実

- ローカル ポートを自動割り当てにするソケットでアドレスの再利用を有効にしていたため、同じホストの複数のクライアントに同じローカル ポートが割り当てられ、片方にパケットが届かなくなっていました。
- `unicast_bidir` の送信側の経路タイムアウトが、設定で決まっている宛先のポートを 0 に消していたため、切断の後に再接続できませんでした。
- 修正の後は、クライアント 64 の 60 回の実行で停止が 0 回になり、通信を 12 秒遮断した後に自動で再接続しました。公開 API、設定項目、パケットの形式は変えていません。

### 決定

2 つの不具合を、この案件で直します。`porter-bench` の `p2` は、切断と送信のエラーで、失敗として終わるようにします。調査で疑いが出たほかの 2 点 (切断の状態のピアの回収、宛先の情報の同期) は、不具合と確定できなかったため、対象にしません。
