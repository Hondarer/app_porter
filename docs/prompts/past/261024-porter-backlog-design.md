# porter の開始失敗と通常終了における資源所有権の整理

状態: 完了。最終仕様版 1 の実装・Windows/MSVC 局所検証済み。2026-10-24 のチャット「OK」で成果物の受入承認済み。

## 停止完了を確認してから生成済み資源を解放する

BL-001 として、サービス開始失敗と通常終了の資源所有権を明確にし、スレッド停止後の解放処理を共通化します。  
同じ初期化経路の部分失敗で、起動済みスレッド、同期資源、先読みバッファーが残る経路も対策します。  
開始失敗時にも、通常終了で消去している秘密情報を消去してから解放します。

公開 API のシグネチャ、公開型、ABI、通信形式、成功時の振る舞い、既存のエラー分類と終了時の通知条件を保持します。  
通常終了の FIN 送信、FIN_ACK 待機、キュー排出とスレッド停止の順序を保持します。  
未検査だった同期資源の生成失敗は、その場で失敗として扱い、安全に巻き戻します。  
外部契約の変更が必要と判明した場合は、実装を中断し、具体的な変更案を追加確認します。

BL-002〜004 の接続手順、ソケット準備、受信監視の分離は実施しません。  
接続管理スレッドの開始・停止は、部分起動失敗の回収と所有権管理に必要な範囲で修正します。  
BL-005 はユーザーの対策済み申告に基づいて残課題一覧から除き、この案件の検証成功として扱いません。

## 資源ごとの所有者と使用終了条件

Table: porter サービス資源の所有者と解放条件

| 資源 | 生成・管理する処理 | 解放できる条件と担当 |
| --- | --- | --- |
| コンテキスト本体、設定コピー | `potr_service_open` | 全スレッドの停止と内部資源解放後に呼び出し側が本体を解放 |
| コールバック用ロック | `potr_internal_callback_mutex_init` | コールバックを発火する全スレッドの停止後に共通解放 |
| コンテキストの送受信ウィンドウ | `alloc_context_buffers` | 使用する全スレッドの停止後に共通解放。N:1 のピア別ウィンドウとは別に回収 |
| 共通送受信・圧縮・暗号・断片バッファー | `alloc_context_buffers` | 使用する全スレッドの停止後に共通解放。消去対象は解放前に消去 |
| UDP ソケット、TCP listen・接続ソケット | パス準備処理と接続管理 | 停止のための shutdown・close は既存の停止処理が実施。停止後に残る有効ソケットを共通解放 |
| N:1 ピアテーブルと各ピアの資源 | `potr_peer_table.c` | 使用する全スレッドの停止後に既存のテーブル破棄処理へ委譲 |
| TCP サービス用ロック・条件変数 | `start_threads_tcp` | 接続管理と従属スレッドの終了待ち後に、失敗・通常終了共通の処理で破棄 |
| 送信キュー | TCP・UDP の開始処理 | 送信スレッドと他の利用スレッドの停止後に開始失敗側または通常終了側が破棄 |
| 送信ウィンドウ用ロック | send スレッドの開始処理 | send スレッド生成失敗の巻き戻し、または終了待ち後の stop が破棄 |
| UDP ヘルス監視用ロック・条件変数 | UDP health スレッドの開始処理 | 開始失敗の巻き戻し、または終了待ち後の stop が破棄 |
| TCP ヘルス監視用ロック・条件変数 | `start_threads_tcp` | TCP health の stop では破棄せず、全スレッド停止後に TCP 同期資源とともに破棄 |
| TCP 受信者のセッション確立ロック・先読みバッファー | connect スレッドの開始処理 | 起動成功分を含む全 connect スレッドの終了待ち後、または生成前の失敗時に connect 側が回収 |
| connect・send・recv・health のスレッド ハンドル | 各 start | 生成成功分だけを終了待ちし、成功後にハンドルを NULL へ戻す |

同期オブジェクトと動的バッファーのポインターは NULL、ソケットは `CPLAT_INVALID_SOCKET` を未生成・解放済みの状態として使います。  
生成結果を確認してから次の初期化へ進み、生成失敗時に成功扱いの状態を残しません。  
解放後はメンバーを未生成状態へ戻します。  
既存メンバーで状態を表現し、全資源を一括管理する汎用台帳や関数ポインター表は導入しません。

`*_running` は停止要求や稼働状態を示すため、終了待ちが必要かどうかの唯一の判断材料にしません。  
スレッド関数が先に終了して稼働フラグを下げた場合も、生成済みハンドルがあれば終了待ちします。  
生成失敗したスレッドには join を呼ばず、join 成功後のハンドルへ再度 join を呼びません。  
待機失敗を停止完了として扱ってコンテキストを解放しないことを条件とし、下位 API の契約外の失敗が確認された場合は原因と対処案を追加確認します。

## 共通解放は通信とスレッド停止を実行しない

`prod/libsrc/porter/api/api_context_cleanup.c` と私有ヘッダー `api_context_cleanup.h` を追加します。  
同じ api ディレクトリの既存 makefile による走査を利用し、`ADD_SRCS` への相対パス列挙は行いません。

私有ヘッダーには、停止後のコンテキスト資源解放と TCP 同期資源の破棄を宣言します。  
関数は `api_context_dispose_resources` と `api_context_dispose_tcp_sync` とし、公開 API には追加しません。  
有効なコンテキストと、関連スレッドが未起動または終了待ち済みであることを呼び出し前提として記載します。

`api_context_dispose_resources` は、コンテキストの送受信ウィンドウ、共通バッファー、残存ソケット、N:1 ピアテーブル、コールバック用ロックと設定コピー内の鍵を対象にします。  
本体の free、トレース出力、送信キューの破棄、スレッド停止、FIN 処理、マルチキャスト離脱は呼び出し側に残します。  
開始失敗時の `ctx_cleanup` と、TCP・UDP 通常終了の末尾が同じ解放処理を呼びます。  
TCP 同期資源の破棄は、TCP 開始失敗と通常終了の両方から同じ関数を呼びます。  
UDP health が所有する同期資源は UDP health 側で破棄し、共通関数から重複して破棄しません。

秘密情報の消去対象は `frag_buf`、`compress_buf`、`crypto_buf`、`recv_buf`、`recv_compress_buf`、`recv_crypto_buf`、`tcp_recv_buf[]` と `service.encrypt_key` です。  
各バッファーは既存の確保サイズで消去し、NULL のときは消去を呼びません。  
確保前に失敗した場合も、コピー済みの鍵を消去してからコンテキスト本体を解放します。  
先読みバッファーは connect 側が使用を終えてから回収し、回収時には確保サイズで消去します。  
ウィンドウ、キュー、ピア資源内部の全消去方式を再設計する変更は加えません。

## 部分初期化の失敗は生成した範囲だけ巻き戻す

### サービス開始処理

コールバック用ロック、TCP 同期資源、送信キュー、send・health スレッドの初期化、N:1 ピアテーブル初期化で、対象経路の同期資源生成結果を検査します。  
メモリ確保失敗は `POTR_ERR_OUT_OF_MEMORY`、詳細原因を得られない同期資源・スレッド生成失敗は `POTR_ERR_UNKNOWN` とし、cplat の結果コードをそのまま返しません。  
既存の引数検査、ソケット・設定エラーと失敗時の handle 出力の規約は変更しません。

コールバック ロック初期化は内部関数の戻り値で生成結果を返せる形に変更し、呼び出し側で検査します。  
送信キューとピアテーブルの初期化は、失敗して戻る時点でその関数が生成した資源を回収し、未初期化状態へ戻します。  
呼び出し側は、成功した資源の所有権だけを引き継ぎます。

UDP の send 起動後に health または recv の起動が失敗した場合は、現在の巻き戻し順序を維持し、起動成功分の終了待ちを完了してからキューと共通資源を解放します。  
UDP health のロック・条件変数・スレッド生成のいずれかが失敗した場合は、生成済みの同期資源だけを回収します。  
監視無効でスレッドを生成しない経路も、未生成資源を破棄しません。

### TCP の複数パス起動

受信者用ロックと各パスの先読みバッファーは、connect スレッド生成前の準備として管理します。  
準備中に失敗した場合は、スレッド停止を要求せず、生成済みの準備資源だけを回収します。

途中の connect スレッド生成が失敗した場合は、起動済みパスへ停止を要求し、既存の起床・ソケット shutdown による停止手順を使います。  
起動成功した connect スレッドをすべて join し、それらが管理する recv・health と共有 send スレッドの使用終了を確認してから、受信者用準備資源を回収します。  
この巻き戻しでは FIN 送信、FIN_ACK 待機、通常終了用のキュー排出は行いません。  
失敗の戻り値は最初の生成失敗の分類を保持します。

起動数ゼロの場合も、受信者用準備資源を回収します。  
stop は稼働フラグだけを理由に準備資源の回収や生成済みハンドルの join を省略しない構造にします。  
接続成立、再接続、先読みパケット引き渡し、通常時のロック取得順、通常終了の通知順序は維持します。

## 変更対象とテストの配置

以下のパスは `app/porter/` からの相対パスです。

- `prod/libsrc/porter/api/api_context_cleanup.c` と `.h` を追加し、`potr_service_open.c` と `potr_service_close.c` から共通解放を呼びます。
- `prod/libsrc/porter/thread/potr_connect_thread.c`、`potr_health_thread.c`、`potr_send_thread.c`、`potr_recv_thread.c` の生成・終了待ち・ハンドル初期化を対象範囲で整えます。
- `prod/libsrc/porter/infra/potr_send_queue.c`、`prod/libsrc/porter/potr_peer_table.c`、`prod/libsrc/porter/potr_path_event.c` の該当初期化と破棄を整えます。
- `prod/include_internal/porter/potr_path_event.h` と関連する既存内部ヘッダーに、初期化の結果、所有権と停止・解放の前提を記載します。`potr_context.h` は既存メンバーの所有権説明に必要な範囲を対象とします。
- `test/src/libporter/` に `apiContextCleanupTest`、`potrServiceOpenTest`、`potrServiceCloseTest`、`potrConnectThreadTest`、`potrHealthThreadTest`、`potrSendThreadTest`、`potrRecvThreadTest`、`potrPeerTableTest` を追加し、既存の `potrSendQueueTest` と `potrPathEventTest` を拡張します。
- 対象ソース 1 本を複数の単体テスト ディレクトリの `TEST_SRCS` に重複指定しません。テスト本体、makepart.mk、makefw の標準 makefile と必要な依存 mock を同じ変更に含めます。
- 依存関数の差し替えは `test/include/mock_porter.h`、`test/libsrc/mock_porter/` と関連する override 宣言へ追加します。通常 C 関数向け mock の規則に従い、cplat の既存 mock を利用します。cplat や testfw 自体は変更しません。

各テストは、生成を N 回目で失敗させるだけでなく、その時点までに生成した対象と破棄した対象の一致、破棄回数、終了待ちと解放の前後関係を確認します。  
秘密情報の消去は、実際の領域を解放する直前の内容と消去範囲を照合します。  
mock によりスレッド関数が実行されないテストと、実ライブラリによる既存の通信テストを区別します。

## 局所検証と受入条件

Windows/MSVC の利用可能な作業環境で、porter の製品・mock をビルドし、追加・変更した各単体テスト ディレクトリで `make test` を実行します。  
既存の `potrConnectedThreadsTest` と `potrSendQueueTest`、`potrPathEventTest` も影響する範囲として確認します。  
`porterSendRecvTest` では終了時の最終 DATA 配信、N:1 終了、暗号化 TCP 双方向通信と、`tcpMultipathTest` の複数パス・再接続・順序保証ケースを `GTEST_FILTER` で選択します。  
具体的なフィルターと実行件数を結果に残します。  
ワークスペース全体、複数 app にまたがる全体テストは実行しません。

ビルド後は対象範囲で内容がある `.warn` を確認し、変更起因の失敗・警告を修正して影響範囲を再検証します。  
既存ソースは変更箇所の clang-format、新規ソースは clang-format、内部ヘッダーの契約変更は porter の `make doxy` で確認します。  
Markdown は変更ファイルごとに `text_style_jp.py --dry-run` の提案を確認し、`--in-place` を実行します。  
機能仕様の追加・変更は予定しません。実装中に機能や利用者の前提の変更が必要と判明した場合は追加確認します。

受入条件は以下のとおりです。

1. 開始失敗と TCP・UDP 通常終了が同じコンテキスト資源解放処理を使用し、資源の所有者と停止条件を文書と宣言側で説明できること。
2. 対象の初期化失敗点で、未生成資源を破棄せず、生成済み資源を一度だけ回収し、起動済みスレッドの終了待ち完了より前に共有資源を解放しないこと。
3. 開始失敗と通常終了の両方で指定の秘密情報が解放前に消去され、N:1 のコンテキスト資源もピア資源と区別して回収されること。
4. 利用可能な環境の局所テスト、関連通信ケース、文書と生成確認が成功し、変更起因の失敗・警告が残らないこと。Linux/GCC が未検証の場合は未確認と明記すること。

両 OS の CI 成功は必須条件にしません。  
環境不足や未実行を成功として記録せず、検証できた範囲と受入判断に残る制約を提示します。  
ステージング、コミット、アンステージ、スタッシュ、push はこの仕様の承認に含めません。
