## 技術的な推奨案と検証計画

以下は採用前の案です。  
ユーザー回答で決定した内容だけを最終仕様へ移します。

### 公開ハンドルの検証と使用中参照の取得を一体化します

解放済み構造体のフラグや参照数を読み取る方法では、その読み取り自体で解放後参照が発生します。  
公開ハンドルの識別情報を、解放対象の通信コンテキストより長く有効な場所で管理する案を推奨します。  
受付時は識別と状態確認と使用中参照の取得を同じ保護区間で行い、その後に内部コンテキストを参照します。  
参照数が 0 になったことだけを確認して解放する方式では、確認後に新しい参照が入る競合を防げないため、受付停止と組み合わせます。

状態は OPEN → CLOSING → CLOSED を基本候補とし、終了失敗時には通常操作を再開させない状態を設けます。  
API 全体を大きな mutex で囲む方式は並行送信と別ハンドルの処理を直列化するため避ける案です。  
共有のハンドル表を使う場合も、ロックは検索・参照取得・状態変更に限定し、送信待ち、コールバック、join の間は保持しません。  
アドレス再利用で古いハンドルが新しい接続を指す ABA 問題の扱いは [Q-001](#q-001-ハンドルの識別方式) で決定します。

### close は受付停止と終了処理を分離します

CLOSING への遷移を、close と他 API の受付順を決める境界とする案です。  
先に受け付けた API の寿命を守り、後からの API は内部コンテキストに触れずに拒否します。  
close は、実行中 API とコールバックの完了、内部スレッドの停止を確認してから資源を破棄します。  
close 成功復帰後にコールバックが実行されないことを受入条件の候補にします。

送信を取消可能にする場合は、キューの空き待ちだけでなく push_mutex 待ち、チケット待ち、drain、TCP の接続状態変化も確認対象です。  
待機条件と通知を同じ同期規則で更新し、待機者が条件を再確認する方式とします。  
途中まで登録した断片の扱いと、成功を返すタイミングも決定します。  
close が先に必要なスレッドを停止し、API がそのスレッドの進行を待つ循環を防ぐ必要があります。

### コールバックを内部の状態保護ロックの外で実行します

N:1 の送信拒否判定を削除するだけでは、peers_mutex の再取得で停止します。  
再帰 mutex に変更しても、キューの空きや送信完了を待つ間に送信スレッドが peers_mutex を必要とする循環は残ります。  
データと通知内容を確定し、内部状態を保護するロックを外してから通知する案を推奨します。

通知後にピアポインターを再使用する箇所は、参照を保持するか、識別子で再検索する必要があります。  
受信データ、展開バッファー、PATH 状態配列は、コールバック復帰まで有効に保ちます。  
既存のハンドル単位の通知直列性とイベント順序を維持する案とし、状態変更と通知の間に切断が入る場合も順序を定義します。  
peers_mutex → callback_mutex の取得経路を一部だけ残すと、callback_mutex を保持したコールバックの send との循環が起こり得るため、受信・ヘルス チェック・disconnect をまとめて調査します。

専用の通知スレッドを設ける案は、受信処理を進めたままコールバック内の送信待ちを行える一方、スレッド、有限通知キュー、データ コピーが増えます。  
既存スレッドから同期通知する案は追加コストを抑えられますが、受信進行が必要な条件でのブロッキング送信を検証する必要があります。  
通知キューを設ける場合は、容量、満杯時の扱い、close 中の残通知の扱いを追加 Q で確認します。

### 安全性を決定的な競合試験で確認します

時間待ちだけに依存せず、バリアなどで受付・参照取得・受付停止・解放の順序を固定する試験を計画します。

- send、disconnect、別の close と close の競合。受付境界の前後それぞれの戻り値と資源解放回数
- close 後の古いハンドルを使用した send・disconnect・close。open と close の繰り返し後も新しいハンドルを操作しないこと
- キュー満杯、分割メッセージ、圧縮、送信チケット待機中の close。取消を採用した場合の待機解除と部分登録の処理
- N:1 の DATA コールバック内で、受信元への返信、別ピアへの送信、全ピア送信。対応範囲に応じてブロッキングと非ブロッキングを確認
- UDP、TCP、RAW の適用される経路で、コールバック内送信と外部スレッドの close の競合
- DATA、PATH、接続・切断イベントの順序、コールバックの非並行実行、データ寿命、ピア切断との競合
- close のスレッド停止失敗、open 途中失敗、参照取得失敗時に、資源の二重破棄や利用可能状態への誤復帰がないこと

局所テストを基本とし、全体テストはコストを説明して別途確認します。  
Linux/GCC と Windows/MSVC の両方を計画対象にし、実施環境が不足する場合は結果と未確認事項を分けます。  
競合検査ツールを利用できる場合の追加検査も候補とし、通常試験の代用にはしません。

### 通常送信の追加コストと別ハンドルへの影響を測定します

改修前後を同じマシン、ビルド条件、通信条件で比較する案です。  
小メッセージと分割を伴う大メッセージ、圧縮の有無、単一スレッドと並行送信、単一ハンドルと複数ハンドルを分けます。  
N:1 のコールバック返信は改修後に新たに対応するため、既存の外部スレッドからの返信も比較対象にします。

測定項目はスループット、API 遅延の中央値と p95/p99、CPU 使用量、送信ごとのメモリ確保回数、ピーク メモリ、open/close 反復時の保持メモリ、close 所要時間です。  
コールバック遅延と内部ロックの待機時間も、方式比較に必要な範囲で確認します。  
測定回数と負荷条件をそろえ、ばらつきを含めて報告します。

通常送信への毎回のメモリ確保、全ハンドルの線形探索、全ハンドル共通の長時間ロックを避ける案です。  
通知データのコピーは寿命保証に必要な範囲に限定し、再利用領域やピア参照保持と比較します。  
具体的な劣化率の上限はユーザーから示されていないため、[Q-009](#q-009-性能の受入基準) で確認します。

- クライアントが CONNECTED を公開してから、NORMAL を載せた PING を書き込むまでの間に DATA が先行し、サーバーが CONNECTED 前の DATA として破棄する競合
- TCP の送信で、送信バッファーに空きがない path のパケットを捨て、`cplat_socket_send_all()` の失敗も無視したまま送信キューを成功として完了する欠陥

- TCP の送信は、どの path にも書き込めないままパケットを捨てません。書き込めなかった path は停止して再接続させ、通番を消費せず、ブロッキング送信へ `POTR_ERR_DISCONNECTED` を返します。
- TCP の受信は、ウィンドウより先の通番でストリームを切断し、受信済みの重複だけを破棄します。

DATA 前の通知だけを一時的に無効にした版では 300 回中 7 回失敗し、修正版では 300 回すべて成功したため、直接原因は 1 件目の競合と確定しました。
