17 条件のうち、処理件数が上がった条件は両 OS とも 13 条件です。Linux の 5000[B] の 3 条件は、5 回すべてで低下しました。低下の原因は調べていません。

### BL-001 の実装と検証の状態

実装は cplat と porter のブランチ `fix/bl001-tcp-nodelay` にあり、`main` には入っていません。cplat に `cplat_socket_set_nodelay` を追加し、porter は接続の開始前と受け入れの直後に呼びます。設定に失敗した場合は警告を記録して続行します。

確認済みの検証は、両 OS での新規テスト 3 件の `make test` と、対象 4 ディレクトリのテスト バイナリの直接実行です。次の検証は終わっていません。

- Linux の全件 `make test` は、途中で停止したため未完了です。
- Doxygen の生成は、後処理が 60 分を超えて停止したため未完了です。
- CI は実行していません。

### TCP の送信の作り

`tcp_write_path()` は、パケット 1 個ごとに `cplat_socket_send_all()` を 1 回呼びます。パケットの最大ペイロード長の既定は 1400[B] (`POTR_DEFAULT_MAX_PAYLOAD`)、まとめ送信の待ち時間の既定は 0[ms] (`POTR_DEFAULT_PACK_WAIT_MS`) です。

### BL-002 の調査の状態

旧案件は、関数ごとの CPU 時間を測る計装を試しました。計装そのものが処理件数を最大 91.5% 下げたため、結果は原因の特定に使えません。Linux の `perf` は実行ファイルがなく、`perf_event_open` も権限エラーでした。Windows の WPR は権限の条件で起動していません。BL-002 の原因は特定できておらず、製品コードは変更していません。

コードを読んで挙げた原因の候補は、圧縮送信ごとの約 65[KiB] の確保と全量の消去、送信 1 回あたり 3 回のハンドル ロック、送信キューの毎回の起床通知、通知キューの空きノードの線形探索、N:1 でのピア ロックの保持区間の 5 点です。どれも実測での裏付けはありません。

A で確定しました。送信キューに溜まった分をメッセージの境界をまたいでまとめて送る変更を、製品コードとして BL-001 の対策に含めます。Linux の 5000[B]・ブロッキング・1 スレッドに残る約 17% の低下は、既知の特性として残課題一覧に記録します。[Q-002](#q-002-旧案件の-bl-001-の方針の引き継ぎ) の 1 点目 (`TCP_NODELAY` を常に有効にする) は、この回答により見直す理由がなくなり、そのまま維持します。変更の範囲が送信スレッドへ広がるため、最終仕様を版 2 に改版し、承認を受け直します。試行版の課題 (断片の途中の待ち、複数経路での送出通番の順序、単体テストの不足、Windows の通知遅延の p95 の増加) の扱いは、最終仕様に記載しました。

### 実装で確かめる事項の結果

- 複数経路での送出通番の順序は、問題ありません。送出通番は重複の検出だけに使い、検出の範囲は 256 です。まとめ送りで生じるずれは最大 16 パケット × 経路数の上限 8 = 128 未満で、この関係をコンパイル時の検査 (`_Static_assert`) で固定しました。単体テスト (`two_paths_receive_same_packets`) でも確認しました。
- 断片の途中で次の断片を待つ処理 (上限 5[ms]) は外しました。Windows の 5000[B] の 4 条件で、待つ版と待たない版の処理件数に差はなく、Linux の final も batch2 と同等でした。
- Windows の通知遅延の上位の増加は、解消できていません。5000[B]・ブロッキング・1 スレッドで、p50 は 107.0[µs] から 63.9[µs] へ短くなりましたが、p95 は 140.0[µs] から 694.9[µs] へ、p99 は 241.3[µs] から 1,038.6[µs] へ増えました。5000[B]・ブロッキング・4 スレッドでは、p50 が 446.7[µs] から 1,416.0[µs] へ増えました (処理件数は 4.9 倍)。

Windows の通知遅延について、試したことは次のとおりです。

- 連結したバッファーを 1 パケットずつ送る版 (`final-split`) では増加が消えましたが、処理件数が約 45% 下がりました。
- 送信の呼び出しを 4096[B] 以下に分ける版 (`final-chunk4k`) では、増加は消えませんでした。
- Linux では同じ増加は出ていません (上の Linux の通知遅延を参照)。

原因は特定できていません。Windows のループバックの TCP に固有の動作という見方は推測です。最終仕様の定めに従い、`main` へ取り込む前に、数値を示してユーザーに確認します。

ユーザーの指示 (2026-11-17、チャット): 2 倍程度であれば、環境起因のばらつきとして懸案とはせず、経緯の記録だけを行う。

この指示の条件 (2 倍程度) に対して、測定値の増加は、1 スレッドの p95 が約 5.0 倍、p99 が約 4.3 倍、4 スレッドの p50 が約 3.2 倍です。2.2 倍は処理件数の増加の値です。条件に当てはまるかどうかを、ユーザーに確認しました。

ユーザーの判断 (2026-11-17、チャット): 絶対値は最大でも約 1.5[ms] で、秒の単位の遅延は起きていない。問題なしとする。

この判断により、Windows の通知遅延の上位の増加は懸案とせず、残課題一覧にも記載しません。経緯はこの節の記録だけを残します。

### CI の 1 回目の失敗と修正 (2026-11-17)

プル リクエスト [#59](https://github.com/Hondarer/c-modernization-kit/pull/59) の CI の 1 回目 (run `44050752536`) で、Windows と docs のジョブは成功し、Linux の 3 ジョブ (ol8、ol9、ol10) が同じテスト 1 件で失敗しました。

- 失敗したテスト: `porterSendRecvTest` の `receive_buffers/tcp_allocation_failure_test.releases_buffers_and_reopens_endpoints/recv_compress_buf` (Linux 専用)。対象サイズの確保回数の期待値 2 に対して、実際は 3 回でした。
- 原因: まとめ送りの平文バッファー (16 × 最大ペイロード長 = 16 × 512 = 8192[B]) が、このテストの最大メッセージ長 (8192[B]) と同じサイズになり、数える対象に入りました。製品コードの不具合ではなく、テストの期待値のずれです。Windows ではこのテストを実行しないため、Windows の全件テストでは検出できませんでした。
- 修正 (porter `e102d94`): 期待値を直し、サイズが同じになる前提を `static_assert` で固定しました。まとめ送り用の 2 つのバッファーの確保が失敗する場合のケースを 2 件加えました。

Windows では、`e102d94` の変更が及ぶ 3 ディレクトリ (`test/src/cmd/porterTestOutputTest`、`test/src/cmd/windows/tcpServerWindowsTest`、`test/src/integration/porterSendRecvTest`) を `MAKEFW_TEST_FORCE=1` で実行し直しました。それぞれ 7 件、1 件、36 件で、すべて成功しました。ログにコンパイラの警告の行はありません。
