17 条件のうち、処理件数が上がった条件は両 OS とも 13 条件です。Linux の 5000[B] の 3 条件は、5 回すべてで低下しました。低下の原因は調べていません。

### BL-001 の実装と検証の状態

実装は cplat と porter のブランチ `fix/bl001-tcp-nodelay` にあり、`main` には入っていません。cplat に `cplat_socket_set_nodelay` を追加し、porter は接続の開始前と受け入れの直後に呼びます。設定に失敗した場合は警告を記録して続行します。

確認済みの検証は、両 OS での新規テスト 3 件の `make test` と、対象 4 ディレクトリのテスト バイナリの直接実行です。次の検証は終わっていません。

- Linux の全件 `make test` は、途中で停止したため未完了です。
- Doxygen の生成は、後処理が 60 分を超えて停止したため未完了です。
- CI は実行していません。

### TCP の送信の作り

`tcp_write_path()` は、パケット 1 個ごとに `cplat_socket_send_all()` を 1 回呼びます。パケットの最大ペイロード長の既定は 1400[B] (`POTR_DEFAULT_MAX_PAYLOAD`)、まとめ送信の待ち時間の既定は 0[ms] (`POTR_DEFAULT_PACK_WAIT_MS`) です。

### BL-002 の調査の状態

旧案件は、関数ごとの CPU 時間を測る計装を試しました。計装そのものが処理件数を最大 91.5% 下げたため、結果は原因の特定に使えません。Linux の `perf` は実行ファイルがなく、`perf_event_open` も権限エラーでした。Windows の WPR は権限の条件で起動していません。BL-002 の原因は特定できておらず、製品コードは変更していません。

コードを読んで挙げた原因の候補は、圧縮送信ごとの約 65[KiB] の確保と全量の消去、送信 1 回あたり 3 回のハンドル ロック、送信キューの毎回の起床通知、通知キューの空きノードの線形探索、N:1 でのピア ロックの保持区間の 5 点です。どれも実測での裏付けはありません。
