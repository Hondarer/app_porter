# porter ハンドル寿命管理の追加性能評価 最終仕様

ファイル名: `261115-porter-handle-lifecycle-perf-design.md`

## 目的と範囲

porter のハンドル寿命管理の改修 (専用通知スレッド、通知キュー、ハンドル制御情報の保持) について、改修時に未確認だった性能を測定し、受入判断の材料をそろえます。  
対象は過去 backlog `../past/261107-porter-handle-lifecycle-backlog.md` の BL-001 に挙げた次の 5 項目です。

- N:1 のコールバック内返信と外部スレッド返信の比較
- 低速コールバック時の通知遅延、ピーク メモリ、通知消費後の保持メモリ
- open/close 反復時の通信資源の回収、制御オブジェクトの保持量、終了所要時間
- API 遅延の中央値・p95・p99、通知遅延の中央値・p95・p99、ウォーム アップ条件と測定のばらつき
- TCP 予備測定で記録された終了時エラーの再確認と、比較測定への適用可否

性能の合否を劣化率で自動判定しません。  
測定結果、追加コストの原因、測定の限界を提示し、ユーザーが受入を判断します。

zlib と OpenSSL は外部由来の配布物のため、両版ともワークスペースのビルド済みライブラリ (現行の固定版) を使います。外部ライブラリの版の差を、porter の改修前後の比較に混ぜないためです。改修前の親 `f2d8dfde` が固定していた zlib は `787210bb` ですが、測定には使いません。

改修前版の porter、cplat、cjson は、各セッションが自分のリポジトリから、サブモジュールごとに `git archive` で一時ディレクトリへ取り出します。リポジトリへは書き込みません。  
現行版は、作業ツリーのソースをそのまま使います。

### ビルド方法

makefw は使わず、両版とも測定プログラムのビルド手順で porter、cplat、cjson の製品ソース (`prod/libsrc/` 配下) を直接コンパイルし、測定プログラムと静的に結合します。版の間でビルド方法とフラグをそろえるためです。OpenSSL は、現行版だけがワークスペースのビルド済みライブラリと結合します。

| 対象 | Windows/MSVC | Linux/GCC |
| --- | --- | --- |
| 製品の C ソース | `/std:c17 /O2 /MD /DNDEBUG` | makefw の設定と同じ C17 の指定 (`-std=c17` または `-std=gnu17`)、`-O2 -DNDEBUG -fno-omit-frame-pointer` |
| 測定プログラム (C++) | `/std:c++17 /O2 /MD /DNDEBUG /EHsc` | `-std=c++17 -O2 -DNDEBUG -fno-omit-frame-pointer` |

Table: OS ごとのコンパイル フラグ

製品の C ソースに必要なマクロ定義とインクルード パスは、現行の makefw の設定 (`makepart.mk` など) から読み取って測定プログラムのビルド手順へ写し、検証記録に実際の指定を残します。

> [!NOTE]
> makefw の既定 (`CONFIG=RelWithDebInfo`) で作った現行版のライブラリをそのまま使わないのは、改修前版を makefw でビルドするにはワークスペース一式 (サブモジュールを含む) の取り出しが必要になり、版の間でビルド条件をそろえにくいためです。

## 測定プログラム

測定プログラムはリポジトリに置きません。結果と測定条件の文章だけを残します。

- Windows セッションが、自分のセッション用一時ディレクトリ配下の `porter-perf/` に作成します。WSL セッションは `/mnt/c/...` から読み取り、WSL セッションの一時ディレクトリへ複製してビルドします。実際のパスは作業開始時にセッション間で連絡します。
- C++17 のうち GCC 8.5 と MSVC の共通部分だけを使います。`<charconv>` の浮動小数点版と `std::filesystem` は使いません。
- 公開 API (`potr_service_open`、`potr_service_send`、`potr_peer_disconnect`、`potr_service_close`、受信コールバック) だけを使います。改修前版と現行版で API の差がある場合は、版ごとの条件付きコンパイルで吸収します。
- 結果は 1 行 1 計測の CSV で出力します。WSL セッションは結果の CSV を共有ディレクトリの `porter-perf/results/linux/` に置きます。一時ディレクトリは消える場合があるため、Windows セッションは測定完了の連絡を受けるたびに、結果を本案件の CSV へ取り込みます。

## 共通の測定規則

- 各条件を 5 回実行します。各実行の先頭で、測定対象外のウォーム アップとして 1000 件 (open/close 反復では 10 サイクル) を処理し、結果から除きます。
- 1 回の実行の中で中央値・p95・p99 を求め、5 回分の値の最小・中央値・最大を記録します。
- 通信はループバック (127.0.0.1) を使います。ネットワークを介した実運用の性能を保証する値ではありません。
- Windows と Linux は同じ物理マシンを共有するため、測定の実行は交互にします。片方が測定している間、もう片方はビルドや重い処理を行わずに待機します。切り替えは、セッション間で「測定開始 (OS、条件群)」と「測定完了 (OS、条件群、結果の置き場所)」を連絡して行います。
- 時刻は単調増加時計 (Windows は `QueryPerformanceCounter`、Linux は `clock_gettime(CLOCK_MONOTONIC)`) で取得します。通知遅延は、送信側の API 呼び出し直前の時刻を本文に書き込み、受信コールバックの入口で差を取ります。送受信は同じプロセス内で行います。

### メモリ量の指標

| 指標 | Windows | Linux |
| --- | --- | --- |
| 現在の常駐量 | `GetProcessMemoryInfo` の `WorkingSetSize` | `/proc/self/status` の `VmRSS` |
| ピークの常駐量 | `PeakWorkingSetSize` | `VmHWM` |
| 確保済みの私有量 | `PrivateUsage` (`PROCESS_MEMORY_COUNTERS_EX`) | `RssAnon` |
| 通信資源の数 | `GetProcessHandleCount` | `/proc/self/fd` の項目数 |
| スレッド数 | Toolhelp32 のスレッド列挙 | `/proc/self/status` の `Threads` |

Table: OS ごとのメモリと資源の計測手段

OS 間で比べる値は、各実行の開始時点 (ウォーム アップ後) からの増加量だけとします。絶対値は OS の実装差を含むため、OS 間では比べません。

## 測定条件

| ID | 項目 | 通信種別 | 負荷 | 測る版 |
| --- | --- | --- | --- | --- |
| P1 | 遅延分布 | UDP ユニキャスト | 64 / 5000 バイト、通常・圧縮・ブロッキング、1 スレッド 1 ハンドルと 4 スレッド 1 ハンドル。各スレッド 10000 件、同時未完了 16 件まで | 改修前版、現行版 |
| P2 | N:1 返信 | UDP N:1 双方向 | クライアント 4 本が 64 / 5000 バイトの要求を各 5000 件送り、サーバーが返信する。返信は「コールバック内で送信」と「キュー経由で外部スレッドから送信」の 2 方式 | コールバック内: 現行版のみ。外部スレッド: 改修前版、現行版 |
| P3 | 低速コールバック | UDP ユニキャスト | 受信コールバックが 1 件ごとに 1[ms] 待機する。送信側は 5000 バイトを 10000 件、送信間隔なしで送る | 改修前版、現行版 |
| P4 | open/close 反復 | UDP ユニキャスト、TCP | open、接続、1 件の送受信、close を 1000 サイクル繰り返す | 改修前版、現行版 |
| P5 | TCP 遅延分布 | TCP | P1 と同じ負荷 | 改修前版、現行版 (TCP 終了時エラーの扱いの決定後) |

Table: 負荷条件と測定対象の版

| ID | 記録する値 |
| --- | --- |
| P1、P5 | 処理件数/秒、API 呼び出し時間の中央値・p95・p99、通知遅延の中央値・p95・p99、プロセス CPU 時間 |
| P2 | 往復時間 (要求送信から返信受信まで) の中央値・p95・p99、処理件数/秒、受信欠落数 |
| P3 | 通知遅延の中央値・p95・p99・最大、ピーク常駐量と私有量の増加、全通知の消費後 1[s] 時点の保持量の増加、受信欠落数 |
| P4 | close の所要時間の中央値・p95・p99、100 サイクルごとの常駐量・私有量・通信資源の数・スレッド数。1 サイクルあたりの保持量の増加 (最小二乗法の傾き) |

Table: 測定条件ごとの記録値

> [!NOTE]
> 改修前版はコールバックを受信スレッド内で直接実行し、通知キューを持ちません。P3 では、改修前版は受信が遅れてソケット側で破棄が起き、現行版は通知キューにメモリを保持する、という性質の違いが表れる見込みです。受信欠落数とメモリの両方を記録し、方式の違いとして報告します。
>
> 公開ハンドルの制御オブジェクトは再利用しないため、P4 の 1 サイクルあたりの保持量の増加が制御オブジェクトの保持量の目安になります。内部の構造体の大きさを直接読むことはしません。

## TCP 終了時エラーの切り分け

1. P5 の負荷を Windows と Linux の両方で、改修前版と現行版について実行し、終了時エラーの再現有無と内容 (戻り値、ログ、発生した段階) を記録します。
2. 再現した場合は、測定プログラムの終了手順 (送信完了待ちと close の順序、受信側の切断処理) と porter の終了処理のどちらに原因があるかを切り分けます。
3. 原因が測定プログラムにある場合は、プログラムを直して P5 を測ります。
4. 原因が porter の製品不具合の場合は、本案件で修正し、再現する単体テストまたは結合テストを追加します。両 OS で影響範囲の局所テストを実行し、対象範囲の `.warn` に変更起因の警告がないことを確認してから、P5 を測ります。振る舞いの変更が利用側から見える場合は、`AGENTS.md` の表に従って機能仕様の見直し要否を確認します。
5. 再現しない場合は、再現しなかった条件と回数を記録し、P5 を測ります。

測定は P1、P2、P3、P4、P5 の順に、条件群ごとに Windows、Linux の順で交互に実行します。

本案件の範囲に限り、各セッションはユーザーの個別指示を待たずに、コミット、push、相手側の取り込み (pull) を行います。対象は次の変更に限ります。

- 本案件の検証記録、CSV、検討用 Markdown、最終仕様、残課題一覧
- 過去 backlog BL-001 と元案件の検証記録への追記
- TCP 終了時エラーの修正と、そのテスト
- `app/porter` の変更に伴う親リポジトリのサブモジュール参照の更新

上記以外の変更 (WSL の clone にある別案件の未追跡ファイルなど) はステージングしません。コミット メッセージはリポジトリの既存の形式に合わせます。

## 実行の権限と中断時の扱い

- 各セッションのエージェントが、担当 OS のビルドと測定を自走します。
- Windows Defender ファイアウォールの許可はユーザーが行います。許可の遅れで測定が失敗した場合は、その結果を採用せず、ユーザーと対話して許可を得てから再実行します。WSL 内のループバック通信はこのファイアウォールを通らないため、Linux 側の測定には許可は不要です。
- 測定中に想定外の失敗 (クラッシュ、受信の全欠落など) が起きた場合は、その条件を中断し、事象を記録してから原因を確認します。

## 正本とコード コメントへの反映計画

測定値そのものは環境に依存するため、正本 (`docs/` 配下) には反映しません。  
TCP 終了時エラーを修正した場合は、修正の理由と前提をソースのコメントに残し、OS 固有の挙動が根拠であれば `see: <URL>` を併記します。  
測定から恒久的に有用な性質 (例: 低速コールバック時に通知キューのメモリが受信量に比例して増えること) が確認された場合は、反映先の正本と記載案を第 3 ゲートで提示し、ユーザーの判断を受けてから反映します。

## 受入条件
