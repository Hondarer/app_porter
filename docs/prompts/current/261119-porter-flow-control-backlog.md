## BL-001 フロー制御の Windows と WSL の相互接続による確認が未実施

- **現状の事象**: フロー制御の受入は、単体テスト、Linux 上の `porter-test` による結合の確認、CI の成功で判定します。Windows と Linux の間でフロー制御パケットを交換する確認は行いません。
- **摘出契機**: 前提検討時に見送り (受入の検証範囲の質問で、相互接続による確認が選択されなかった)。

## BL-002 フロー制御が無効の構成での性能を変更前後で比較していない

- **現状の事象**: フロー制御の導入により、無効の構成でも通知の登録と取り出しに占有量の計算が加わる可能性があります。変更前後の処理件数と遅延の比較は行いません。
- **摘出契機**: 前提検討時に見送り (受入の検証範囲の質問で、性能の比較が選択されなかった)。

## BL-003 抑制の要求の再送周期と有効期限の既定値に実測の根拠がない

- **現状の事象**: 既定値の再送周期 200 ms と有効期限 1,000 ms は、検討時の提案値であり、経路の遅延や喪失率の実測に基づいていません。構成で変更できます。
- **摘出契機**: 前提検討時に判明 (値の提案の時点で実測の根拠がないことを明示し、構成で変更できる形で採用された)。

## BL-004 抑制の解除の直後に送信キューの内容がまとめて送出され、受信側の容量や下位の通信の受信バッファーを超える

- **現状の事象**: 抑制中に送信キューへ溜まった DATA (最大で `send_queue_depth` × `max_payload`。既定で約 1.4 MB) は、解除の直後に間隔なしで送出されます。受信側の容量の余裕がこの量より小さい場合、TCP では占有量が容量を超えて切断になります。UDP では、受信側のソケット受信バッファー (Linux の既定は約 208 KB) があふれ、欠落から再送不能の切断になります。`send_queue_depth` を 64 にした構成では、どちらも起きませんでした。
- **摘出契機**: 実装作業中に、一時的な確認プログラムでの動作確認で発見しました (容量 2 MB、`send_queue_depth` 1,024、1,000 バイトのメッセージ、受信コールバックの遅延 1 ms)。
- **今回の扱い**: 構成で調整できるため、`docs/config.md` の「容量の決め方」に指針として記載しました。既定値と動作は変えていません。送出の速さを制限する仕組み (解除の直後の送出の間隔の制御など) は、機能仕様が適用範囲外とする帯域の制御に当たるため、この案件では扱いません。
