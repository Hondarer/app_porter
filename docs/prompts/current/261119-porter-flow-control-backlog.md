## BL-001 Linux (WSL) と Windows をまたぐ確認、および Windows での受入条件 8・10 と性能測定が未実施

### 概要と問題点

- **現状の事象**: フロー制御の確認は、単体テスト、Linux (WSL) 上の `porter-test` と `porter-bench` による結合の確認、CI (Linux と Windows のビルドとテスト) で行いました。Windows と Linux の間でフロー制御パケットを交換する確認 (最終仕様の版 7 の受入条件 7) は行っていません。次の事項が未確認です。
    - `unicast`、`unicast_bidir`、`tcp` を、送信側と受信側の OS を入れ替えた両方向で確認すること。`multicast` は、WSL と Windows の間で届く場合だけ確認し、届かない場合は各 OS の中で確認すること。
    - Windows 上での受入条件 8 (待ち合わせを指定しない連続送信で、欠落による切断がなく全件が届くこと。`tcp` を除く) と、受入条件 10 (`multicast`)。Windows が受信側の場合の送出上限の更新の頻度の記録。
    - Windows 上での OS の受信バッファーに基づく送出上限の有効と無効の `porter-bench` による比較、およびフロー制御が無効の構成での変更前後の比較。Linux だけで測定しており、Windows の値は未測定です。
- **本来あるべき姿**: 受入条件 7 の確認が行われ、OS が異なる送信側と受信側の間でも、抑制と解除、送出上限の通知が働き、欠落と切断がないことが確認されていること。Windows の OS の受信バッファーの大きさ (`cplat_socket_get_receive_buffer_size()` の値) の取り扱いと、そこから計算する送出上限の幅が、Windows でも妥当であることが確認されていること。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (Q-024)。その後、Q-038 で受入の条件に加えましたが、Windows 側の操作を行えるセッションがなく、実行できませんでした。
- **今回の見送り理由**: ユーザーが 2026-11-21 に、この案件では行わずに残課題とすると指示しました (LADR-014、LADR-018)。
- **継続作業での経緯と対処**: 2026-11-21、対策する継続案件を開始しました (検討 ID: 261121-porter-flow-control-refine、全体管理文書: `261121-porter-flow-control-refine-overview.md`)。状態は「検討中」で、対策の方針をユーザーに確認しています。

### 影響範囲とリスク

- **影響対象**: Windows の受信側、および Windows と Linux の間の通信。OS の受信バッファーの大きさの取得 (`app/cplat` の `cplat_socket_get_receive_buffer_size()`) と、それに基づく送出上限。
- **放置した場合のリスク**: Windows で、受信バッファーの幅が過大または過小に計算されると、欠落と切断、または処理件数の低下が、Linux の確認では見つからないまま残ります。CI は、ビルドと既存の単体テストの成功を確認するだけで、実機での通信を確認しません。

### 推奨される対応策

- **恒久対応案**: Windows の作業ツリーを持つセッションで、`bin/interop_matrix.py` の `--direction` と `--scenario flow-control` を使い、受入条件 7 の組み合わせを実行します。あわせて、Windows 上で受入条件 8 と 10 の連続送信 (1,000 byte × 6,000 件) と、`porter-bench` の有効と無効の比較を実行し、結果を記録します。受入条件 10 は BL-006 が解消するまで、既定の構成では満たしません。
- **参考情報**: 最終仕様 (`261119-porter-flow-control-design.md`) の「受入条件」の 7 から 10、全体管理文書の作業 WBS 4.11a と「反映と検証の記録」、LADR-014、LADR-018、[Q-024](261119-porter-flow-control-discussion.md#q-024-受入の検証範囲)、[Q-038](261119-porter-flow-control-discussion.md#q-038-os-をまたぐ確認の範囲)。

## BL-006 multicast と broadcast で、既定のしきい値 (2) では、受信者が同じ速さでも連続送信で欠落と切断が起きる

### 概要と問題点

- **現状の事象**: `multicast` と `broadcast` の送信者は、送出上限に達した受信者の数が、外れ値を無視するしきい値 (`flow_control_receiver_count`、既定 2) 以上になるまで止まりません。しきい値が 2 以上の場合、1 台の受信者が一時的に遅れた (OS のスケジューリングによる受信スレッドの停止など) だけでは、送信者が止まらず、その受信者の OS の受信バッファーがあふれます。受信者が同じ速さでも、連続送信の間、最も遅い受信者が入れ替わりながら欠落し、保持範囲 (`window_size`、既定 16 パケット) を超えると切断になります。
- **再現条件** (2026-11-21、Linux の同じホスト、`multicast`、受信者 3 つ、容量の指定なし、待ち合わせを指定しない `burst 6000 1000`、受信報告が届いた後に送信を開始):

    | `flow_control_receiver_count` | 実行回数 | 結果 |
    | --- | --- | --- |
    | 2 (既定) | 3 | 3 回とも、1 台から 3 台の受信者で欠落と切断が起きた |
    | 1 | 3 | 3 回とも、全受信者が 6,000 件を順序どおりに受信し、切断はなかった |

    しきい値が 2 の実行でも、監視対象の選択と、監視対象の一覧の通知は、仕様どおりに働いていました (3 台とも監視対象に選ばれ、送出上限を送出していました)。
- **本来あるべき姿**: 既定の構成の `multicast` で、受信者が同じ速さであれば、連続送信でも欠落と切断が起きず、全受信者に全件が渡ること (最終仕様の受入条件 10)。

### 経緯と見送り理由

- **摘出契機**: 最終仕様の版 7 の実装後の、`porter-test` による結合の確認 (受入条件 10)。
- **今回の見送り理由**: ユーザーが Q-060 で、基本のアルゴリズムに致命的な問題はなく、判定、バッファーの大きさ、条件の設定、追加の処理で対応できるため、残課題として記録して作業を進めると判断しました。受入条件 10 は、既定の構成では満たせないまま、第 3 ゲートで満たしていない条件として示しました。
- **継続作業での経緯と対処**: 2026-11-21、対策する継続案件を開始しました (検討 ID: 261121-porter-flow-control-refine、全体管理文書: `261121-porter-flow-control-refine-overview.md`)。状態は「検討中」で、対策の方針をユーザーに確認しています。

### 影響範囲とリスク

- **影響対象**: `multicast` と `broadcast` で、既定の構成のまま、待ち合わせを指定しない連続送信を行う利用側。受信報告を送らない構成 (実効 `health_interval_ms` が 0) の `multicast` と `broadcast` の受信者には、OS の受信バッファーに基づく送出上限を適用しないため (最終仕様の仕様)、同様に防げません。
- **放置した場合のリスク**: 連続送信で、欠落と、再送不能の切断と接続の繰り返しが起きます。フロー制御の導入前からある動作と同じ結果で、導入によって悪化はしていません。

### 推奨される対応策

- **恒久対応案** (未決定。Q-060 の選択肢 A、B と、ユーザーが示した方向):
    - 送出上限による停止は、しきい値を使わず、監視対象のどれか 1 台が上限に達した時点で止める。極端に遅い受信者への備えは、送出上限の有効期限 (上限で止まったまま `flow_control_request_lifetime_ms` の間進まない受信者の上限を破棄する。実装済み) に任せる。抑制の要求の判定は、従来どおりしきい値を使う。ただし、常に遅い受信者が 1 台いると、全体がその受信者の速さになります。
    - `flow_control_receiver_count` の既定値を 1 にする。
    - 受信バッファーの幅を小さくして、一時的な遅れを OS の受信バッファーの残りで受け止める (`flow_control_receive_buffer_percent` の既定値の見直し)。
    - 順位ではなく、遅れの大きさや続いた時間で、外れ値を判定する。
- **回避策**: 全受信者を守る必要がある構成では、`flow_control_receiver_count` を 1 に設定します (`flow_control_receiver_percent` は無効のまま)。制約と回避策は `docs/config.md` に記載済みです。
- **参考情報**: [Q-060](261119-porter-flow-control-discussion.md#q-060-multicast-と-broadcast-の既定の設定で起きる欠落への対処)、[Q-055](261119-porter-flow-control-discussion.md#q-055-監視対象の方式と既存の-1-対-n-の判定の関係)、LADR-018、全体管理文書の「反映と検証の記録」(版 6 と版 7 の結合の確認)、`docs/protocol.md` と `docs/config.md` の監視対象の節、`prod/libsrc/porter/protocol/receiver_report.c`。

## BL-007 N 対 1 サーバーで、OS の受信バッファーに基づく送出上限を有効にすると、処理件数が約 16% 下がる

### 概要と問題点

- **現状の事象**: `unicast_bidir_n1` のサーバーは、すべてのピアが 1 つのソケットを共有するため、受信バッファーの幅を接続中のピア数で割ります。ピアが 4 つの場合、幅はピアごとに 10 パケット (OS の受信バッファーが既定の Linux) になり、送出上限の更新が約 5 パケットにつき 1 個に増えます。この更新の送受信の分だけ、処理件数が下がります。
- **再現条件** (2026-11-21、Linux の同じホスト、`porter-bench` の既定の条件、有効 (`--receive-buffer-limit on`) と無効 (`off`) を交互に 3 回、各回 5 測定の中央値):

    | 条件 | 指標 | 有効 | 無効 | 差 |
    | --- | --- | --- | --- | --- |
    | p2 (N 対 1、クライアント 4 つ) | 処理件数 [件/秒] | 85,495 | 101,494 | −15.8% |
    | p2 (N 対 1、クライアント 4 つ) | 往復時間の中央値 [マイクロ秒] | 706 | 596 | +18.4% |
    | p1 (`unicast`、64 byte) | 処理件数 [件/秒] | 135,153 | 133,705 | +1.1% |
    | p1 (`unicast`、1,000 byte) | 処理件数 [件/秒] | 88,048 | 85,078 | +3.5% |
    | p1 (`unicast`、64 byte、待ち合わせを指定) | 処理件数 [件/秒] | 10,957 | 10,849 | +1.0% |
    | p1 (`unicast`、1,000 byte、待ち合わせを指定、4 スレッド) | 処理件数 [件/秒] | 9,907 | 9,968 | −0.6% |
    | p3 (`unicast`、受信コールバックを遅延) | 欠落の件数 | 0 | 521 | 欠落がなくなった |

    p2 の欠落は、有効と無効のどちらも 0 件でした。
- **本来あるべき姿**: 既定の構成の N 対 1 で、有効にしても、処理件数の低下が許容範囲 (最終仕様の受入条件 9 の目安は 5% 以内) に収まること。

### 経緯と見送り理由

- **摘出契機**: 最終仕様の版 7 の受入条件 9 (`porter-bench` による、有効と無効の比較)。
- **今回の見送り理由**: ユーザーが Q-061 で、版 7 のまま進め、残課題として記録すると判断しました。欠落は起きておらず、低下は設定で避けられます。幅の決め方の見直しは、BL-006 とあわせて検討するほうが、整合のとれた対策になるためです。
- **継続作業での経緯と対処**: 2026-11-21、対策する継続案件を開始しました (検討 ID: 261121-porter-flow-control-refine、全体管理文書: `261121-porter-flow-control-refine-overview.md`)。状態は「検討中」で、対策の方針をユーザーに確認しています。

### 影響範囲とリスク

- **影響対象**: `unicast_bidir_n1` のサーバー (既定の構成)。処理件数と往復時間。
- **放置した場合のリスク**: 既定の構成の N 対 1 で、処理件数が約 16% 低く、往復時間が約 18% 長くなります。ピア数が多いほど、幅が小さくなり、更新が増える可能性があります (4 つより多いピア数では未測定)。

### 推奨される対応策

- **恒久対応案** (未決定):
    - N 対 1 サーバーの幅の決め方を見直す (ピア数で割らずに、実際に送信しているピアの数で割るなど)。
    - 送出上限の更新の条件 (前回知らせた範囲の半分) を、幅が小さい場合に緩める。
    - N 対 1 サーバーの受信用のソケットに、既定より大きい OS の受信バッファーを設定する。
- **回避策**: 処理件数を優先する構成では、OS の受信バッファーを大きくするか、サーバーとクライアントの `flow_control_receive_buffer_percent` を無効にします (`docs/config.md` に記載済み)。

## BL-009 急に遅くなった受信者を、次の受信報告を待たずに監視対象へ加える手段がない

- **今回の見送り理由**: 受信報告による順位付けだけで足りると判断し、追加の合図の設計は、この案件では扱わないとしたためです。

### 推奨される対応策

- **恒久対応案**: NACK など、既存のパケットの受信を合図に、その受信者の余裕を 0 として扱い、候補に加えます (抑制の要求の受信と同じ扱い)。受信報告の周期を短くする方法は、パケットの数が増えるため推奨しません。BL-006 の対策とあわせて検討します。
- **参考情報**: 最終仕様の「残課題の扱い」、[Q-057](261119-porter-flow-control-discussion.md#q-057-遅い集団を見つける方法)、`docs/protocol.md` の監視対象を選ぶ節。

## BL-011 余裕が同じ受信者の選び順が、管理表の先頭に固定されている

## BL-012 unicast の受信者が受信報告に送出上限を載せないため、送出上限の更新の喪失を受信報告で補えない

### 概要と問題点

- **現状の事象**: `multicast` と `broadcast` の受信者は、受信報告に自身の送出上限を載せますが、`unicast` の受信者は載せません (`seq_num` と `ack_num` を 0 にします)。`unicast` の送信者は、フロー制御パケットで知らされた送出上限だけを使います。更新のフロー制御パケットが続けて失われた場合は、送出上限の有効期限 (`flow_control_request_lifetime_ms`) が過ぎてから、送出上限を破棄して制限なく送出し、次の通知が届くまで続きます。
- **本来あるべき姿**: 更新の喪失からの回復に、周期的に届く受信報告を使える形にするかどうかが、判断されていること。

### 経緯と見送り理由

- **摘出契機**: 版 7 の整理時の確認 (`docs/protocol.md` の受信報告の節)。
- **今回の見送り理由**: `unicast` は、受信者が 1 台のため、送出上限を順位付けに使う必要がなく、現行の回復 (周期の再送と有効期限) で足りると判断しており、仕様として記載しています。ただし、更新の喪失時の挙動を、受信報告で補う案は検討していません。
- **継続作業での経緯と対処**: 2026-11-21、対策する継続案件を開始しました (検討 ID: 261121-porter-flow-control-refine、全体管理文書: `261121-porter-flow-control-refine-overview.md`)。状態は「検討中」で、対策の方針をユーザーに確認しています。

### 影響範囲とリスク

- **影響対象**: `unicast` の受信者と送信者。
- **放置した場合のリスク**: 更新の連続した喪失と、有効期限の経過の間に、送出上限を使った制限が外れる時間が生じます。実害は、更新の喪失が続いた場合に限られます。

### 推奨される対応策

- **恒久対応案**: 現行のまま容認するか、`unicast` の受信者も受信報告に送出上限を載せて、送信者が補助的に使うかを判断します。判断した結果を、`docs/protocol.md` に根拠とともに記載します。
- **参考情報**: `docs/protocol.md` の受信報告の節と送出上限の有効期限の節。
