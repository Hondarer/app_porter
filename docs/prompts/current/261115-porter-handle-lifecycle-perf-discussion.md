### Q-001 Windows と WSL の測定分担

**Status**

解決済み

**Question**

BL-001 の測定を、Windows と Linux (WSL) のどちらで行いますか。

**Context**

元案件の性能比較は Windows/MSVC だけで行いました。設計は Linux/GCC と Windows/MSVC の両方を検証対象としていますが、性能測定の環境は「同じマシン、OS、ビルド設定」で比較することだけを定めています。

両 OS で全項目を測ると、OS 間の差 (スレッドの起床、ソケットの実装、メモリ計測の方法) も比べられますが、測定と記録の量は約 2 倍になります。TCP 終了時エラーは Windows の予備測定で発生しており、Linux で再現するかは記録がありません。

WSL2 は同じ物理マシン上の VM です (WSL セッションの報告では、72 論理 CPU と 62[GiB] を割り当て)。両 OS で同時に測ると CPU、メモリ帯域、キャッシュを奪い合い、遅延分布やばらつきの値が乱れます。このため、ビルドと準備は並行して行い、測定の実行は交互にする (片方が測っている間はもう片方が待つ) ことを前提とします。セッション間で「測定開始」と「測定完了」を連絡して切り替えます。

メモリ量の計測手段は OS ごとに異なります。Linux 側の glibc は 2.28 で `mallinfo2` (glibc 2.33 以降) が使えないため、`/proc/self/status` の `VmRSS` と `VmHWM` などを使う想定です。Windows 側は `GetProcessMemoryInfo` (`PROCESS_MEMORY_COUNTERS`) などを使う想定です。OS ごとの計測手段と、OS 間で比べられる指標の定義は、最終仕様で明記します。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 両 OS で全 5 項目を測定する。Windows セッションが Windows/MSVC、WSL セッションが Linux/GCC を担当し、同じ測定プログラムを使う。測定の実行は交互にする。
- [ ] B: 全項目を Windows で測定し、WSL では TCP 終了時エラーの再現確認だけを行う。
- [ ] C: 測定項目を OS ごとに分ける (例: 返信経路と遅延分布は Windows、低速コールバックと open/close 反復は Linux)。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-15 15:18:57 JST (回答を記録したファイルの最終更新日時。個別の選択時刻は特定できない)

**Assessment**

A が明示選択されています。両 OS で全 5 項目を測り、ビルドと準備は並行、測定の実行は交互にします。測定の切り替えは、セッション間で「測定開始」と「測定完了」を連絡して行います。

第 2 ゲート承認記録: 2026-11-15、ユーザーは最終仕様に対して「本件承認するので、対処を自走してください」と回答しました。あわせて次の指示を受けました。

進行中の方針変更と判断 (2026-11-15):

- ビルド方法: Windows は makefw を使わず cl で直接コンパイルしました。現行版の OpenSSL は、Windows 用の静的ライブラリがないため DLL のインポート ライブラリと結合しました。改修前版の zlib と cjson は、同梱のパッケージから接頭辞なしの静的ライブラリを作りました。Linux は zlib を共有ライブラリ、OpenSSL を静的ライブラリで結合しています。
- ポート: WSL の NAT モードでは WSL 内の待ち受けに Windows の localhost から接続できるため、基準ポートを Windows 19000、Linux 29000 に分けました。
- TCP 終了時エラー: Windows で POTR_TYPE_TCP_BIDIR の連続 close が 5[s] 後に POTR_ERR_TIMEOUT となる不具合を、両版で再現しました。原因は cplat の単一ソケット待機が POLLHUP を ready と扱わないこと、porter が FIN 受理後も経路を維持すること、close の FIN_ACK 待ちが経路切断で起こされないことです。[Q-007](#q-007-tcp-終了時エラーが製品不具合だった場合の扱い) の B に従い本案件で修正します。原因の一部が cplat にあるため、修正範囲に `app/cplat` を含めます。
- 現行版の定義: cplat の修正は全通信種別に効くため、本測定の現行版は修正後のコミットとします。
- 両版に共通する TCP の約 40[ms] の停止 (TCP_NODELAY なし) は、本案件の backlog BL-001 に記録しました。
- Windows の基準ポート: 別アプリ (AdobeCollabSync) が 127.0.0.1:19292 で待ち受けており、P4 TCP が bind エラーになったため、Windows の基準ポートを 39000 に変えて P4 を再実行しました。P1〜P3 は 19000 で問題なく完了したため、そのまま使いました。
- P4 の標本: Windows のスレッド数の取得が重く、1 サイクルあたり約 175[ms] かかったため、保持量の傾きの標本を 10 サイクルごとにしました。
- P1 の 5000 バイト・通常・4 スレッド: Linux で既定負荷が 900 秒で終わらなかったため、件数 1000 件の追加条件を両 OS で測りました。
- Linux の保持量: ページ単位の指標では 1 サイクルあたり数百バイトの保持を検出できないため、制御情報の保持量の目安は Windows の値を使いました。
