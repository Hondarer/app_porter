## LADR-001 しきい値による抑制と解除

決定者: Tetsuo Honda  
最終更新日: 2026-11-20

### 背景と課題

porter には送信の流量を制御する仕組みがなく、受信側の処理が追い付かない場合の扱いが定まっていませんでした。フロー制御を導入するにあたり、抑制と解除を判定する方式と、しきい値を変更できるかどうかを決める必要がありました。

### 得られた事実

- 機能仕様は、輻輳制御と帯域の制御を適用範囲外としており、フロー制御の要件はありません (`docs/functional-spec/delivery.md`、`docs/functional-spec/transport.md` の「適用範囲外」)。
- 過去の検証では、受信コールバックが遅い負荷で、受信側が追い付けない分が UDP の受信バッファーのあふれと REJECT による切断で失われています (`docs/prompts/past/261115-porter-reject-recovery-discussion.md` の P3 の注記)。

### 決定

porter にフロー制御を導入します。受信側の占有量が、抑制を要求するしきい値を超えたら送信を抑制し、解除するしきい値を下回ったら抑制を解除します。  
2 つのしきい値は構成で変更でき、既定値は 80% と 50% です。解除のしきい値が要求のしきい値以上の構成は、エラーにします。  
容量が 0 でない場合に、要求のしきい値から容量までの余裕が `max_message_size` 未満の構成も、エラーにします。

## LADR-002 占有量を計測する対象

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

依頼の「receiver のバッファー」に当たる候補が、受信側に 3 つありました (通知キュー、受信ウィンドウ、OS のソケット受信バッファー)。80% と 60% を何の占有量で判定するか、その単位と集計の範囲を決める必要がありました。

### 得られた事実

- 受信スレッドは、受信した DATA を通知キューへ登録し、通知スレッドが利用側コールバックを実行します (`docs/architecture.md` の「ハンドルの寿命と通知の実行」)。
- 通知キューには容量の上限がなく、通知 1 件ごとに管理情報とデータ長の領域を確保します (`prod/libsrc/porter/potr_notify.c` の `potr_internal_notify_enqueue()`)。
- コールバックの処理が受信より遅い間は、保持する領域が受信データ量に比例して増えます (`docs/api.md` の「通知継続不能のエラー イベント」)。
- 受信ウィンドウ (`window_size`、既定 16、最大 256) は、順序の整列のための領域です (`docs/protocol.md` の「スライディング ウィンドウ」)。
- 通知キューはハンドルに 1 本であり、N 対 1 サーバーでは全ピアからの受信データが同じ通知キューに並びます。

### 決定

占有量は、受信側の通知キューで計測します。割合の基準になる容量を、設定値として新設します。  
占有量と容量は、DATA のバイト数で数えます。CONNECTED などのデータを伴わない通知は、占有量に含めません。  
N 対 1 サーバーでは、占有量をピアごとに数え、しきい値を超えたピアにだけ抑制を要求します。通知キューはハンドルに 1 本のままとし、コールバックを受信順に実行する現在の動作は変えません。

## LADR-003 対象とする通信種別

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

porter の通信種別は 10 種類あり、受信側から送信側へ戻るパケットの有無と、下位の通信の性質が異なります。フロー制御を導入する通信種別の範囲を決める必要がありました。

### 得られた事実

- 通信種別は、再送を行わない RAW モード (`unicast_raw`、`multicast_raw`、`broadcast_raw`)、片方向 UDP (`unicast`、`multicast`、`broadcast`)、双方向 UDP (`unicast_bidir`、`unicast_bidir_n1`)、TCP (`tcp`、`tcp_bidir`) に分かれます (`prod/include/porter/porter_type.h` の `potr_type`)。
- 片方向 UDP の受信者は、NACK と受信報告 (REPORT) を送信者へ送出します。RAW モードの受信者は、どちらも送出しません (`docs/protocol.md` の「再送制御」「受信報告」)。
- TCP の受信スレッドも、受信した DATA を通知キューへ登録します (`docs/architecture.md` の「UDP / TCP 機能共有状況」)。

### 決定

フロー制御の対象は、片方向 UDP の再送を行う通信種別 (`unicast`、`multicast`、`broadcast`)、双方向 UDP (`unicast_bidir`、`unicast_bidir_n1`)、TCP (`tcp`、`tcp_bidir`) とします。  
RAW モード (`unicast_raw`、`multicast_raw`、`broadcast_raw`) は対象外とします。

## LADR-004 1 対 N での抑制の判定

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

1 対 N (`multicast`、`broadcast`) の送信は、全受信者に共通の 1 本の流れであり、受信者ごとに送出を止め分けられません。一部の受信者だけが抑制を要求した場合の、送信側の判定方法を決める必要がありました。

### 得られた事実

- 送信側は、受信報告を送ってきた受信者をセッション識別子ごとに管理表へ登録し、`health_timeout_ms` の間に受信報告が届かない受信者を活動中でないと判定します。管理表の上限は `max_peers` (省略時 1,024) です (`prod/libsrc/porter/protocol/receiver_report.c`)。
- 受信報告は、実効 `health_interval_ms` が 0 の構成では送出されません。受信者は、起動から最初の受信報告までに実効 `health_interval_ms` だけ待ちます (`prod/libsrc/porter/thread/thread_recv_report.c`)。

### 決定

フロー制御は、1 対 N でも利用できるようにします。  
1 対 N では、抑制を要求している受信者の「割合」と「台数」の 2 つの条件を設け、どちらかを満たしたら送信を抑制します。どちらの条件も満たさなくなったら解除します。無効にした条件は判定に使いません。  
割合の分母と台数の判定には、活動中の受信者数を使います。活動中の受信者は、受信報告で活動中と判定している受信者と、有効な抑制の要求を送ってきている受信者です。後者は受信報告の有無にかかわらず数えます。この扱いはフロー制御の判定に限り、経路の優先グループの判定と死活監視のタイムアウトには使いません。  
1 対 N でフロー制御を有効にする場合は、実効 `health_interval_ms` が 0 でないことを必須にします。  
既定値は、割合 0 (無効)、台数 2 です。活動中の受信者数が台数の設定値を下回る場合は、活動中の受信者数を台数のしきい値として使います (例: 設定値 2 で活動中の受信者が 1 台なら、その 1 台の要求で抑制する)。

## LADR-005 容量を超えた受信データの扱い

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

抑制の要求が送信側へ届くまでの間や、要求が失われた場合に、占有量が容量の 100% を超えることがあります。超えた DATA を受け入れ続けるか、破棄するかを決める必要がありました。

### 得られた事実

- 過去の案件で、通知キューについて「メモリ使用量の固定上限は設けず」「通知キューが満杯という理由で I/O スレッドを空き待ちさせない」と決定しています (`docs/prompts/past/261107-porter-handle-lifecycle-design.md`)。
- 再送を行う通信種別は、再送を要求した範囲が送信側に存在しない場合に、その通信を切断として利用側へ通知します。切断後は受信の状態を破棄し、次に届いた DATA または PING から新しい通信として受信を再開します (`docs/protocol.md` の「REJECT の役割」)。

### 決定

占有量が容量の 100% を超えた場合は、超えた DATA を破棄し、その通信を切断として利用側へ通知します。受信スレッドを待たせることはしません。  
切断の時点で通知キューにある DATA は、そのまま順に利用側へ渡し、その後に切断を通知します。受信の状態 (受信ウィンドウの保持内容、フラグメント途中の状態) は破棄します。N 対 1 サーバーでは、容量を超えたピアだけを切断します。TCP では、その接続を切断します。  
切断の後は、占有量が解除のしきい値を下回るまで、その相手からの受信を再開しません。UDP では DATA と PING を破棄して新しい通信として採用せず、TCP では接続を確立しません。この間も、抑制の要求は送り続けます。  
占有量が解除のしきい値を下回った後は、従来の切断と同じく、次に届いたパケットまたは接続から受信を再開します。

## LADR-006 抑制状態を伝えるパケットとプロトコル バージョン

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

抑制の要求と解除を受信側から送信側へ伝える手段が必要です。既存のパケットに相乗りするか新しい種別を設けるか、TCP でも同じ手段を使うか、対向側と交換する形式の版を上げるかを決める必要がありました。

### 得られた事実

- 受信側から送信側へ戻る既存のパケットは、片方向 UDP が NACK と受信報告、双方向 UDP が NACK と PING、TCP が PING と FIN_ACK です (`docs/protocol.md`)。
- 受信報告は実効 `health_interval_ms` ごとに送出し、0 の構成では送出しません。受信報告と PING のペイロード長は 8 バイトであることを検査しています (`prod/libsrc/porter/protocol/receiver_report.c`)。
- TCP の受信スレッドはソケットから読み続けて通知キューへ移すため、利用側コールバックが遅くても下位のフロー制御は働きません。
- 受信側は、`protocol_version` が自身の版と一致しないパケットを破棄します。現行の版は 2 です (`docs/protocol.md` の「外側パケット」)。

### 決定

抑制の要求と解除は、新しいパケット種別で伝えます。対象の全通信種別 (片方向 UDP、双方向 UDP、TCP) で同じ形式を使います。  
ペイロードは 1 バイトの状態 (抑制の要求または解除) だけを持ちます。しきい値をまたいだ時点で即時に送出し、受信側の全経路から送信者へ送出します。保護 (暗号化と認証) は、同じ向きの既存パケット (受信報告、PING) と同じ鍵と方式にします。  
TCP の受信側は読み取りを止めず、PING と FIN の処理を抑制中も継続します。  
プロトコル バージョン (`POTR_PROTOCOL_VERSION`) を 2 から 3 へ上げます。

## LADR-007 抑制の要求と解除が届かない場合の回復

決定者: Tetsuo Honda  
最終更新日: 2026-11-19

### 背景と課題

UDP では抑制の要求と解除のパケットが失われることがあり、抑制を要求した受信者が停止すると解除は届きません。これらの場合に、送信側が止まり続けたり、抑制が効かなくなったりしない方式を決める必要がありました。

### 得られた事実

- porter の再送は、通常時は確認を返さず、問題発生時のみ受信側から通知する方式です (`docs/protocol.md` の「再送制御」)。
- 再送周期 200 ms と有効期限 1,000 ms は提案値であり、実測に基づくものではありません。
- パケットの封緘と送出は、送信スレッド、受信スレッド、ヘルス チェック スレッドが並行して行っており、送出通番はアトミックに採番されます (`prod/include_internal/porter/protocol/packet_seal.h`、`prod/libsrc/porter/protocol/packet_seal.c` の呼び出し元)。
- 占有量の減算は、コールバックから復帰した通知スレッドで起きます。片方向の受信者の受信スレッドは、ソケットの受信を時間を区切って待っており、他のスレッドから即時に起こす手段を持ちません (`prod/libsrc/porter/thread/potr_recv_thread.c` の `recv_thread_func()`)。

### 決定

抑制の要求に有効期限を持たせます。受信側は、抑制を要求している間、一定の周期で要求を再送します。送信側は、最後に要求を受けてから有効期限が過ぎたら、その受信者の要求を取り消します。  
解除は、占有量が解除のしきい値を下回ったことを受信側が検出した時点で、即時に 1 回送出します。検出した通知スレッドがその場で送出し、受信スレッドの周期処理を待ちません。取り下げを伝えるパケットは、フロー制御パケットの「解除」の状態です。  
受信者のセッションが変わった場合と、切断と判定した場合も、その受信者の要求を取り消します。1 対 N では、要求の再送の間隔を受信報告と同じ方法でばらつかせます。  
再送周期と有効期限は構成で変更でき、既定値は 200 ms と 1,000 ms です。有効期限が再送周期以下の構成は、エラーにします。

## LADR-016 解除の直後の集中送出への対策

決定者: Tetsuo Honda  
最終更新日: 2026-11-20

### 背景と課題

抑制の解除の直後に、送信キューの内容がまとめて送出され、受信側の容量を超えて切断になることがあります (残課題一覧の BL-004)。

### 得られた事実

- 一時的な確認プログラムでは、容量 2 MB、送信キューの深さ 1024 (既定値) の `tcp` で、解除の直後に容量を超えて切断になりました。深さ 64 では切断が起きませんでした。
- 受信側が要求を出してから送信側が止まるまでの間に届く DATA は、要求のしきい値から容量までの余裕に収まる必要があります。
- 送信側が保持する再送用のパケットは `window_size` (既定 16、最大 256) 個のため、まとまった欠落は再送で回復できません (`docs/config.md`)。
- TCP の生存の判定は PING の受信時刻で行うため、受信側が TCP の受信を止める方式は、生存の判定による切断を招きます (`prod/libsrc/porter/thread/potr_recv_thread.c`)。
- 通番は、UDP と TCP のどちらでも、外側のパケットごとに 1 ずつ増えます (`docs/protocol.md`)。

### 決定

集中送出への対策を、この案件で行います。方式は「送出上限の通知」です。受信側が「この通番まで送ってよい」という上限をフロー制御パケットで知らせ、送信側は上限に達したら、次のフロー制御パケットが届くまで新しい DATA の送出を止めます。  
抑制の要求と再送、要求の有効期限、1 対 N の判定、N 対 1 サーバーのピアごとの保留、容量を超えた場合の切断は変えません。  
個別の ACK にはしません。完全な防止は求めず、UDP の OS の受信バッファーあふれ、圧縮した DATA、最初の送出上限が届く前の送出は、対策の対象外とします。

## LADR-018 UDP の連続送信による OS の受信バッファーあふれへの対策

決定者: Tetsuo Honda  
最終更新日: 2026-11-21

### 背景と課題

UDP で、待ち合わせを指定せずに連続して送信すると、受信側の OS の受信バッファーがあふれ、欠落から再送不能の切断になります。この案件で対策するかどうかと、その方式、適用する範囲を決める必要がありました。

### 得られた事実

- 欠落と切断は、変更前のライブラリでも、送信側と受信側を別のプロセスにすると起きます (同じホストの Linux、`unicast`、1,000 byte × 6,000 件)。
- 既存の設定では防げません (`send_queue_depth` を 16 まで下げた場合だけ起きず、64 では起きる。`window_size` を最大にしても起きる)。
- 送出上限の幅を OS の受信バッファーに入る数 (約 90 パケット) より小さくすると (約 57 パケット)、欠落も切断も起きず、待ち合わせを指定した送信の約 6 倍の速さで全件が届きました。幅が約 114 パケットと約 228 パケットの場合は、あふれました。
- `multicast` と `broadcast` では、受信者のそれぞれが送信者へ通知を送るため、送信者が受ける通知の数が受信者の台数に比例します。

### 決定

- この案件で対策します。
- 方式は、OS の受信バッファーに基づく送出上限とします。受信側が、OS の受信バッファーの大きさから送出上限の幅を計算し、通知キューの占有量から求めた許可数と比べて、小さいほうを知らせます。
- `unicast`、`unicast_bidir`、`unicast_bidir_n1` の受信側には、容量 (`flow_control_capacity`) の設定によらず、既定で適用します。無効にする設定を設けます。TCP は対象外です。
- `multicast` と `broadcast` では、全台ではなく、送信者が選んだ限られた台数の受信者 (監視対象) だけが送出上限を通知します。監視対象は、遅い集団 (台数または割合) です。
- 極端に遅い少数の受信者 (外れ値) は、送出の判定で無視します。この判定には、既存の 1 対 N の判定 (`flow_control_receiver_count`、`flow_control_receiver_percent`) を、意味を変えずに使います。送信者は、遅いほうから「しきい値」番目の受信者に合わせます。
- 遅い集団は、全受信者の受信報告から見つけます。受信者は、受信報告に自身の送出上限を載せます。送信者は、余裕 (送出上限 − 次に割り当てる通番) が小さいほうから監視対象を選びます。受信報告に載せた送出上限は、順位付けだけに使います。受信者を順に試す段階は設けません。
- `multicast` と `broadcast` では、送出上限を送るのは、容量 (`flow_control_capacity`) の設定によらず、監視対象の受信者だけです。抑制の要求と解除は、容量を設定した受信者の全員が送ります。
- 監視する数は、`flow_control_monitored_receiver_count` (既定 4) と `flow_control_monitored_receiver_percent` (既定 0) で決めます。両方を設定した場合は多いほう、無視するしきい値より少ない場合はしきい値の台数、活動中の受信者が少ない場合は全員を監視します。
