# porter の TCP 遅延の改善 (TCP_NODELAY) 最終仕様

ファイル名: `261117-porter-transport-performance-redo-design.md`

版: 1

状態: 承認済み (2026-11-17)

## 目的と範囲

porter の TCP 通信で、小さい送信が約 40[ms] 止まる事象 (残課題 BL-001) を解消します。原因は、小さい送信をまとめて送る Nagle アルゴリズムと、受信側が確認応答を遅らせる遅延 ACK が重なることです。対策として、Nagle アルゴリズムを無効にするソケット オプション `TCP_NODELAY` を、porter が使うすべての TCP 接続で有効にします。

この案件は、対策を cplat と porter の `main` へ取り込み、両方の作業環境 (Windows と Linux (WSL)) を同期した時点で完了とします。

小さいメッセージと圧縮送信の処理件数の低下 (残課題 BL-002) は、この案件の対象外です。BL-001 の完了後に、別の案件として扱います。

## 対策の方針

対策は次の 3 点で構成します。

- porter が使うすべての TCP 接続で、`TCP_NODELAY` を常に有効にします。利用者が切り替える設定は設けません。
- cplat に汎用の関数 `cplat_socket_set_nodelay` を設け、porter が接続の開始前と受け入れの直後に呼びます。cplat のソケット生成の既定は変えません。
- 設定に失敗した場合は、警告を記録して接続を続けます。

> [!IMPORTANT]
> 1 点目の「常に有効」は、後述の性能の確認で見直す理由が出た場合に、ユーザーへ再確認します。再確認の結果で方針が変わる場合は、この文書を改版して承認を受け直します。

## 性能の確認

`main` へ入れる前に、対策の前後の性能を改めて測ります。過去の測定で、Linux の 5000[B] のメッセージの処理件数が 35.8%〜77.9% 下がりました。原因は分かっていません。

### 確かめる仮説

porter は、5000[B] のメッセージを最大 1400[B] のパケット 4 個に分け、パケットごとに送信の関数を 1 回呼びます。Nagle アルゴリズムが有効な間は OS が複数のパケットをまとめて送りますが、`TCP_NODELAY` を有効にするとパケットごとに送り出します。処理件数の低下はこの違いで起きている、というのが仮説です。

仮説は、1 メッセージ分のパケットをまとめて 1 回の送信の呼び出しで送る試行版を作り、処理件数が戻るかどうかで確かめます。

### 測る版

| 版 | 内容 | ソース |
| --- | --- | --- |
| off | 対策なし | cplat と porter の `main` |
| on | 対策あり | cplat と porter のブランチ `fix/bl001-tcp-nodelay` |
| batch | 対策あり、かつ 1 メッセージ分のパケットをまとめて 1 回で送る試行版 | on のソースの複製に、`potr_send_thread.c` の試行の変更を加えたもの |

Table: 測る版

試行版は、リポジトリの作業ツリーではなく、一時領域のソースの複製に対して作ります。性能の測定は、準備 (一時領域、試行版、ビルド) が終わった時点でユーザーに確認してから始めます。仮説が否定された場合や、別の原因の候補が見つかった場合は、同じ手順で試行版を追加します (最大ペイロード長を大きくした設定での比較など)。追加した版と理由は、検討用 Markdown の「反映と検証の記録」に残します。

### 測る条件

測定プログラムは、一時領域 `C:\Users\tetsuo\AppData\Local\Temp\porter-transport-perf-ab-20261116` の `bench/bench.cc` を変更せずに使います。条件は、過去の測定と同じ 18 条件です。

- close の所要時間を測る 1 条件 (TCP、片方向)。
- 処理件数を測る 16 条件。メッセージ長 (64[B]、5000[B])、送信の種類 (通常、圧縮、ブロッキング、圧縮とブロッキング)、スレッド数 (1、4) の組み合わせです。

### 結果の扱い

測定の後、版ごと・条件ごとの中央値を表にまとめ、ユーザーへ提示します。5000[B] の低下の扱いは、ユーザーが結果を見て決めます。想定する選択肢は次の 3 つです。

- 送信をまとめる修正を、この対策に含める。
- 低下を既知の特性として受け入れる。
- `TCP_NODELAY` を利用者が切り替えられる設定にする。

送信をまとめる修正を含める場合や、設定を設ける場合は、製品コードとテストの変更の内容をこの文書に追記して改版し、承認を受けてから実装します。

## 検証

性能の確認と、その結果の反映が終わった後に、次の順で検証します。

1. Linux の全件 `make test` が過去に完了しなかった原因を調べます。過去の実行では、テスト 1 件ごとの後処理が 1 分を超えました。
2. cplat と porter のブランチを作業ツリーへ切り替え、Windows と Linux (WSL) のそれぞれで、cplat と porter の全件 `make` と `make test` を実行します。対象範囲の `.warn` ファイルに内容がないことを確認します。
3. porter の機能仕様 (`docs/functional-spec/`) と設計文書に、この対策で追記が必要な箇所があるかを確認し、必要な場合は反映します。
4. 親リポジトリにブランチ `fix/bl001-tcp-nodelay` を作り、cplat と porter のブランチを参照させ、`main` 向けのプル リクエストを作ります。CI の全ジョブの成功と、警告がないことを確認します。

> [!NOTE]
> 親リポジトリの CI は、`main` への push と `main` 向けのプル リクエストだけで起動します。ブランチの内容を `main` へ入れる前に CI で確かめるには、プル リクエストが必要です。

手順 1 で原因を解消できず、全件 `make test` を完了できない場合は、作業を止めてユーザーに確認します。全件テストの所要時間は、手順 1 の調査の後に見積もって報告します。
