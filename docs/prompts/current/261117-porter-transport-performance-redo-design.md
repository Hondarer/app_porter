# porter の TCP 遅延の改善 (TCP_NODELAY とまとめ送り) 最終仕様

ファイル名: `261117-porter-transport-performance-redo-design.md`

版: 2

状態: 再承認待ち (版 1 は 2026-11-17 に承認済み。版 2 で送信をまとめる変更を追加)

## 目的と範囲

porter の TCP 通信で、小さい送信が約 40[ms] 止まる事象 (残課題 BL-001) を解消します。原因は、小さい送信をまとめて送る Nagle アルゴリズムと、受信側が確認応答を遅らせる遅延 ACK が重なることです。対策として、Nagle アルゴリズムを無効にするソケット オプション `TCP_NODELAY` を、porter が使うすべての TCP 接続で有効にします。あわせて、`TCP_NODELAY` によって増える小さい送信を減らすため、送信スレッドが送信キューに溜まったパケットをまとめて 1 回で送るようにします (以下「まとめ送り」)。

この案件は、対策を cplat と porter の `main` へ取り込み、両方の作業環境 (Windows と Linux (WSL)) を同期した時点で完了とします。

小さいメッセージと圧縮送信の処理件数の低下 (残課題 BL-002) は、この案件の対象外です。BL-001 の完了後に、別の案件として扱います。

## 対策の方針

対策は次の 4 点で構成します。

- porter が使うすべての TCP 接続で、`TCP_NODELAY` を常に有効にします。利用者が切り替える設定は設けません。
- cplat に汎用の関数 `cplat_socket_set_nodelay` を設け、porter が接続の開始前と受け入れの直後に呼びます。cplat のソケット生成の既定は変えません。
- 設定に失敗した場合は、警告を記録して接続を続けます。
- TCP の 1:1 通信で、送信スレッドが送信キューに溜まったパケットを、メッセージの境界をまたいでまとめて 1 回の送信の呼び出しで送ります。待ち時間は足しません。

> [!NOTE]
> `TCP_NODELAY` だけを有効にすると、Linux で 1400[B] を超えるメッセージの処理件数が 35.2%〜74.4% 下がります。分割したパケットを 1 個ずつ送り出すためです。まとめ送りは、この低下を解消するために加えます。

## まとめ送りの仕様

### 対象

対象は、TCP の 1:1 通信の送信スレッド (`prod/libsrc/porter/thread/potr_send_thread.c`) です。UDP と N:1 の送信は変更しません。ワイヤ上のバイト列 (各パケットを封緘した結果と、その並び順) は、経路が 1 本の場合、変更の前と同じです。受信側の変更はありません。

### 動作

送信スレッドは、送信キューからエントリを 1 件取り出すたびに、その時点でキューにある後続のエントリも取り出し、外側パケットを順に組み立てます。組み立てたパケットは、経路 (path) ごとに順に封緘して 1 つのバッファーへ連結し、送信の関数を 1 回だけ呼びます。

- 外側パケットの組み立ての規則は変えません。分割されたメッセージの断片は、1 件で 1 つの外側パケットにします。分割されていないメッセージは、従来と同じ規則で後続の単体のエントリを同じ外側パケットへ詰めます。
- 1 回にまとめるパケットは最大 16 個です。連結用のバッファーが 64[KiB] を超える設定 (最大ペイロード長が大きい場合) では、上限を下げます。
- メッセージの境界では待ちません。キューが空になった時点で、集めた分を送ります。
- 分割されたメッセージの断片の途中で、次の断片がまだキューにない場合は、上限付き (5[ms]) で次の断片を待ちます。ただし、完結したメッセージをすでに集めている場合は待たずに送ります。
- 集めた結果が 1 パケットだけの場合は、従来の 1 パケットの送信の手順を使います。
- まとめ送りの待ち合わせ (`pack_wait_ms`) が設定され、先頭が分割されていないメッセージの場合は、待ち合わせを含む従来の処理を使います。

> [!NOTE]
> 断片の途中で次の断片を待つ理由は 2 つあります。同じメッセージの断片は、送信の API が排他を保持したまま続けて登録するため、次の断片はすぐに届きます。また、受信側は全断片がそろうまでメッセージを配信できないため、この待ちはそのメッセージの配信を遅らせません。試行版の測定では、待ちが上限に達した回数は 0 回でした。

### 維持する不変条件

- 経路ごとの送信の排他 (`tcp_send_mutex`) を保持したまま、PING の通知、封緘、送信を行います。
- DATA の前に、未通知の経路状態の PING を書き込みます。
- PING の通知、封緘、送信のどれかに失敗した経路は、ソケットを停止して受信スレッドに切断を検知させます。
- 送信バッファーに空きがない経路は、ほかの経路に書き込めた場合に限り飛ばします。どの経路にも書き込めないまま、パケットを捨てません。この判定は、まとめたパケット列を 1 つの単位として行います。
- どれかの経路に書き込めた場合に限り、まとめた全パケットを送信ウィンドウへ登録し、通番を進めます。
- 再送が必要な場合は、保持中の DATA を、新しい DATA より先に送ります。
- 取り出したエントリは、書き込みの後に、すべて成功または失敗として完了させます。ブロッキング送信の完了の判定は変えません。

### 作業用のバッファー

連結用のバッファーは、送信のたびに確保しません。送信スレッドの開始時、またはコンテキストの初期化時に 1 回だけ確保し、終了時に内容を消去してから解放します。確保に失敗した場合の扱いは、既存の暗号用バッファーの確保の失敗と同じ扱いにそろえます。

### 実装で確かめる事項

試行版で分かっている次の 3 点は、実装の中で確かめ、結果を検討用 Markdown に記録します。

- **複数の経路での送出通番の順序**: 従来はパケットごとに経路を巡って封緘しますが、まとめ送りでは経路ごとにパケット列を封緘します。このため、経路間で送出通番の割り当て順が変わります。受信側の重複検出と順序の扱いで問題が起きないことを、コードの確認と、2 経路の単体テストで確かめます。問題がある場合は作業を止めて、ユーザーに確認します。
- **Windows の通知遅延の上位の増加**: 試行版では、Windows の 5000[B]・ブロッキング・1 スレッドで、通知遅延の p95 が 143.5[µs] から 647.2[µs] に増えました (中央値は 109.5[µs] から 64.4[µs] へ短縮)。原因を調べます。まとめ送りが原因で、解消できない場合は、数値を示してユーザーに確認します。
- **断片の途中の待ちの要否**: 待ちを外しても同じ性能が出る場合は、待ちを外して単純にします。

### 単体テスト

`test/` 配下の送信スレッドの単体テストに、次の観点を追加します。配置とエビデンスの規則は、リポジトリのテストの規範に従います。

- 分割されたメッセージの全パケットが、1 回の送信の呼び出しで、変更の前と同じバイト列で書き込まれる。
- キューにある複数のメッセージ (分割されたものと、されていないもの) が、境界をまたいで 1 回で書き込まれる。
- 上限 (16 パケット) を超える分は、次の送信に分かれる。
- 1 パケットだけの場合は、従来の手順で書き込まれる。
- 封緘または送信に失敗した場合に、ソケットを停止し、取り出した全エントリを失敗として完了させ、送信ウィンドウと通番を進めない。
- 2 経路で、両方の経路に同じパケット列が書き込まれる。片方の経路だけ書き込めない場合の扱いが、従来と同じである。
- 再送が必要な場合に、保持中の DATA が新しい DATA より先に書き込まれる。

## 性能の確認 (実施済み)

### 確かめる仮説

porter は、5000[B] のメッセージを最大 1400[B] のパケット 4 個に分け、パケットごとに送信の関数を 1 回呼びます。Nagle アルゴリズムが有効な間は OS が複数のパケットをまとめて送りますが、`TCP_NODELAY` を有効にするとパケットごとに送り出します。処理件数の低下はこの違いで起きている、というのが仮説です。

仮説は、1 メッセージ分のパケットをまとめて 1 回の送信の呼び出しで送る試行版を作り、処理件数が戻るかどうかで確かめます。

- Linux の 5000[B]・ブロッキング・1 スレッドで、まとめ送りを加えても、対策の前より処理件数が約 17% 低いこと。送信キューに同時に 1 メッセージしか入らないため、待ち時間を足さずにまとめる方法がありません。
- Windows の圧縮送信の処理件数が、同じ版でも測定ごとに大きく変わること。原因は未調査です。
