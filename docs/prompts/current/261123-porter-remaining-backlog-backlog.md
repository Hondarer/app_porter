## BL-003 小さいメッセージと圧縮送信で処理件数が低下し通知遅延が増える

区分: 過去 backlog からの転記 (`../past/261117-porter-transport-performance-redo-backlog.md` の BL-001)  
優先度 / 影響度: 中

### 概要と問題点

- **現状の事象**: ハンドル寿命管理の改修の前に比べて、64 byte、圧縮・4 スレッド、N:1 の返信の条件で、処理件数が下がっています。
    元の条件で戻ったことを示す測定は、ありません。

    転記元にある 2026-11-15 の測定 (5 回の中央値) では、ハンドル寿命管理の改修前の版に比べて、次の条件で処理件数が下がり、通知遅延が増えました。

    - UDP 64 byte・通常・1 スレッド: 処理件数 Windows -34.5%、Linux -23.6%
    - UDP 64 byte・圧縮・4 スレッド: 処理件数 Windows -26.5%、Linux -60.8%。通知遅延の p99 は約 8 倍
    - TCP 圧縮・4 スレッド: 処理件数 Windows -72.3% (64 byte)、-61.4% (5,000 byte)
    - Linux の N:1 返信 (外部スレッド、64 byte): 往復時間 約 1.5 倍、処理件数 -31.3%
- **本来あるべき姿**: 未確定です。
    安全性と公開契約を維持したまま減らせる追加のコストがあるかを特定し、許容するか改善するかを判断する必要があります。

### 経緯と見送り理由

- **摘出契機**: `../past/261117-porter-transport-performance-redo-backlog.md` の BL-001 からの転記です。
    `../past/261115-porter-reject-recovery-backlog.md` の BL-002 からの引き継ぎです。
- **今回の見送り理由**: この案件の `unicast` の計測 (最終仕様の作業 4) と領域が重なりますが、原因が複数に分かれる見込みのため、範囲に含めませんでした (簡易 ADR の LADR-002)。
    この案件の計測で分かったことは、「参考情報」に記載しました。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `261123-porter-remaining-backlog-phase2` を開始し、この項目を今回の範囲に含めるかどうかを検討しています (継続案件の検討用 Markdown の Q-001)。  
    2026-11-25 に、ユーザーが継続案件の対策の範囲を BL-010 だけにすると決めたため (継続案件の検討用 Markdown の Q-001、簡易 ADR の LADR-001)、状態を「次フェーズへ転記」にしました。転記先は `261123-porter-remaining-backlog-phase2-backlog.md` の BL-003 です。

### 影響範囲とリスク

- **影響対象**: 非ブロッキング送信の処理件数と通知遅延。
    特に、圧縮を指定した複数スレッドの送信。
- **放置した場合のリスク**: 小さいメッセージを高頻度で送る用途や、圧縮を多用する用途で、改修前より処理能力が下がります。

### 推奨される対応策

- **恒久対応案**: 圧縮・4 スレッドの条件でプロファイルを取り、通知スレッドの起床、通知キューへの受け渡し、圧縮と展開の各段階の時間とロックの競合を測ります。
    主因を特定してから、改善案と安全性への影響を比べます。  
    TCP の条件は、転記元の案件の変更 (`TCP_NODELAY` とまとめ送り) で数値が変わったため、基準を測り直してください。
- **参考情報**: `../past/261115-porter-reject-recovery-backlog.md` の BL-002 (旧案件での調査の経緯を含む)。
    転記元の測定プログラムと結果の保存先は、`C:\Users\tetsuo\AppData\Local\Temp\porter-transport-perf-redo-20261117` です。  
    TCP の基準は、`TCP_NODELAY` とまとめ送りの変更を含めて測り直す必要があります。

    この案件では、1 対 1 の片方向の UDP の送信側で、DATA パケットを送出するたびにヘルス チェックのスレッドを起こす処理を、`prod/libsrc/porter/thread/potr_send_thread.c` の `flush_packed()` から外しました。  
    Linux (WSL)、ループバック、送信スレッド 1 つで、変更の前の版、変更の後の版、`tcp` を交互に 3 回測り、各回 5 測定の中央値の、さらに 3 回の中央値で比較しました。

- **恒久対応案** (未決定): サニタイザーを使うと判断した場合は、開発環境と CI のコンテナーへ `libasan` と `libtsan` を導入し、makefw にサニタイザーを有効にするビルドの指定の方法を用意して、手順を文書にします。使わないと判断した場合は、その判断を記録して、この項目を閉じます。
- **暫定対応案**: `dnf download libasan` で取得したパッケージを `rpm2cpio` で一時領域へ展開し、展開先の `usr/lib64` に `libasan.so` から `libasan.so.5.0.0` へのシンボリック リンクを作って、`LIBRARY_PATH` (リンク時) と `LD_LIBRARY_PATH` (実行時) に指定します。フラグ (`-fsanitize=address -fno-omit-frame-pointer -g`) は、作業ツリーの複製の `app/<name>/makepart.mk` で `CFLAGS`、`CXXFLAGS`、`LDFLAGS` に加えます。

## BL-010 unicast の待ち合わせを指定した 5,000 byte の送信が、tcp の約 0.48 倍にとどまる (複数のパケットを 1 回の呼び出しで送る方法が未実装)

区分: 検討時見送り  
優先度 / 影響度: 中

### 概要と問題点

- **現状の事象**: `unicast` で、1 つのメッセージが複数の外側パケットに分かれる大きさ (5,000 byte は 4 パケット) を、待ち合わせを指定して送ると、処理件数が `tcp` の約 0.48 倍です (この案件の、パケットごとのヘルス チェックのスレッドの起床を外す変更の後。変更の前は 0.34)。送信スレッドは、外側パケットごとに `cplat_socket_sendto()` を呼び、この条件では、1 パケットあたりのカーネルの時間が約 32 µs あります (送信の指定なしでは約 5 µs)。
- **本来あるべき姿**: `unicast` の処理件数が、同じ条件の `tcp` に対して、数倍の劣化になっていないこと (この案件の基準では、比が 0.5 以上)。

### 経緯と見送り理由

- **摘出契機**: 検討時の見送り (2026-11-23。この案件の検討用 Markdown の Q-007、簡易 ADR の LADR-007)。対策元は、`../past/261121-porter-flow-control-refine-backlog.md` の BL-001 です。
- **今回の見送り理由**: 対策 (複数のパケットを 1 回の呼び出しで送る方法) は、`app/cplat` への関数の追加、`framework/testfw` の mock、porter の送信スレッドの UDP の送出の作り直しを伴い、送信ウィンドウとフロー制御の更新の順序などの設計が必要なためです。ユーザーが、別の案件で設計すると決めました。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `261123-porter-remaining-backlog-phase2` を開始し、この項目を今回の範囲に含めるかどうかを検討しています (継続案件の検討用 Markdown の Q-001)。  
    2026-11-25 に、ユーザーがこの項目を継続案件の対策の範囲にすると決めました (継続案件の検討用 Markdown の Q-001)。合意した方針は、適用の範囲を UDP の DATA の送出のすべて (1 対 1 の 4 つの通信種別と N 対 1。暗号化と複数経路を含む)、Windows も Registered I/O などで一括の送信にする、Linux の性能の基準は待ち合わせを指定した 5,000 byte の `tcp` との比が 0.5 以上でほかの条件が下がらない、一部だけ送れた場合の残りは 1 個ずつ 1 回ずつ試みる、です (簡易 ADR の LADR-003 から LADR-006)。Windows の実装の担当、Registered I/O の実現性の確認、cplat の API の形、Windows の性能の基準、N 対 1 のまとめる単位を、追加の質問 (Q-008 から Q-014) で確認しています。  
    2026-11-25 に、追加の質問の回答で、次を決めました (簡易 ADR の LADR-002、LADR-003、LADR-004、LADR-008、LADR-009)。Linux のセッションが Windows の実装の初版まで書き、Windows のセッションがビルド、テスト、測定を行う。最終仕様の前に Windows で Registered I/O の試作を行い、使えない、または速くない場合は Windows を `sendto` の繰り返しにする。cplat には、呼び出し元のバッファーを渡して先頭から送れた個数を返す同期の関数を追加する。N 対 1 は同じピア宛てに続くパケットだけをまとめる。Windows の基準は、変更の前より待ち合わせを指定した 5,000 byte の処理件数が上がり、ほかの条件が下がらないこと。現在は、Windows の試作の結果を待っています。  
    2026-11-25 に、Windows の試作で、Registered I/O のソケットでは `WSAEventSelect()`、`sendto`、`recvfrom` が `WSAENOTSOCK` で失敗すると分かり、Windows の一括の送信は `sendto` の繰り返しに確定しました。最終仕様 `261123-porter-remaining-backlog-phase2-design.md` を作成し、状態を「対応中」にしました。確定した方針は、cplat に登録したソケットの一括の送信の関数 (`cplat_socket_watch_sendto_multi()`。Linux は `sendmmsg()`) を追加し、porter の送信スレッドが UDP の DATA を、1 対 1 は送信キューに続く外側パケットを、N 対 1 は同じピア宛てに続く外側パケットを、最大 16 個まで 1 回で送る、です。Windows の処理件数が上がることの確認と、暗号化と複数経路の性能の測定は、継続案件の残課題一覧の BL-012 と BL-013 へ送りました。

### 影響範囲とリスク

- **影響対象**: `unicast` (および、同じ送出の経路を使う UDP の通信種別) で、1,400 byte (`max_payload`) を超えるメッセージを、待ち合わせを指定して送る用途。
- **放置した場合のリスク**: この用途で、porter の UDP が TCP の約半分の処理件数にとどまります。ループバックでの値で、実際のネットワークでの差は未確認です。

### 推奨される対応策

- **恒久対応案**: `app/cplat` の net カテゴリに、複数のデータグラムを 1 回で送る関数を追加し (Linux は `sendmmsg()`、Windows は 1 個ずつの繰り返し、または相当の機能)、porter の送信スレッドが、送信キューに同時にある複数の外側パケット (少なくとも、1 つのメッセージを分けたパケット) をまとめて送るようにします。設計で決める点は、一部だけ送れた場合の扱い、通番、送信ウィンドウへの登録、フロー制御の許可数との関係、再送、経路が複数の場合、適用する通信種別 (`unicast_bidir`、N 対 1、`multicast`、`broadcast`) です。受信側の一括の受信 (`recvmmsg()`) の効果は、確かめていません。
- **参考情報**: 一時領域の複製での実験 (2026-11-23。1 対 1 の `unicast`、経路 1 つ、最大 16 個を `sendmmsg()` で送る試作。起床を外す変更を含む。再現の試験と同時に測った参考の値): 待ち合わせを指定した 5,000 byte の処理件数は、5,624 と 5,365 件/秒が、9,366 と 11,787 件/秒になり、`tcp` (11,586 と 12,154 件/秒) との比は、0.44 から 0.49 が、0.81 から 0.97 になりました。送信の指定なしの 5,000 byte (比 0.58 から 0.65) と、1,000 byte では、はっきりした効果は見えませんでした。`strace` では、5,100 メッセージに対して、`sendmmsg` が 5,103 回、`sendto` が 488 回でした。試作は一時領域にあり、リポジトリには入っていません。
