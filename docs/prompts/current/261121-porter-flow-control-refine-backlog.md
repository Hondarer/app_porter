## BL-001 unicast の処理件数が、同じ条件の tcp を下回る

### 概要と問題点

- **現状の事象**: `porter-bench` で、`unicast` (`p1`) と `tcp` (`p5`、片方向) の処理件数を同じ条件で比べると、64 byte 以外のメッセージ長で、`unicast` が `tcp` を下回ります。
- **再現条件** (2026-11-21、Linux (WSL) の同じホストのループバック、送信スレッド 1 つ、交互に 3 回、各回 5 測定の中央値の、3 回の中央値):

    | メッセージ長 | 送信の指定 | `unicast` [件/秒] | `tcp` [件/秒] | `unicast` ÷ `tcp` |
    | --- | --- | --- | --- | --- |
    | 64 byte | 指定なし | 133,721 | 129,784 | 1.03 |
    | 1,000 byte | 指定なし | 84,081 | 121,224 | 0.69 |
    | 5,000 byte | 指定なし | 17,405 | 74,119 | 0.23 |
    | 64 byte | 待ち合わせを指定 | 10,755 | 12,476 | 0.86 |
    | 1,000 byte | 待ち合わせを指定 | 10,669 | 12,069 | 0.88 |
    | 5,000 byte | 待ち合わせを指定 | 4,004 | 11,823 | 0.34 |

    `unicast` の値は、どの条件でも、毎秒およそ 7 万から 8.5 万パケットで頭打ちになっています (5,000 byte のメッセージは、`max_payload` 1,400 byte のため 4 パケットに分かれます)。フロー制御によるものではありません (OS の受信バッファーに基づく送出上限の有効と無効の差は、`unicast` で −0.6% から +3.5%)。
- **本来あるべき姿**: `unicast` の処理件数が、同じ条件の `tcp` に対して、数倍の劣化になっていないこと。ユーザーは、1 対 N では、流れるパケットの量を考えると porter の UDP が総合的に高速と見なせるため、1 対 1 の比較で数倍の劣化になっていない限りは問題ないとしています。5,000 byte の条件 (0.23 倍、0.34 倍) は、この範囲を外れています。

### 経緯と見送り理由

- **摘出契機**: 受入の基準を確かめるための測定 (検討用 Markdown の Q-011、Q-022)。
- **今回の見送り理由**: 原因がフロー制御の外 (送信スレッドと受信スレッドの、パケットごとの OS の呼び出し) にあり、対策は OS ごとの送受信の処理の作り直しになるためです。ユーザーが Q-022 で、この案件には含めず、別の案件で行うと判断しました。この案件では、フロー制御の変更の前後で、比が下がらないことだけを確認します。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: UDP の通信種別の、1,000 byte 以上のメッセージの処理件数。`prod/libsrc/porter/thread/` の送信スレッドと受信スレッド。
- **放置した場合のリスク**: メッセージが大きい用途で、porter の UDP が TCP より遅くなります。ループバックは TCP に有利な条件のため、実際のネットワークでの差は未確認です。

### 推奨される対応策

- **恒久対応案** (未決定): まず、どの処理に時間がかかっているかを特定します (OS の呼び出しの回数、スレッドの間の起床の回数)。そのうえで、複数のパケットを 1 回の呼び出しでまとめて送受信する方法 (Linux の `sendmmsg()` と `recvmmsg()` など。OS ごとに異なる) と、スレッドの間の起床を減らす方法を検討します。実際のネットワークでの `tcp` との比較も行います。
- **参考情報**: 検討用 Markdown の Q-011 と Q-022、簡易 ADR の LADR-002 と LADR-011、性能の案件の残課題一覧 (`261117-porter-transport-performance-redo-backlog.md` の BL-001 から BL-003。同じ領域の課題)、`bin/porter_bench_ab.py`。

- **本来あるべき姿**: 複数のホストの多数の受信者で、猶予時間、除外する数の上限、予算の既定値が妥当であることが確認されていること。

### 経緯と見送り理由

- **今回の見送り理由**: 複数のホストの環境がないためです。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: `multicast` と `broadcast` の既定の構成。
- **放置した場合のリスク**: 実機の多数の受信者で、既定値が適さない可能性があります。

### 推奨される対応策

- **恒久対応案**: 複数のホスト (またはコンテナーとネットワークの遅延の模擬) で、受入条件 5 と 6 と同じ確認を行い、既定値を見直します。
- **参考情報**: 最終仕様の「既定値の根拠と確認」と受入条件 5、6。

## BL-003 Windows のビルドで、1 つのディレクトリのソースが多いと、コンパイルのコマンド行が長さの上限を超える

### 概要と問題点

- **現状の事象**: Windows (MSVC) のビルドは、1 つのディレクトリのソースを、1 つのコマンド行にまとめてコンパイラへ渡します (`framework/makefw/makefiles/_msvc_compile.mk` の `_msvc_compile_cpp_normal`)。`app/porter/test/libsrc/mock_porter` の直下の `.cc` が 148 個から 158 個に増えた時点で、コマンド行が 8,388 文字になり、Windows のコマンド プロセッサの上限 (8,191 文字) を超えて、ビルドが失敗しました。エラーの表示は、シェルの構文エラー (`unexpected EOF while looking for matching ')'`) で、原因が分かりにくい形です。Linux では起きません。
- **本来あるべき姿**: ソースの数によらず、Windows でビルドできること。上限を超える場合に、原因が分かるエラーになること。

### 経緯と見送り理由

- **摘出契機**: 作業中の気付き (2026-11-22。Windows のセッションでの、作業用のブランチの MSVC のビルドの確認で判明)。
- **今回の見送り理由**: 恒久の対処は、`framework/makefw` の変更になり、この案件 (`app/porter` のフロー制御) の範囲の外です。この案件では、`mock_porter` のフロー制御の mock を、サブディレクトリ (`test/libsrc/mock_porter/flow_control/`) へ分けて、直下のソースの数を減らすことで、回避します。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: 1 つのディレクトリに多数のソースを置く、すべての app (ライブラリ、mock のライブラリ)。Windows のビルドだけに影響します。
- **放置した場合のリスク**: ソースを追加した時点で、Windows のビルドだけが失敗します。Linux の確認では見つからず、CI の Windows のジョブ、または Windows の利用者の環境で、初めて分かります。回避 (サブディレクトリへの分割) は、ディレクトリごとに、余裕を見ながら行う必要があります。

### 推奨される対応策

- **恒久対応案**: `_msvc_compile.mk` が、ソースの一覧を、応答ファイル (`@file`) などで、コンパイラへ渡すようにします。または、コマンド行の長さを、実行の前に検査し、上限を超える場合に、原因と対処 (サブディレクトリへの分割) を示すエラーにします。
- **暫定対応案**: ソースが多いディレクトリを、サブディレクトリ走査方式 (`framework/makefw/docs/subfolder-compilation.md`) で分けます。
- **参考情報**: `app/porter/test/libsrc/mock_porter` の、分割の前の直下の `.cc` は 158 個、コマンド行は 8,388 文字。この案件で、フロー制御の mock とスレッドの mock をサブディレクトリへ分け、直下は 106 個、6,208 文字になりました (余裕 1,983 文字。mock をあと約 30 個足すと、再び上限に届きます)。

## BL-004 multicast の受信者の切断が起きる構成の測定で、1 回、プロセスが異常終了した

### 概要と問題点

- **現状の事象**: `porter-bench` の `p6` (送信者 1、受信者 3 を、同じプロセスで動かす) を、保持範囲 64、OS の受信バッファーの拡大を要求しない、監視する数の下限 1 の構成で 20 回測定した中で、1 回、プロセスが SIGSEGV で異常終了しました。この構成は、既定の構成ではなく、監視対象でない受信者が欠落から回復できずに、切断と再接続を起こす実行が、6 回に 1 回ほどあります。異常終了の位置と原因は、分かっていません。
- **本来あるべき姿**: 欠落、切断、再接続が起きる条件でも、プロセスが異常終了しないこと。

### 経緯と見送り理由

- **摘出契機**: 作業中の気付き (2026-11-22。レビューの指摘の修正の後の測定)。
- **今回の見送り理由**: 再現できていないためです。同じ構成の 200 回の実行 (うち 32 回で、欠落と切断が起きた)、デバッガーの下の 304 回の実行で、異常終了は 0 回でした。メモリの検査ツール (valgrind) の下の 6 回の実行 (うち 2 回で、切断が起きた) でも、不正なメモリの参照は、検出されませんでした。異常終了が起きた測定は、別の作業がライブラリをビルドし直す可能性がある時間帯に行われており、実行中のプロセスが読み込んでいる共有ライブラリの置き換えが原因である可能性を、否定できていません。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: 不明です。ライブラリの不具合であれば、`multicast` と `broadcast` の、受信者の切断と再接続が起きる場面が、対象になります。
- **放置した場合のリスク**: まれな条件で、利用側のプロセスが異常終了する可能性があります。

### 推奨される対応策

- **恒久対応案**: 異常終了の位置を取得できる状態 (コア ダンプの取得の設定、または、アドレス サニタイザーとスレッド サニタイザーを有効にしたビルド) で、欠落と切断が起きる構成を、繰り返し実行します。
- **暫定対応案**: なし。この案件の受入の測定 (Linux で約 260 回の実行) では、再発しませんでした。
- **参考情報**: 測定のコマンドは、`porter-bench --cond p6 --receivers 3 --runs 1 --config window_size=64 --config udp_receive_buffer_size=-1 --config flow_control_monitored_receiver_count=1` です。

## BL-005 Windows で、N 対 1 の送出上限を有効にすると、処理件数が約 10% 下がる

### 概要と問題点

- **現状の事象**: Windows の `porter-bench` の `p2` (N 対 1 サーバー、クライアント 4、64 byte、10,000 件) で、OS の受信バッファーに基づく送出上限を有効にすると、無効の場合に比べて、処理件数が約 10% 下がります (15 回の中央値で 80,052 と 89,075 件/秒)。Linux の同じ条件では、差は約 3% です。Windows の受信バッファーは 4 MiB (幅 834 パケット) で、順番の許可にはなっていません。欠落と切断はありません。
- **本来あるべき姿**: 送出上限の有無の差が、5% 以内であること (この案件の受入条件 7 の基準)。

### 経緯と見送り理由

- **摘出契機**: 作業中の気付き (2026-11-23。受入条件 11 の Windows での測定)。
- **今回の見送り理由**: ユーザーの判断で、残課題とします。欠落と切断がなく、大きな問題ではないためです。調査をするかどうかは、案件の終了後に改めて判断します。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: Windows の `unicast_bidir_n1`。
- **放置した場合のリスク**: Windows の N 対 1 サーバーで、処理件数が 1 割ほど低くなります。

### 推奨される対応策

- **恒久対応案**: Windows で、送出上限の有効と無効の差の内訳 (フロー制御パケットの数、ロックの待ち、送出可否の確認の時間) を計測し、原因を特定します。Linux で効果があった対策 (送出可否の記録) が、Windows で働いているかも確かめます。
- **参考情報**: コマンドは `porter-bench --cond p2 --bytes 64 --count 10000 --warmup 1000 --clients 4 --reply-mode ext --inflight 16 --receive-buffer-limit on|off --config window_size=64`。
