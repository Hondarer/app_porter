# porter のフロー制御の残件対策 最終仕様

ファイル名: `261121-porter-flow-control-refine-design.md`

版: 3

## 目的と方針

porter のフロー制御を、次の 3 つの方針に沿って見直します。

| 方針 | 内容 |
| --- | --- |
| 1 | 複数台との通信で、スループットが下がった一定割合の送受信者は、救済を優先しません。システム全体が健全に動作することを優先します |
| 2 | スループットを高く維持します |
| 3 | フロー制御によって、受信側のバッファーのあふれを回避します。健全な送受信者が受けるあふれを、防ぐ対象にします |

Table: 方針

方針 2 と方針 3 がぶつかる場合は、スループットを優先します。あふれを防げなかった場合は、再送で回復できれば足りるものとします。

この文書は、現在の仕様 (`docs/protocol.md`、`docs/config.md`、`docs/functional-spec/` に記載されているフロー制御) からの変更を定めます。この文書に記載のない動作は、現在の仕様のままです。

### 用語

| 用語 | 意味 |
| --- | --- |
| 送出上限 | 受信側が送信側へ知らせる「この通番まで送ってよい」という値 |
| 許可数 | 送出上限と、受信側が次に受信する通番の差 |
| 許可数の上限 | 受信側が 1 回に知らせる許可数の最大値。受信バッファーの幅と、容量から決まる最大の許可数の小さいほう |
| 受信バッファーの幅 | OS の受信バッファーに収まると見積もったパケット数 |
| 止める状態 | 相手から有効な抑制の要求を受けている、または相手の送出上限に達している状態 |
| 監視対象 | `multicast` と `broadcast` で、送信者が送出上限を使う相手として選んだ受信者 |
| 除外 | 送信者が、遅い受信者を「救済しない」と判定し、止める判定に使わなくすること |
| 猶予時間 | 遅い相手が全体を止めてよい時間の上限 (`flow_control_grace_ms`) |
| 保持範囲 | 送信側が再送のために保持する過去のパケット数 (`window_size`) |

## プロトコルの変更

プロトコル バージョンを 4 にします。バージョン 3 以前の相手とは通信しません (バージョンが異なるパケットの扱いは、現在の仕様と同じです)。

### フロー制御パケットの状態の値

| 値 | 名前 | 向き | 意味 |
| --- | --- | --- | --- |
| 1 | 抑制の要求 | 受信側 → 送信側 | 変更なし |
| 2 | 解除 | 受信側 → 送信側 | 変更なし |
| 3 | 監視対象の一覧 | 1 対 N の送信者 → 受信者 | 変更あり (「監視対象の一覧への応答」の節) |
| 4 | 問い合わせ | 送信側 → 受信側 | 追加。受信側に、現在の状態と送出上限の送出を求める。ペイロードは状態の 1 byte だけ |
| 5 | 上限なし | 受信側 → 送信側 | 追加。受信側が送出上限を使わないことを知らせる。送出上限の欄は 0 |

Table: フロー制御パケットの状態の値

### 受信報告

受信報告のヘッダーの欄の意味を、次のとおり変更します。パケットの数と大きさは変わりません。

| 欄 | 変更前 | 変更後 |
| --- | --- | --- |
| `seq_num` | 送出上限の有無 (`1` または `0`) | 許可数の上限。送出上限がある場合は 1 以上。`0` は、送出上限がないことを表す |
| `ack_num` | 送出上限 | 変更なし |

Table: 受信報告の欄

`unicast` の受信者も、`multicast` と `broadcast` の受信者と同じく、受信報告に送出上限と許可数の上限を載せます。

> [!NOTE]
> 許可数の上限は、送信者が監視する数を決める計算だけに使います。容量を設定した受信側の許可数は、通知キューの占有量によってパケットごとに変わるため、その時点の値ではなく、受信者ごとにほぼ一定の上限を載せます。監視する数が、受信報告のたびに増減しないようにするためです。

### DATA パケット

DATA パケットに、フラグ「送出上限あり」を追加します。このフラグが立っている DATA は、ヘッダーの `ack_num` に、送出する側が相手へ知らせる送出上限を載せます。フラグが立っていない DATA の `ack_num` は、従来どおり 0 で、受信時に無視します。フラグのビットは、実装時に未使用のビットから割り当て、`docs/protocol.md` に記載します。

## 送出上限の共通の動作

### 初期の幅

送信側は、相手から最初の通知 (送出上限、または「上限なし」) を受けるまで、セッションの最初の通番から「初期の幅」(4 パケット) を超える DATA を送出しません。

- 対象は、`multicast` と `broadcast` の送信者を除く、すべての通信種別です。N 対 1 サーバーは、ピアごとに適用します。
- 送出上限を使わない受信側 (容量が 0 で、OS の受信バッファーに基づく送出上限も使わない) は、最初に送出できる時点で、「上限なし」を 1 回送出します。問い合わせを受けた場合も、「上限なし」を返します。
- 「上限なし」を受けた送信側は、相手のセッションが変わるまで、その相手に送出上限がないものとして扱います。
- 相手のセッションが変わった場合は、最初の通知を受けていない状態に戻します。

> [!NOTE]
> 初期の幅は、受信バッファーの幅の下限と同じ値です。どの受信側も、4 パケットは受け取れます。最初の通知は、最初のパケットの往復の時間で届くため、影響は接続の直後に限られます。

> [!IMPORTANT]
> `multicast` と `broadcast` の送信者は、受信者を知る前に送出を始めるため、初期の幅を適用しません。受信者は、送信者を採用した時点で、周期を待たずに最初の受信報告を送ります。送信者がその受信報告を処理するまでの間は、あふれを防げません。

### 問い合わせ

UDP の通信種別の送信側は、送出する DATA があるのに、相手の送出上限 (または初期の幅) で止まっている間、相手へ「問い合わせ」を送出します。

- 最初の問い合わせは、止まり始めてから 10 ms 後に送出します。以後は、間隔を 2 倍ずつ延ばし、`flow_control_request_interval_ms` を上限とします。止まっている状態が終わったら、間隔を元に戻します。
- 問い合わせを受けた受信側は、その時点の状態 (抑制の要求、解除、上限なし) と送出上限を、フロー制御パケットで 1 回送出します。
- `multicast` と `broadcast` の送信者は、問い合わせの代わりに、同じ間隔で監視対象の一覧を送出し直します (「監視対象の一覧への応答」の節)。
- TCP は、フロー制御パケットが失われないため、問い合わせを行いません。

送出上限の破棄の条件を、次のとおり変更します。

| 場合 | 変更前 | 変更後 |
| --- | --- | --- |
| 止まったまま、有効期限 (`flow_control_request_lifetime_ms`) の間、送出上限が進まない | 送出上限を破棄し、制限なく送出する | 相手から何らかのパケット (フロー制御パケット、受信報告、NACK、PING、DATA) が届いている間は、破棄しない |
| 止まったまま、有効期限の間、相手から何も届かない | 同上 | 相手がいないものとして、送出上限を破棄する。その後、相手からパケットが届いた時点で、その時点の通番から初期の幅までに抑え、問い合わせを送出する |
| 最初の通知を受けていない状態 (初期の幅) で止まったまま、有効期限の間、最初の通知が届かない | (初期の幅は、この仕様で追加) | 相手からパケットが届いていても、相手がいないものとして扱う (上の行と同じ動作) |

Table: 送出上限の破棄の条件

この破棄の条件は、`multicast` と `broadcast` の送信者が保持する、監視対象の受信者の送出上限にも適用します。

> [!NOTE]
> 最初の通知を受けていない状態では、相手が、こちらのセッションをまだ採用していない場合があります (最初の DATA がすべて失われた場合)。この場合、相手は問い合わせを受理できないため、相手からのパケットを、相手が送出上限を知らせられる証拠としては扱いません。有効期限の後に、初期の幅の分の DATA を改めて送出できるようにすることで、相手がセッションを採用できるようにします。

> [!NOTE]
> 通知が失われた場合は、問い合わせで 10 ms 後に回復します。相手が動いているのに制限なく送出する経路は、なくなります。相手が停止した場合に、片方向の送信側が止まり続けることもありません。

### 送信が途切れた後の許可

UDP の通信種別では、送信側と受信側の双方が、送信が途切れた後に、未使用の許可を初期の幅まで減らします。

- 送信側は、相手への DATA の送出が `flow_control_request_lifetime_ms` 以上途切れた場合、送出上限を「次に割り当てる通番 + 初期の幅」と、保持している送出上限の小さいほうにします。
- 受信側は、相手からの DATA の受信が `flow_control_request_lifetime_ms` の半分以上途切れた後に DATA を受理した場合、その時点で送出上限の更新を送出します。

> [!NOTE]
> 送信していない相手が大きな許可を持ち続けると、N 対 1 サーバーで、多数のピアが同時に送信を始めたときに、許可の合計が OS の受信バッファーを超えます。途切れた後の許可を小さくすることで、この合計を抑えます。受信側の時間を半分にするのは、双方の時計のずれで、送信側だけが許可を減らした状態になるのを避けるためです。

### 受信報告による回復

送信側は、受信報告に載った送出上限が、保持している送出上限より先へ進んでいる場合、送出上限を更新します。`unicast` と、`multicast` と `broadcast` の監視対象に適用します。

### 逆方向の DATA への相乗り

`unicast_bidir` と `unicast_bidir_n1` では、送出上限を使う側が相手へ DATA を送出するときに、「送出上限あり」のフラグを立てて、その時点の送出上限を載せます。

- 受ける側は、載っている送出上限が、保持している値より先へ進んでいる場合だけ、送出上限を更新します。再送された DATA に載っている古い値は、この条件で無視されます。
- 送出上限を知らせた記録 (「前回知らせた範囲」) は、フロー制御パケットと DATA のどちらで知らせた場合も更新します。DATA で知らせた分は、更新のフロー制御パケットを送出しません。
- 抑制の要求と解除は、従来どおりフロー制御パケットで送出します。

### 圧縮した DATA の許可数

容量を設定した受信側は、「占有量による許可数」の計算で、1 パケットの大きさとして、`max_payload` と「そのセッションで受信した DATA パケット 1 個の、展開後の大きさの最大値」の大きいほうを使います。

## OS の受信バッファー

### 拡大の要求

porter は、UDP のソケットを開くときに、OS の受信バッファーの大きさを OS へ要求します。

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `udp_receive_buffer_size` | 4,194,304 (4 MiB) | OS へ要求する受信バッファーの大きさ [byte] |

Table: 受信バッファーの大きさの設定

- `global` とサービスごとの設定の両方に追加します。サービス側の 0 と省略は「`global` の値を使用」、`global` の 0 は「既定値を使用」です。要求しない場合は、専用の値 (構成ファイルでは `-1`、構造体では `POTR_FLOW_CONTROL_DISABLED`) を指定します。
- 受信バッファーの幅は、要求の後に OS から取得した実際の大きさで計算します。計算式は変更しません。
- 実際の大きさが要求より小さい場合は、要求した値、実際の値、OS の設定の見直しが必要であることを、診断出力 (INFO) にサービスごとに 1 回記録します。エラーにはしません。
- TCP のソケットには適用しません。
- OS への要求は、`app/cplat` に追加する関数で行います。testfw の標準ライブラリのモックにも、対応する関数を追加します。

| OS | 既定の大きさ | 既定の幅 | 4 MiB を要求した場合 |
| --- | --- | --- | --- |
| Windows | 65,536 byte | 13 パケット | 要求どおりになる |
| Linux | 212,992 byte | 42 パケット | OS の上限 (`net.core.rmem_max`) で切り詰められる。Linux は設定値を 2 倍にして保持するため、上限が既定 (212,992) のままの場合は、425,984 byte (約 84 パケット) になる。4 MiB の場合の幅 (約 834 パケット) にするには、上限を大きくする必要がある |

Table: OS ごとの受信バッファーの大きさ

### 設計の指針として文書に記載する事項

`docs/config.md` に、次の事項を記載します。

- 受信バッファーの幅が大きいほど、送出上限の更新が減り、一時的な遅れを受け止められます。あふれの回避とスループットを両立させる手段は、OS の受信バッファーを大きくすることです。
- Linux では、要求した大きさどおりの受信バッファーにするために、`net.core.rmem_max` を要求する大きさ以上にする必要があります。
- 仮想化された環境などでは、ホスト側のネットワーク アダプターの設定 (受信バッファー、受信キューなど) の見直しが必要になる場合があります。これは porter の責務の外ですが、あふれがホスト側で起きると、porter のフロー制御では防げません。

## multicast と broadcast (1 対 N の通信種別)

### 止める判定と除外

送信者は、除外していない受信者のうち、1 台でも「止める状態」であれば、新しい DATA の送出を止めます。

送信者は、受信者ごとに、「その受信者が止める状態で、送信者が送出を止めていた時間」を積算します。

```text
止めていた間     : 積算 = 積算 + 経過時間
止めていない間   : 積算 = 積算 − 経過時間 ÷ 9   (0 を下回らない)
全体が遅い間     : 積算を変えない
積算 ≧ 猶予時間 : その受信者を除外する (除外している数が上限に達していない場合)
```

「全体が遅い間」は、止める状態の受信者の数 (除外している受信者を含む) が、除外する数の上限を超えている間です。この間は、どの受信者の積算も進めず、新しく除外もしません。送信者は、止める状態の受信者に合わせて止まります。

- 「止めていた間」は、送信者が、送出する DATA があるのに止まっていた区間です。その区間の始めの判定の時点で、止める状態だった受信者に加算します。
- 複数の受信者が同時に止める状態で、その数が除外する数の上限以下の場合は、その全員の積算を進めます。
- 除外している数が上限に達している場合は、それ以上除外しません。送信者は、止める状態の受信者に合わせて止まり続けます (全体が遅い状態として扱います)。積算は、猶予時間を上限として保持します。
- 同時に複数の受信者が猶予時間に達した場合は、積算に達した順に除外します。

```text
除外する数の上限 = 「flow_control_excluded_receiver_count」と
                   「活動中の受信者数 × flow_control_excluded_receiver_percent ÷ 100 (切り捨て)」の大きいほう
                   ただし、「活動中の受信者数 − 1」を超えない
```

| 活動中の受信者数 | 除外する数の上限 (既定の設定) |
| --- | --- |
| 1 | 0 |
| 3 | 1 |
| 10 | 1 |
| 50 | 5 |
| 100 | 10 |

Table: 除外する数の上限の例

除外した受信者の扱いは、次のとおりです。

- 送信者は、除外した受信者の送出上限と抑制の要求を、止める判定に使いません。監視対象にも選びません。
- 送信者は、除外した受信者へ特別な通知を送りません。除外した受信者は、欠落を NACK で要求し、保持範囲を超えた場合は、従来どおり切断になります。
- 除外は、その受信者の送出上限 (受信報告に載った値) が、送信者が次に割り当てる通番より先にある状態が、猶予時間の 10 倍の間続いた時点で解きます。
- セッションが変わった受信者は、新しい受信者として扱います。
- 除外している数は、活動中の受信者だけで数えます。除外した受信者が活動中でなくなった場合は、除外を解きます。
- 除外と、除外を解いたことは、診断出力 (INFO) に記録します。

> [!NOTE]
> 全受信者が同じように遅い場合は、遅い一部ではなく、全体の速さです。誰かを除外しても全体は速くならず、除外された受信者だけが、送出上限による保護を失います。このため、止める状態の受信者の数が、除外する数の上限を超えている間は、除外のための積算を進めません。N 対 1 サーバーの切断と、同じ考え方です。

> [!NOTE]
> 積算を「止めていない時間の 9 分の 1」ずつ減らすのは、全体の送出時間のうち約 10% までの停止を、一時的な遅れとして受け入れるためです。長い間この割合を超えて全体を止める受信者は、止まったり進んだりを繰り返していても、積算が猶予時間に達して除外されます。1 回の連続した停止は、猶予時間まで受け入れます。

> [!IMPORTANT]
> 従来の「台数の条件」と「割合の条件」(`flow_control_receiver_count`、`flow_control_receiver_percent`) による判定は、廃止します。従来は、条件に満たない数の受信者が止める状態でも、送信者は止まりませんでした。変更後は、1 台でも止める状態であれば止まり、止め続けた受信者だけを除外します。

### 監視対象の選び方

送信者は、除外していない活動中の受信者で、余裕の記録があるものを、余裕が小さい順に、次の条件を満たす範囲で監視対象にします。

```text
通知の見込み = 監視対象の各受信者の「2 ÷ 許可数の上限」の合計   (DATA 1 パケットあたりのフロー制御パケットの数)
条件         : 通知の見込み ≦ flow_control_feedback_percent ÷ 100
監視する数   : 条件を満たす最大の数
               ただし、flow_control_monitored_receiver_count (下限) 以上、64 と候補の数以下
```

- 「許可数の上限」は、その受信者の受信報告に載った値です。
- 余裕が同じ受信者の間では、現在の監視対象を優先します。その次に、監視対象でなくなってからの時間が長い受信者を優先します。
- 監視対象でない受信者から、NACK または抑制の要求を受けた場合は、その受信者の余裕を 0 として記録し、選び直します。

| 受信者の OS の受信バッファー | 許可数の上限 | 監視する数 (既定の予算 5%) |
| --- | --- | --- |
| Linux の既定 (212,992 byte) | 42 | 1 |
| 1 MiB | 約 208 | 5 |
| 4 MiB | 約 834 | 20 |

Table: 監視する数の例

> [!IMPORTANT]
> 監視対象の外の健全な受信者が、合図を送る間もなく遅れた場合 (OS が受信スレッドを止めた場合など) は、OS の受信バッファーがあふれます。この場合は、再送で回復します。あふれを確実に防ぐ受信者を増やすには、OS の受信バッファーを大きくするか、`flow_control_monitored_receiver_count` または `flow_control_feedback_percent` を大きくします。

### 監視対象の一覧への応答

- 監視対象の受信者は、自身を含む監視対象の一覧を受けるたびに、その時点の送出上限を、フロー制御パケットで 1 回送出します。
- 送信者は、監視対象の送出上限で止まっている間、「問い合わせ」の節の間隔で、監視対象の一覧を送出し直します。
- 一覧の送出の時点 (監視対象が変わった時点と、`flow_control_request_interval_ms` の周期) は、変更しません。

### 遅れを早く知らせる合図

監視対象でない受信者は、次の場合に、周期を待たずに受信報告を送出します (臨時の受信報告)。

| 場合 | 条件 |
| --- | --- |
| 送信者を採用した | 新しい送信者のセッションを採用した時点 |
| 読み出しが遅れている | 受信用のソケットが空にならないまま、「受信バッファーの幅 ÷ 2」個以上の DATA を続けて処理した時点 |

Table: 臨時の受信報告を送出する場合

- 臨時の受信報告の間隔は、`flow_control_request_interval_ms` 以上あけます。
- 臨時の受信報告の形式と、送信者での扱いは、周期の受信報告と同じです。

> [!NOTE]
> 「読み出しが遅れている」の検出は、OS の受信バッファーの中の量を直接知る共通の手段がないため、ソケットが空になったかどうかで代用します。実装の最初に試作で精度を確かめます。遅れていない受信者が頻繁に送出する、または遅れを検出できない場合は、作業を止めて、検出の方法を確認します。

## N 対 1 サーバー (unicast_bidir_n1)

### 幅の配分

サーバーは、受信バッファーの幅を、「送信中のピア」の数で割ります。

- 「送信中のピア」は、直近の `flow_control_request_interval_ms` の間に DATA を受信したピアと、問い合わせを送ってきたピアです。
- ピアごとの幅は、「全体の幅 ÷ 送信中のピアの数 (切り捨て)」です。送信中のピアがない場合は、1 として計算します。
- ピアごとの幅が 4 以上の場合は、送信中のピアの全員に、その幅で許可します。

ピアごとの幅が 4 未満になる場合は、許可を順番に出します。

- 同時に許可を持つピアの数を、「全体の幅 ÷ 4 (切り捨て)」までにします。
- 1 回の許可は 4 パケットです。
- 許可を使い終えたピアが出るたびに、待っているピアのうち、最後に許可を受けてからの時間が最も長いピアへ、次の許可を出します。
- 許可を待っているピアの送出上限は、進めません。待っているピアからの問い合わせには、進めていない送出上限を返します。

順番の許可の間の、許可数と通知は、次のとおりです。

| ピアの状態 | 許可数 |
| --- | --- |
| 許可を持つ (順番の許可を受けて、まだ使い終えていない) | 受けた許可の残り (許可した送出上限と、次に受信する通番の差) |
| 待っている、または送信中でない | 0 (送出上限は、次に受信する通番と同じ値) |

Table: 順番の許可の間の許可数

- 最初の通知、問い合わせへの応答、逆方向の DATA への相乗りは、どのピアにも、この許可数で行います。「待っているピアの送出上限は、進めません」は、相手がすでに送出した範囲を超える許可を出さない、という意味です。
- 未通知のピアが、最初の通知を受ける前に送出する初期の幅の分は、同時に許可を持つピアの数には数えません。順番の許可の間に、最初の通知で許可数 0 を受けたピアは、初期の幅の残りを使えなくなります。
- 受信バッファーの幅の下限 (4 パケット) は、全体の幅に適用します。ピアごとの幅には、適用しません。
- 通常の配分と、順番の許可が切り替わる時点で、すでに知らせた送出上限は、戻しません。知らせた送出上限が、次に受信する通番より先にあるピアは、その分を使い終えるまで、許可を持つピアとして数えます。

> [!NOTE]
> 順番の許可になる送信中のピアの数は、全体の幅で決まります。全体の幅が 42 の場合は 11 以上、約 84 の場合は 22 以上、4 MiB の場合 (全体の幅 約 834) は 209 以上です。

### 全体を妨げている遅いピアの切断

サーバーは、止める状態を続けて、ほかのピアへの送信を妨げているピアを切断します。

「妨げている」とは、ピアが止める状態である間に、次のどちらかが起きたことです。

- 全ピア宛 (`POTR_PEER_ALL`) の送信が、そのピアが止める状態であるために、受け付けられなかった、または待たされた。
- 送信キューが満杯で、そのピア宛のエントリが送信キューに保留されている状態で、送信要求が受け付けられなかった、または待たされた。

サーバーは、妨げが起きた時点から、そのピアが止める状態である時間を積算します (積算の方法は、1 対 N の「止める判定と除外」と同じです)。積算が猶予時間に達したら、そのピアを切断します。

- 同時に止める状態にあるピアの数が、「除外する数の上限」(1 対 N と同じ式。「活動中の受信者数」を「接続中のピア数」と読み替える) を超えている間は、全体が遅い状態として扱います。この間は、積算を進めず、切断しません。
- 切断の手順と、利用側への通知は、ヘルス チェックのタイムアウトによるピアの切断と同じです。そのピア宛の保留中のエントリは破棄します。
- 特定のピア宛の送信だけが待たされている場合 (ほかのピアへの送信を妨げていない場合) は、切断しません。従来どおり、解除まで待ちます。
- 切断は、診断出力 (WARNING) に記録します。
- 切断したピアのセッションからのパケットは、切断から猶予時間の 10 倍の間、受け入れません (応答もしません)。その後は、通常どおり受け入れます。受け入れの後も遅い場合は、同じ手順で、再び切断します。クライアントが、新しいセッションで接続し直した場合は、新しいピアとして扱います。
- 受け入れないセッションの記録は、除外する数の上限の数まで保持し、古いものから消します。

> [!NOTE]
> 切断されたクライアントのハンドルは、接続の再試行を続けます。受け入れない期間を設けないと、遅いままのクライアントが、すぐに再接続して、再び全体を止めます。猶予時間の 10 倍は、1 対 N の除外を解く条件と同じ倍率で、遅いままのクライアントが全体を止める時間を、約 9% までに抑えます。クライアントの性能が回復すれば、次の受け入れで、利用側の操作なしに接続が回復します。切断されていた間のメッセージは、再送しません。
