### 変更前の測定 (2026-11-21、Linux (WSL) の同じホストのループバック、ライブラリは 68a1d71 の時点)

- 受信者 3 つの既定の設定では、欠落と切断が起きます (対策元の BL-006 の再現)。同じ設定でも、起きる実行と起きない実行があります。`flow_control_receiver_count` を 1 にした実行では、起きていません。
- `window_size` を 64 と 256 にした実行でも、既定のしきい値 (2) では欠落と切断が起きました。この測定からは、`window_size` を大きくする効果は確認できていません。変更後の測定で、改めて確かめます。

### 読み出しの遅れの検出の精度 (2026-11-22、Linux (WSL) の同じホストのループバック)

`porter-bench` の `p6` (`multicast`、1,000 byte × 10,000 件) で、検出の回数を測りました。

| 構成 | 診断出力のレベル | 受信者の状態 | 検出の回数 |
| --- | --- | --- | --- |
| 受信者 3、16、32 (受信バッファーの幅 約 84) | 既定 (warning) | 全受信者が全件を受信 | 0 |
| 受信者 16 (受信バッファーの幅 42) | 既定 (warning) | 全受信者が全件を受信 | 0 |
| 受信者 16 (受信バッファーの幅 約 84) | debug | 受信者に欠落あり (最少で 9,196 件) | 2 回の実行の合計で 5,845。受信者 1 つあたりの送出は、1 回の実行で最大 13 |
| 受信者 16 (受信バッファーの幅 42) | debug | 受信者に欠落あり (最少で 8,722 件) | 2 回の実行の合計で 11,477。受信者 1 つあたりの送出は、1 回の実行で最大 15 |

Table: 読み出しの遅れの検出の回数

- 遅れていない受信者 (既定の診断出力のレベル) は、どの構成でも検出しませんでした。
- debug のレベルでは、診断出力の書き込みで受信スレッドの読み出しが実際に遅れ、欠落が起きます。この状態を、遅れている受信者として検出しました。一時的な計測コード (コミットしていない) で、検出の時点の OS の受信バッファーの使用量を調べたところ、中央値が 22%、検出の約 2 割が 50% 以上、最大が 100% でした。
- 検出しても、送出は `flow_control_request_interval_ms` (既定 200 ms) に 1 回までです。
- この結果から、検出の方法は、最終仕様のとおり (ソケットが空になったかどうかで代用する) とします。Windows での判定の精度は、Windows での確認 (4.13) で確かめます。
