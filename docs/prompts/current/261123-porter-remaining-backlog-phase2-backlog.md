## BL-003 小さいメッセージと圧縮送信で処理件数が低下し通知遅延が増える

区分: 過去 backlog からの転記 (`261123-porter-remaining-backlog-backlog.md` の BL-003)  
優先度 / 影響度: 中

### 概要と問題点

- **現状の事象**: ハンドル寿命管理の改修の前に比べて、64 byte、圧縮・4 スレッド、N:1 の返信の条件で、処理件数が下がっています。
    元の条件で戻ったことを示す測定は、ありません。

    転記元にある 2026-11-15 の測定 (5 回の中央値) では、ハンドル寿命管理の改修前の版に比べて、次の条件で処理件数が下がり、通知遅延が増えました。

    - UDP 64 byte・通常・1 スレッド: 処理件数 Windows -34.5%、Linux -23.6%
    - UDP 64 byte・圧縮・4 スレッド: 処理件数 Windows -26.5%、Linux -60.8%。通知遅延の p99 は約 8 倍
    - TCP 圧縮・4 スレッド: 処理件数 Windows -72.3% (64 byte)、-61.4% (5,000 byte)
    - Linux の N:1 返信 (外部スレッド、64 byte): 往復時間 約 1.5 倍、処理件数 -31.3%
- **本来あるべき姿**: 未確定です。
    安全性と公開契約を維持したまま減らせる追加のコストがあるかを特定し、許容するか改善するかを判断する必要があります。

### 経緯と見送り理由

- **摘出契機**: `261123-porter-remaining-backlog-backlog.md` の BL-003 からの転記です。転記元の摘出の契機は次のとおりです。
    `../past/261117-porter-transport-performance-redo-backlog.md` の BL-001 からの転記です。  
    `../past/261115-porter-reject-recovery-backlog.md` の BL-002 からの引き継ぎです。
- **今回の見送り理由**: 継続案件 `261123-porter-remaining-backlog-phase2` で、ユーザーが対策の範囲を BL-010 (UDP で複数のパケットを 1 回の呼び出しで送る) だけにすると決めたためです (簡易 ADR の LADR-001)。
    転記元の案件の計測で分かったことは、「参考情報」に記載しています。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: 非ブロッキング送信の処理件数と通知遅延。
    特に、圧縮を指定した複数スレッドの送信。
- **放置した場合のリスク**: 小さいメッセージを高頻度で送る用途や、圧縮を多用する用途で、改修前より処理能力が下がります。

### 推奨される対応策

- **恒久対応案**: 圧縮・4 スレッドの条件でプロファイルを取り、通知スレッドの起床、通知キューへの受け渡し、圧縮と展開の各段階の時間とロックの競合を測ります。
    主因を特定してから、改善案と安全性への影響を比べます。  
    TCP の条件は、転記元の案件の変更 (`TCP_NODELAY` とまとめ送り) で数値が変わったため、基準を測り直してください。
- **参考情報**: `../past/261115-porter-reject-recovery-backlog.md` の BL-002 (旧案件での調査の経緯を含む)。
    転記元の測定プログラムと結果の保存先は、`C:\Users\tetsuo\AppData\Local\Temp\porter-transport-perf-redo-20261117` です。  
    TCP の基準は、`TCP_NODELAY` とまとめ送りの変更を含めて測り直す必要があります。

    この案件では、1 対 1 の片方向の UDP の送信側で、DATA パケットを送出するたびにヘルス チェックのスレッドを起こす処理を、`prod/libsrc/porter/thread/potr_send_thread.c` の `flush_packed()` から外しました。  
    Linux (WSL)、ループバック、送信スレッド 1 つで、変更の前の版、変更の後の版、`tcp` を交互に 3 回測り、各回 5 測定の中央値の、さらに 3 回の中央値で比較しました。  
    `unicast` の 1,000 byte・送信の指定なしは、85,581 から 147,801 件/秒になりました。  
    64 byte・送信の指定なしは、136,481 と 135,797 件/秒で、変化はありませんでした。  
    `multicast` (`p6`、受信者 3) も同じ起床を行っており、既定の引数で前後を交互に 2 回測った結果は、19,170 と 18,507 件/秒から、87,221 と 93,300 件/秒へ、約 19,000 から約 90,000 件/秒になりました。  
    これらは、この案件の起床を外す変更の前後の比較です。  
    本項目の元の条件である、ハンドル寿命管理の改修の前との比較は、測り直していません。  
    記録は `261123-porter-remaining-backlog-overview.md` の「反映と検証の記録」にあります。

## BL-011 Windows で、Registered I/O の送信だけに使う専用のソケットによる一括の送信が未検討

区分: 作業中摘出  
優先度 / 影響度: 低

### 概要と問題点

- **現状の事象**: Windows の UDP の一括の送信は、`sendto` の繰り返しです。Registered I/O (RIO) のソケット (`WSA_FLAG_REGISTERED_IO` 付き) では、`WSAEventSelect()`、`sendto`、`recvfrom`、`select` が `WSAENOTSOCK` で失敗するため、porter が受信と制御パケットの送信に使うソケットを RIO にできません。
- **本来あるべき姿**: Windows でも、複数のデータグラムを 1 回の起動で送れることが望ましい。RIO の送信だけに使う専用のソケットを、受信用のソケットとは別に作れば、RIO を使える可能性があります。

- **摘出契機**: 継続案件 `261123-porter-remaining-backlog-phase2` の Windows の試作 (2026-11-25) の後に、Windows 側のセッションが代案として示しました (未実施)。
- **今回の見送り理由**: 専用のソケットでは、DATA の送信元のポートが、受信と制御パケットのソケットのポートと分かれます。受信側の相手の識別や、送信元の契約に影響する可能性があり (未確認)、要件の判断が必要です。ユーザーの自走の指示 (決定した最終仕様が実現できない場合は残課題一覧へ送る) に従い、この案件では扱いません。

- **影響対象**: Windows の porter の UDP の送信の処理件数。`app/cplat` の net カテゴリの Windows の実装。
- **放置した場合のリスク**: Windows の UDP の大きいメッセージの送信の処理件数は、変更の前と同じままです。Windows で同じ事象 (1 パケットあたりのカーネルの時間) が起きているかは、測っていません。

- **参考情報**: Windows の試作の結果は、継続案件の全体管理文書 `261123-porter-remaining-backlog-phase2-overview.md` の「反映と検証の記録」にあります。see: https://learn.microsoft.com/en-us/windows/win32/api/mswsock/nc-mswsock-lpfn_riosendex

## BL-014 make test の実行の省略の判定が、テストの実行ファイルの古さを見ず、古い実行ファイルの結果のまま成功と扱うことがある

区分: 作業中摘出  
優先度 / 影響度: 中

### 概要と問題点

- **現状の事象**: `app/porter/test/src/libporter/potrFlowControlTest` で、実行ファイル `bin/potrFlowControlTest` が、テストを足す前の内容で作られたままでした。
    - 実行ファイルの時刻 (2026-11-26 18:53) は、ソース `potrFlowControlTest.cc` の時刻 (18:52) より新しく、`make` は作り直しませんでした。
    - `test.stamp` (19:17) があるため、`make test` は `INFO: Skipping test (dependencies are unchanged and clean)` で実行を省きました。
    - その結果、162 件のまま成功と報告されました。
    - 2026-11-27 にソースの時刻を更新して作り直すと、163 件が登録されました。`make test` は、その後も同じ理由で実行を省きました。
- **推定の原因 (未確認)**: ソースの時刻が、内容の変更を反映していなかったと考えられます (編集の方法による可能性があります)。
    また、省略の判定がソースの状態だけを見ていて、実行ファイルとの対応を確かめていない可能性があります。  
    どちらも推定であり、確かめていません。
- **本来あるべき姿**: 実行ファイルやリンクの入力が最新でない場合に、`make test` が古い実行ファイルの結果のまま成功と扱わず、再ビルドおよび再実行されること。

### 経緯と見送り理由

- **摘出契機**: 継続案件 `261123-porter-remaining-backlog-phase2` において、Windows の検証結果 (163 件) と Linux の記録 (162 件) の差を確認した際 (2026-11-27) に判明しました。
- **今回の見送り理由**: 対策先は `framework/makefw` であり、この案件 (`app/porter` の BL-010 対策) の範囲外のため、残課題一覧へ起票します。
- **継続作業での経緯と対処**: なし。

### 影響範囲とリスク

- **影響対象**: `framework/makefw` を使用する局所テスト (`make test`)。CI はきれいな状態からビルドするため、影響しない見込みです。
- **放置した場合のリスク**: 局所テストで、追加したテストを流さずに成功と判断するおそれがあります。

### 推奨される対応策

- **恒久対応案**: `framework/makefw` の `test.stamp` と `assured.stamp` の判定 (`makefiles` の `test` の規則と `bin_internal` のスクリプト) を調べ、実行ファイルの内容やリンクの入力を判定に含めるかを検討します。対策先は `framework/makefw` です。
- **参考情報**: 継続案件の全体管理文書 `261123-porter-remaining-backlog-phase2-overview.md` の「反映と検証の記録」(作業 WBS 4.5 から 4.10 の訂正注記)。
