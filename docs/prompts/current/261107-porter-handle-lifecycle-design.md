# porter の close 競合安全性とコールバック内送信の改良計画

検討 ID: 261107-porter-handle-lifecycle

最終仕様版: 1

状態: 実装着手承認済み。実装と検証を実施中

## 改良する動作と対応範囲

同一ハンドルの close と他 API が並行実行されても、解放後参照、二重解放、内部ロックの循環待ちを起こさない構成に変更します。  
close 完了後の古いハンドルは、別のサービスを操作せず、無効ハンドル専用のエラーを返します。

ハンドルごとに通知専用スレッドを設け、同一ハンドルのコールバック内から送信とピア切断を行えるようにします。  
送信はブロッキング指定、キュー空き待ち、分割、圧縮、N:1 の受信元・別ピア・全ピアへの送信を含みます。  
同一ハンドルのコールバック内 close は、引き続き `POTR_ERR_UNSUPPORTED` で拒否します。

既存の公開ポインター型と公開関数のシグネチャを維持します。  
正常 close は受付済み API と登録済み通知の完了を待ちます。  
通知領域のメモリ不足時はサービスを異常状態へ移し、専用イベントで通知します。

対象は porter のハンドル管理、通知処理、関連する終了処理とテスト、仕様文書です。  
通信のワイヤー形式、送信の到達保証、通知データの利用側への所有権移転は変更しません。  
性能は改修前後を比較し、劣化率の固定上限を設けず、原因と代替案を添えて受入時に判断します。

> この文書は改良計画です。実装、ビルド、既存仕様の変更は、実装着手の承認後に行います。
> ステージング、コミット、アンステージ、スタッシュ、プッシュは、この計画の承認に含めません。

## 公開ハンドルと通信資源の寿命を分離します

### 公開制御オブジェクトを再利用しません

公開型 `potr_context *` は、通信資源を直接参照するポインターから、軽量な制御オブジェクトを指すハンドルへ変更します。  
通信バッファー、ソケット、ピア表、ワーカー スレッド、通知スレッドと通知領域は内部の通信コンテキストに分離します。  
公開制御オブジェクトは、ライブラリが存続する間保持し、アドレスを再利用しません。

正常 close の成功時に内部通信資源を解放し、制御オブジェクトを CLOSED にします。  
古いハンドルの識別に必要な情報だけを残し、通信データや秘密情報を保持しません。  
これにより、後続 open のアドレス再利用で古いハンドルが新しいサービスを指すことを防ぎます。  
ライブラリのアンロード後まで古いハンドルの有効性を保証するものではありません。

制御オブジェクトの保持量は累計 open 数に比例します。  
この保持は合意した互換性と識別保証のための仕様であり、性能評価で 1 ハンドル当たりの保持量と反復時の増加量を報告します。  
失敗した open で公開されなかった制御オブジェクトは、内部スレッドの停止と参照終了を確認して回収します。

### ハンドルの検証と使用中参照の取得を保護します

公開ハンドルの登録情報は、解放される通信コンテキストの外で管理します。  
未登録の値を通信コンテキストとして逆参照しません。  
登録情報の検索、制御オブジェクトの状態確認、使用中参照の取得を経てから内部通信コンテキストを使用します。

登録情報は全件の線形探索を避ける構成とし、通常の検索が累計 open 数に比例して遅くならないようにします。  
登録情報の保護とハンドル単位の状態保護は短い区間に限定し、通信処理、送信待機、通知、join の間は保持しません。  
保持済み制御オブジェクトの寿命を利用し、登録情報の保護を外した後も制御オブジェクトへ安全に到達できる構成にします。

状態確認と参照取得は、close による受付停止と同じ同期規則で処理します。  
API の正常系と異常系のすべての復帰経路で使用中参照を返却し、最後の参照の返却を close の待機者へ通知します。  
トレース用のサービス ID や設定値の取得も参照取得後に行います。

open は、通知スレッドと異常通知用の予約領域を含む資源の準備に成功した後にハンドルを公開します。  
公開後に open 自身が内部通信コンテキストを使う場合も、close と競合しない使用中参照を保持します。

## 受付状態と異常理由を分けて管理します

| 受付・終了状態 | 新しい send / disconnect | 外部スレッドの close |
| --- | --- | --- |
| OPEN | 使用中参照を取得して処理 | CLOSING へ遷移し、終了処理を担当 |
| CLOSING | `POTR_ERR_CANCELED` | 後続 close は `POTR_ERR_CANCELED`。先行 close を待たない |
| CLOSE_FAILED | 通常操作を拒否 | 残資源の終了処理を再試行 |
| CLOSED | 無効ハンドル専用エラー | 無効ハンドル専用エラー |

Table: 正常系の受付と close の状態

通知領域のメモリ不足は、上記の状態とは別に永続する異常理由として記録します。  
OPEN で異常理由が設定された状態を、サービスの異常状態として扱います。  
異常状態でも close による資源回収を許可します。  
close の進行中にメモリ不足が発生した場合も、終了担当を変更せず、送信待機の異常解除と通知の終了処理へ切り替えます。

CLOSE_FAILED は、スレッド停止などが失敗し、残資源を安全に回収しきれていない状態です。  
OPEN へ戻さず、停止済みのスレッドや破棄済み資源を再処理しないよう、完了した段階を記録します。  
再試行の担当者も 1 人に限定し、その実行中の重複 close は CANCELED で拒否します。

### API の戻り値と追加イベント

| 条件 | 結果 |
| --- | --- |
| NULL ハンドル | `POTR_ERR_INVALID_ARGUMENT` |
| 未登録または CLOSED のハンドル | 新設する `POTR_ERR_INVALID_HANDLE` |
| 正常な close 中の新規 send / disconnect | `POTR_ERR_CANCELED` |
| 通知メモリ不足後の通常操作 | `POTR_ERR_OUT_OF_MEMORY` |
| 同一ハンドルのコールバック内 close | `POTR_ERR_UNSUPPORTED`。終了要求を設定しない |
| コールバック内 disconnect | 通常のピア検証と切断処理を行う。close・異常状態なら上記の拒否を適用 |
| close 中の重複 close | `POTR_ERR_CANCELED` |
| スレッド停止などの終了失敗 | 原因に応じた既存の失敗コード。close の再試行を可能にする |

Table: 改良後のハンドル関連エラー

無効ハンドル専用コードは既存コードの値を変えずに追加します。  
イベントにも既存値を変えずにエラー通知用の種類を追加します。  
専用エラー イベントは、メモリ不足によって通常通知を継続できなくなったことを表し、原因コードをコールバック復帰まで有効な領域で渡します。  
公開ヘッダーではイベント名、引数の型、長さの意味、サービス単位であること、1 回だけ通知することを明記します。

検証順序は、NULL とハンドル登録・有効性の確認、同一コールバック内 close の拒否、操作に適用する異常理由と受付状態、残りの引数検証の順に整理します。  
無効ハンドルを調べるために、そのポインターが指す領域を直接参照しません。  
close 進行中に異常理由が設定された場合、通常操作は異常理由を返し、重複 close は CANCELED を維持します。

## 正常 close は受け付けた操作を進めてから終了します

1. 同一ハンドルのコールバック内からの close を拒否します。
2. 受付状態を CLOSING に変更し、終了処理の担当を確定します。この変更を API 受付順の境界にします。
3. 受付済み API の使用中参照が返却されるまで待ちます。送信完了に必要な I/O スレッドは動作を継続します。
4. 送信キューの登録済みデータの完了を待ち、通信種別に応じた FIN などの終了処理を行います。
5. 受信、接続管理、ヘルス チェック、送信などの通知生成元と通信スレッドを、依存関係を守って停止します。
6. すべての通知生成元と受付済み API が終了した後で通知キューを確定し、登録済み通知を順序どおりすべて実行します。
7. 通知スレッドの終了を待ち、内部通信資源を破棄し、公開制御オブジェクトを CLOSED にします。

通知は終了処理中も通知スレッドで消費し、キューを確定した後に残通知が 0 になるまで待ちます。  
終了処理中に登録された切断や PATH の通知も、登録済み通知として同じ順序で処理します。  
CLOSING 後に通知コールバックが新たに呼び出した send や disconnect は、受付済みの操作に追加せず、CANCELED で拒否します。

UDP では、受信スレッドが参照する送信ウィンドウ用ロックなどを受信終了前に破棄しない現行の依存関係を維持します。  
TCP では、接続管理スレッドが管理する送受信スレッドの停止を含め、送信の進行が必要な段階で先に停止しないように組み替えます。  
通信種別ごとの停止段階をコードとテストで明示し、共通の受付・寿命管理と分離します。

close の成功復帰後には、当該ハンドルのコールバックと内部通信処理が実行されません。  
close の所要時間には、受付済み送信と通知の処理時間、利用者コールバックの処理時間が含まれます。  
利用者のコールバック自身が復帰しない場合まで、close の有限時間での復帰を保証しません。

## 通知を状態保護ロックの外で実行します

### 通知専用スレッドでハンドル単位に直列実行します

受信や内部状態の変更を行うスレッドは、通知内容を確定してキューへ引き渡します。  
利用者のコールバックは通知専用スレッドだけが実行し、同じハンドルでは同時に実行しません。  
異なるハンドルの通知スレッドは独立して動作します。

受信 DATA、PATH 状態配列、peer_id、接続・切断イベントは、通知の登録時点で内容を確定します。  
状態変更と通知登録の順序をそろえ、状態変更したスレッドがロックを外してから順序を逆転させないようにします。  
ピア切断後でも、登録済み通知は登録時点のデータと識別子を使用します。  
通知コールバック中の send は通知時点の接続を保証するものではなく、呼び出し時点の通常の接続・ピア検証に従います。

### 受信領域とピア領域の寿命を通知から切り離します

コールバックへ渡すデータは、コールバックが復帰するまで通知側が保持します。  
受信スレッドの展開領域、再構成領域、スタック上の PATH 配列、解放可能なピア構造体のポインターを、そのまま非同期通知へ渡しません。  
必要なデータのコピーまたは所有権の内部移動で寿命を保証し、利用側のデータ寿命契約は維持します。

ピア情報は通知に必要な値を確定し、通知後の処理がピアポインターを使用する場合は、寿命の保護または識別子での再検索を行います。  
ロックを外した後に既存のピアポインターをそのまま再使用しないことを、すべての通知生成箇所で確認します。

### コールバック内 disconnect は通知を再入実行しません

コールバック内の peer_disconnect は、ピアの検証、必要な FIN、状態変更と資源管理を行います。  
切断や PATH の通知は現在の通知コールバックの後へ登録し、同じコールバックを同期的に再入実行しません。  
disconnect の復帰は切断操作の結果を表し、切断通知コールバックの完了待ちは行いません。  
コールバック外の disconnect も同じ通知経路を使います。

## 通知キューを動的に拡張し、I/O の空き待ちをなくします

通知キューは負荷に応じて領域を拡張し、通知ノードとデータ領域を可能な範囲で再利用します。  
通知ごとの確保回数、コピー量、消費後に保持するメモリ量を測定し、通常時の追加コストを抑えます。  
メモリ使用量の固定上限は設けず、保持量が増える条件を API 文書に記載します。

通知キューが満杯という理由で I/O スレッドを空き待ちさせません。  
通知の登録と取り出しを保護する短いロックは使用しますが、コールバック実行や送信待機の間は通知キューのロックを保持しません。  
長時間のコールバック実行中も、TCP の受信や制御パケットの処理など、送信完了に必要な処理を継続します。

### 通知領域の確保失敗はサービス異常として通知します

1. 最初の通知領域確保失敗で、メモリ不足の異常理由と通知受付停止を確定します。並行する複数の失敗でも異常通知は 1 回だけ予約します。
2. 新しい通信と通常 API 操作を拒否し、キュー空き待ちや送信チケット待ちを OUT_OF_MEMORY で解除します。
3. 先に登録できた通知を順序どおり実行し、その後に専用エラー イベントを通知します。
4. 以後の通常通知を登録せず、close による終了と資源回収を可能にします。

専用エラー イベント用のノードと原因情報の領域は open 時に予約します。  
予約に失敗した open は、公開前に資源を回収して失敗を返します。  
異常通知の登録、原因情報の保持、待機者への起床は、追加のメモリ確保に依存させません。  
予約ノードは通常ノードの個別回収処理から区別し、通知完了後の内部通信資源の破棄時に回収します。

異常時は送信を完了したことにせず、正常 close の drain をそのまま待ち続けない構成にします。  
途中まで登録した断片や送信済みデータを取り消したとは扱いません。  
通知専用スレッドは先行通知と異常通知を処理できるよう維持し、通信スレッドは共有資源を破棄せずに停止へ進めます。  
同時に外部 close が進行している場合も、同じ通知終了と資源回収の処理へ合流させます。

## ロック順序と待機の規則

| 保護対象 | 保護する処理 | 保持したまま行わない処理 |
| --- | --- | --- |
| 公開ハンドルの登録情報 | 登録と検索 | 通信、通知、join |
| ハンドルの受付状態と使用中参照 | 状態変更、参照取得・返却、終了担当の確定 | API 本体、コールバック、送信完了待ち、join |
| ピア表と通信状態 | 状態変更と通知内容の確定 | 利用者コールバック、通知領域の空き待ち |
| 通知キュー | 通知登録と取り出し | コールバック、send、disconnect、join |
| 送信キューと送信完了状態 | 断片登録、進捗と異常理由の確認 | 利用者コールバック |

Table: 保護区間と待機の制約

ピア表などの状態ロックから通知キューのロックを取得する順序は許容し、通知キューから状態ロックを取得する逆順を作りません。  
通知スレッドは、通知を取り出してキューのロックを外してからコールバックを実行します。  
コールバック内 API も通常の受付処理を通し、内部状態ロックを取得していない状態で実行します。  
受付状態の保護ロックからピア表や送信・通知キューのロックを取得する入れ子を作りません。  
異常理由の確定と待機者の起床も、状態の更新後に保護ロックを外して行い、ロックの逆順取得を防ぎます。  
異常理由の確定、通常通知の受付停止、予約エラー イベントの位置の確定は、通知登録と競合して順序が逆転しないように同期させます。

条件変数の待機では保護ロックを解放し、起床後に完了条件または異常理由を再確認します。  
異常状態への遷移時は、not_full、progress、drained など各待機条件に対応する通知を行います。  
push_mutex を待っていた送信も取得後に異常理由を再確認し、追加の断片登録を行いません。  
通知スレッドと API の使用中参照が必要とするスレッドを、終了待ちの前に停止しないようにします。

## 実施順序と各段階の完了条件

1. 改修前の porter の局所試験と性能を記録します。既存の失敗は変更起因の結果と区別します。
2. 公開制御オブジェクトと内部通信コンテキストを分離し、ハンドル検証と使用中参照を導入します。open 失敗、古いハンドル、参照の全復帰経路を局所試験で確認します。
3. 通知キューと専用スレッドを導入し、すべての通知生成経路を移行します。直列性、順序、データ寿命、ピア寿命を確認します。
4. コールバック内の send と disconnect に対応し、送信拒否判定と同期通知経路を変更します。キュー満杯とブロッキング送信で I/O の進行を確認します。
5. 正常 close、重複 close、close 失敗後の再試行を実装します。受付境界を固定した競合試験と、通信種別ごとの停止順序を確認します。
6. 通知メモリ不足時の異常状態、予約済みエラー通知、待機解除を実装します。close との競合と回収を確認します。
7. 恒久仕様と公開ヘッダーを更新し、局所試験と改修後の性能比較を行います。変更起因の失敗を修正し、影響範囲だけ再検証します。
8. 受入条件を照合し、未対応の残課題があれば記録・整理して結果を提示します。

各段階では対応する単体テストを同時に更新します。  
実装途中で計画の前提を変える必要が生じた場合は、その箇所の変更を中断して追加検討します。  
各 OS の局所検証を行い、内容のある `.warn` を確認します。  
framework や複数 app にまたがる全体テストは、コストを説明して別途確認します。

## 競合と再入送信の試験計画

| 試験群 | 主な確認 |
| --- | --- |
| ハンドル管理 | 参照取得と受付停止の競合、全復帰経路の参照返却、未登録・NULL・CLOSED、open 失敗、累計 open 後の古いハンドル |
| 正常 close | 受付済み API の完了待ち、後続 API の拒否、重複 close、正常 drain と FIN、通知完了後の復帰 |
| close 再試行 | 停止失敗時に生存資源を破棄しないこと、完了済み段階の二重処理をしないこと、再試行の担当が 1 人であること |
| コールバック内 API | N:1 の受信元・別ピア・全ピアへの送信、分割・圧縮・ブロッキング、disconnect、close の拒否 |
| 通知 | DATA、PATH、接続・切断の順序、単一ハンドルの非並行実行、別ハンドルの独立性、受信領域とピア解放からの独立 |
| キュー負荷 | コールバックが送信待機中の通知増加とキュー拡張、送信キュー満杯、通常通知による I/O 空き待ちがないこと |
| メモリ不足 | 通知ノード・データ領域の確保失敗、予約領域による 1 回のエラー通知、先行通知の維持、通常操作の拒否、送信待機の異常解除 |
| 終了と異常の競合 | 正常 close の待機中のメモリ不足、コールバック内送信待機中の異常、異常通知前後の外部 close、資源の二重解放防止 |

Table: 局所試験と結合試験の確認範囲

競合試験はバリアなどで、API 受付、CLOSING 遷移、参照返却、資源破棄の順序を固定します。  
単なる時間待ちで競合が発生することを期待する試験だけにしません。  
通知メモリ不足は確保失敗の注入で再現し、既存の送信圧縮用メモリ不足と区別します。  
UDP、TCP、RAW の適用される経路で実スレッドの結合試験を行い、複数パスと N:1 の差も確認します。  
Linux/GCC と Windows/MSVC の両方を検証対象とし、未実施環境は確認済みの結果と分けて報告します。

既存の `potrServiceOpenTest`、`potrServiceCloseTest`、`potr_service_send_test`、`potr_peer_disconnect_test`、`potrPathEventTest`、`potrSendQueueTest`、`potrSendThreadTest` と結合試験を更新します。  
新設する内部部品には、その責務の競合と失敗条件を確認する単体テストを追加します。  
テスト作成時は testfw の配置とエビデンスの規範を適用します。

## 性能の測定条件と評価

同じマシン、OS、ビルド設定、通信設定、データ、実行回数で改修前後を比較します。  
起動と終了の時間を通常送信の測定と分け、ウォーム アップと測定のばらつきを記録します。

| 条件 | 比較するもの |
| --- | --- |
| 小メッセージ、単一スレッド | ハンドル検証、参照取得・返却、通知登録の追加コスト |
| 大メッセージ、分割、圧縮の有無 | コピー量、メモリ確保回数、CPU、スループット |
| 同一ハンドルの並行送信 | ロック待ち、API 遅延、送信順序、スループット |
| 複数ハンドル | 登録情報の保護による干渉とハンドル単位の独立性 |
| N:1 の返信 | 改修後のコールバック内返信と、外部スレッドからの返信の比較 |
| 低速コールバックと通知増加 | 通知遅延、ピーク メモリ、消費後の保持量、確保とコピー |
| open/close 反復 | 通信資源の回収量、制御オブジェクトの保持量、終了時間 |

Table: 性能比較の負荷条件

測定項目はスループット、API と通知の遅延の中央値・p95・p99、CPU 使用量、メモリ確保回数、コピー量、ピークと保持メモリ、close の所要時間です。  
比較が成立しない新機能は、既存の外部返信経路との比較と絶対値を分けて報告します。

通常送信への毎回の追加確保、登録情報の線形探索、全ハンドル共通の長時間ロックを避けます。  
通知ノードの再利用と必要な範囲のデータ保持で、確保とコピーを抑えます。  
専用スレッドの起床とコンテキスト切り替え、同一ハンドルの参照数更新による競合を測定し、劣化の主因を特定します。

劣化率だけで合否を自動判定しません。  
安全性と公開契約を維持した代替案、追加コストの原因、改善可能性を示し、結果を受入時に判断します。

## 文書と検証の完了条件

- close と send・disconnect・close の競合で、解放後参照、二重解放、内部の循環待ちを起こさないこと。
- close 前の受付済み操作を完了させ、受付停止後の新しい操作を拒否すること。異常停止時は待機を失敗で解除すること。
- close 完了後の古いハンドルが専用エラーとなり、open/close 反復後も新しい接続へ作用しないこと。
- コールバック内送信が既存の待機動作を維持し、同一ハンドルの disconnect を許可し、close の拒否を維持すること。
- 登録済み通知の順序、非並行実行、データ寿命を維持し、close 成功復帰後に通知しないこと。
- 通知領域の確保失敗時に通常操作を停止し、追加確保なしで先行通知の後に 1 回の異常通知を行い、close で回収できること。
- 終了失敗後の再試行で、生存中のスレッドの資源を破棄せず、完了済み資源を二重に破棄しないこと。
- Windows と Linux の対象局所試験が成功し、対象範囲の `.warn` に変更起因の新しい警告が残らないこと。環境不足は未確認として提示すること。
- 公開 API、機能仕様、内部設計、テストが整合し、公開シグネチャと既存エクスポートを維持すること。
- 性能比較結果と追加コスト、制御オブジェクトと通知キューの保持メモリを提示していること。
- 変更 Markdown の整形を確認し、機能仕様の変更時は `python3 app/general/bin/check_functional_spec.py` による確認を行うこと。

実装中の見送り事項や追加の気付きは、その時点で残課題文書へ記録します。  
受入前に解消済み事項と合意した制約を除いて整理し、未対策の残課題だけを提示します。  
計画作成時点では実装と性能測定は未実施であり、上記を達成済みとは扱いません。
