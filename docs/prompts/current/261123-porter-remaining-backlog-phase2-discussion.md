### Q-003 BL-010 を適用する通信種別と経路の範囲

**Status**

未回答

**Question**

BL-010 (UDP で複数のパケットを 1 回の呼び出しで送る) を、どの範囲の送出に適用しますか。([Q-001](#q-001-この案件で対策する残課題の範囲) で BL-010 を選ばない場合は、回答は不要です。)

**Context**

- **経緯と背景**: porter の送信スレッドの UDP の DATA の送出は、2 つの関数に分かれています。
    - `flush_packed()` (`prod/libsrc/porter/thread/potr_send_thread.c`): 1 対 1 の通信種別 (`unicast`、`unicast_bidir`、`multicast`、`broadcast`) が使います。経路 (最大 `POTR_MAX_PATH`) ごとに封緘 (暗号化を指定した場合は暗号化) して `cplat_socket_sendto()` を呼びます。`unicast_bidir` では、逆方向の DATA に送出上限を相乗りさせます。
    - `flush_packed_peer()`: N 対 1 (`unicast_bidir_n1`) が使います。ピアごとの送信ウィンドウ、ピアごとの送出の保留があります。
- **確認した事実**: 前の案件の試作と測定は、経路 1 つ、暗号化なしの `unicast` だけです。効果は、待ち合わせを指定した 5,000 byte で確認し、1,000 byte と、送信の指定なしでは、はっきりした効果は見えませんでした。前の案件で起床を外した後の `multicast` (受信者 3) と N 対 1 が、一括の送信でさらに速くなるかは、測っていません。
- **各案の違い**:

```text
案 A: 経路が 1 つで、暗号化なしの unicast だけを一括にする
  - 試作と同じ条件で、効果は確認済み。
  - flush_packed() の中に「一括にできる条件」の分岐が残り、
    暗号化あり・複数経路・ほかの通信種別は、従来の 1 個ずつの送出のままになる。
```

```text
案 B (推奨): flush_packed() を通る送出の全体を一括にする
  - unicast、unicast_bidir、multicast、broadcast。暗号化あり、複数経路を含む。
  - 1 対 1 の UDP の DATA の送出が 1 つの方式にそろう。
  - 封緘の結果を置くバッファーを、まとめる個数ぶん用意する変更と、
    送出上限の相乗り、経路ごとの成功の記録の設計と単体テストが増える。
  - N 対 1 (flush_packed_peer()) は従来のままで、残課題一覧に残す。
```

```text
案 C: N 対 1 も含めて、UDP の DATA の送出のすべてを一括にする
  - ピアごとの送信ウィンドウと保留の順序の設計が加わり、案 B より大きく増える。
  - N 対 1 の返信は小さいメッセージが中心で、効果の見込みを示す測定がない。
```

**Answer**

選択方式: 単一選択

- [ ] A: 経路が 1 つで、暗号化なしの `unicast` だけ
- [ ] B: (推奨) `flush_packed()` を通る送出の全体 (1 対 1 の 4 つの通信種別。暗号化と複数経路を含む)。N 対 1 は残課題に残す
- [ ] C: N 対 1 も含める
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: B  
優先した基準: 送出の方式を 1 つにそろえること (設計の一貫性) を、変更量の抑制より優先。  
理由: 案 A は、同じ関数の中に 2 つの送出の方式が残り、暗号化や複数経路を使う利用者には効果が届きません。案 B は、関数の単位で方式がそろい、単体テストも 1 つの方式に対して書けます。案 C の N 対 1 は、設計の論点が別 (ピアごとの順序) で、効果の根拠となる測定がないため、分けることを推奨します。案 B では、試作にない条件 (暗号化、複数経路、`multicast`) の性能の測定を、受入の確認に加えます。

**Related**

[Q-001](#q-001-この案件で対策する残課題の範囲)、[Q-005](#q-005-bl-010-の性能の受入の基準)

### Q-004 BL-010 の Windows での実装の方式

**Status**

未回答

**Question**

`app/cplat` に追加する「複数のデータグラムを 1 回で送る関数」の Windows の実装を、どの方式にしますか。([Q-001](#q-001-この案件で対策する残課題の範囲) で BL-010 を選ばない場合は、回答は不要です。)

**Context**

- **経緯と背景**: Linux には、複数のデータグラムを 1 回のシステム コールで送る `sendmmsg()` があります。Windows には、同じ形の同期の関数がありません。`WSASendMsg()` は、複数のバッファーを 1 つのデータグラムにまとめて送る関数で、複数のデータグラムは送れません。Registered I/O (`RIOSendEx()`) は、複数の送信の要求をまとめて起動できますが、バッファーの事前の登録、要求と完了のキュー、非同期の完了の処理が必要です。
- **各案の違い**:
    - A は、関数の契約 (何個送れたかを返す) を両方の OS で同じにし、Windows では、中で `sendto()` を 1 個ずつ呼びます。Windows の処理件数は変わりません。
    - B は、Windows でも呼び出しの回数を減らします。cplat のソケットの作りと、porter のバッファーの寿命の設計まで変更が広がります。Windows の測定の環境が必要です ([Q-002](#q-002-windows-での確認の方法))。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) `sendto()` を 1 個ずつ繰り返す (Windows の性能は変えない)
- [ ] B: Registered I/O などで、Windows でも一括の送信にする
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 変更量の抑制と、確認できる環境の範囲に収めること。  
理由: BL-010 の事象 (カーネルの時間が 1 パケットあたり約 32 µs) は、Linux (WSL) のループバックで測ったものです。Windows で同じ事象が起きているかは、測っていません。根拠のない Windows の最適化のために、非同期の完了の処理を持ち込むことは、推奨しません。

[Q-001](#q-001-この案件で対策する残課題の範囲)、[Q-002](#q-002-windows-での確認の方法)

### Q-005 BL-010 の性能の受入の基準

**Status**

未回答

**Question**

BL-010 の対策の完了を判定する性能の基準を、何にしますか。([Q-001](#q-001-この案件で対策する残課題の範囲) で BL-010 を選ばない場合は、回答は不要です。)

**Context**

- **経緯と背景**: 前の案件は、`porter-bench` の `unicast` (`p1`) の処理件数を、同じ条件の `tcp` (`p5`) で割った比が 0.5 以上であることを基準にしました。6 条件のうち、待ち合わせを指定した 5,000 byte だけが、0.47 から 0.48 で基準に届きませんでした。
- **前の案件の最終の測定 (Linux (WSL)、ループバック、送信スレッド 1 つ、`unicast` ÷ `tcp`)**:

| メッセージ | 送信の指定なし | 待ち合わせを指定 |
| --- | --- | --- |
| 64 byte | 1.03 | 1.06 |
| 1,000 byte | 1.20 | 1.09 |
| 5,000 byte | 0.62 | 0.47 |

- **各案の違い**:
    - A は、前の案件と同じ基準です。試作の値 (0.81 から 0.97) は、ほかの試験と同時に測った参考の値のため、保証する値にはしません。
    - B は、試作の値に近い基準です。製品の実装 (一部だけ送れた場合の扱い、暗号化など) で試作より遅くなった場合に、基準に届かないおそれがあります。
    - C は、基準を、変更の前の測り直しの後に決めます。基準を決める確認が、もう 1 回必要です。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 待ち合わせを指定した 5,000 byte の比が 0.5 以上。かつ、ほかの 5 条件の比が、変更の前の測り直しの値より悪くならない (測定の変動の幅を超えて下がらない)
- [ ] B: 待ち合わせを指定した 5,000 byte の比が 0.8 以上。かつ、ほかの 5 条件が悪くならない
- [ ] C: 変更の前を測り直した後に、基準を決める
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 残課題一覧の「本来あるべき姿」(比が 0.5 以上) との一致。  
理由: BL-010 の「本来あるべき姿」は、「同じ条件の `tcp` に対して、数倍の劣化になっていないこと (比が 0.5 以上)」です。この基準を満たせば、残課題は解消したと判定できます。実際の値は、基準とは別に、すべて記録して報告します。[Q-003](#q-003-bl-010-を適用する通信種別と経路の範囲) で案 B または案 C を選んだ場合は、追加した範囲 (暗号化、複数経路、`multicast` など) について、「変更の前より悪くならない」ことを確認に加えます。

### Q-006 一括の送信で、一部だけ送れた場合の残りの扱い

**Status**

未回答

**Question**

一括の送信が、渡したパケットの先頭の一部だけを送って戻った場合に、残りのパケットをどう扱いますか。([Q-001](#q-001-この案件で対策する残課題の範囲) で BL-010 を選ばない場合は、回答は不要です。)

**Context**

- **経緯と背景**: `sendmmsg()` は、送れたデータグラムの個数を返します。途中のデータグラムで失敗すると、そこで止まり、先頭から送れた個数だけを返します。この場合、失敗の理由 (エラーの番号) は、呼び出し元へ返りません。
- **現在の動作 (1 個ずつの送出)**: `flush_packed()` は、`cplat_socket_sendto()` が失敗しても、そのパケットを送信ウィンドウへ登録し、送信の完了として扱います。受信側が欠落を検出して再送を要求すると、送信ウィンドウから再送します。つまり、現在も「送出を 1 回試みたパケットは、成否によらず、再送の仕組みに任せる」動作です。
- **各案の違い**:

```text
案 A (推奨): 残りを、従来の 1 個ずつの送出 (sendto) で、順に 1 回ずつ試みる
  - どのパケットも「送出を 1 回試みる」という現在の意味を保つ。
  - 失敗の理由も、1 個ずつの送出の戻り値で分かる。
```

```text
案 B: 残りを、もう一度、一括の送信で送る (回数の上限つき)
  - 一時的な失敗 (送信バッファーの満杯など) からの回復が早い可能性がある。
  - 回数の上限と、上限に達した後の扱いを、新しく決める必要がある。
```

```text
案 C: 残りは送出を試みずに、送信ウィンドウへ登録して、再送の仕組みに任せる
  - 処理は最も単純。
  - 送出を 1 回も試みないパケットができ、受信側の再送の要求を待つぶん、届くのが遅れる。
```

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 残りを、1 個ずつの送出で順に 1 回ずつ試みる
- [ ] B: 残りを、一括の送信で再び送る (回数の上限つき)
- [ ] C: 残りは送出を試みずに、再送の仕組みに任せる
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 現在の動作の意味を変えないこと。  
理由: 案 A は、一括の送信を使わない場合と、パケットごとの結果が同じになります。再送、フロー制御、送信の完了の通知の契約を変えずに済み、単体テストも「一括の送信の結果が、1 個ずつの送出と同じになること」として書けます。
