### Q-003 BL-010 を適用する通信種別と経路の範囲

**Status**

解決済み

**Question**

BL-010 (UDP で複数のパケットを 1 回の呼び出しで送る) を、どの範囲の送出に適用しますか。([Q-001](#q-001-この案件で対策する残課題の範囲) で BL-010 を選ばない場合は、回答は不要です。)

**Context**

- **経緯と背景**: porter の送信スレッドの UDP の DATA の送出は、2 つの関数に分かれています。
    - `flush_packed()` (`prod/libsrc/porter/thread/potr_send_thread.c`): 1 対 1 の通信種別 (`unicast`、`unicast_bidir`、`multicast`、`broadcast`) が使います。経路 (最大 `POTR_MAX_PATH`) ごとに封緘 (暗号化を指定した場合は暗号化) して `cplat_socket_sendto()` を呼びます。`unicast_bidir` では、逆方向の DATA に送出上限を相乗りさせます。
    - `flush_packed_peer()`: N 対 1 (`unicast_bidir_n1`) が使います。ピアごとの送信ウィンドウ、ピアごとの送出の保留があります。
- **確認した事実**: 前の案件の試作と測定は、経路 1 つ、暗号化なしの `unicast` だけです。効果は、待ち合わせを指定した 5,000 byte で確認し、1,000 byte と、送信の指定なしでは、はっきりした効果は見えませんでした。前の案件で起床を外した後の `multicast` (受信者 3) と N 対 1 が、一括の送信でさらに速くなるかは、測っていません。
- **各案の違い**:

```text
案 A: 経路が 1 つで、暗号化なしの unicast だけを一括にする
  - 試作と同じ条件で、効果は確認済み。
  - flush_packed() の中に「一括にできる条件」の分岐が残り、
    暗号化あり・複数経路・ほかの通信種別は、従来の 1 個ずつの送出のままになる。
```

```text
案 B (推奨): flush_packed() を通る送出の全体を一括にする
  - unicast、unicast_bidir、multicast、broadcast。暗号化あり、複数経路を含む。
  - 1 対 1 の UDP の DATA の送出が 1 つの方式にそろう。
  - 封緘の結果を置くバッファーを、まとめる個数ぶん用意する変更と、
    送出上限の相乗り、経路ごとの成功の記録の設計と単体テストが増える。
  - N 対 1 (flush_packed_peer()) は従来のままで、残課題一覧に残す。
```

```text
案 C: N 対 1 も含めて、UDP の DATA の送出のすべてを一括にする
  - ピアごとの送信ウィンドウと保留の順序の設計が加わり、案 B より大きく増える。
  - N 対 1 の返信は小さいメッセージが中心で、効果の見込みを示す測定がない。
```

**Answer**

選択方式: 単一選択

- [ ] A: 経路が 1 つで、暗号化なしの `unicast` だけ
- [ ] B: (推奨) `flush_packed()` を通る送出の全体 (1 対 1 の 4 つの通信種別。暗号化と複数経路を含む)。N 対 1 は残課題に残す
- [x] C: N 対 1 も含める
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

**Recommendation**

推奨: B  
優先した基準: 送出の方式を 1 つにそろえること (設計の一貫性) を、変更量の抑制より優先。  
理由: 案 A は、同じ関数の中に 2 つの送出の方式が残り、暗号化や複数経路を使う利用者には効果が届きません。案 B は、関数の単位で方式がそろい、単体テストも 1 つの方式に対して書けます。案 C の N 対 1 は、設計の論点が別 (ピアごとの順序) で、効果の根拠となる測定がないため、分けることを推奨します。案 B では、試作にない条件 (暗号化、複数経路、`multicast`) の性能の測定を、受入の確認に加えます。

**Related**

[Q-001](#q-001-この案件で対策する残課題の範囲)、[Q-005](#q-005-bl-010-の性能の受入の基準)、[Q-014](#q-014-n-対-1-で一括の送信にまとめる単位)

**Assessment**

C (N 対 1 も含める) を選択。推奨 (B) と異なります。補足はありません。

- 適用の範囲は、`flush_packed()` を通る 1 対 1 の 4 つの通信種別 (`unicast`、`unicast_bidir`、`multicast`、`broadcast`。暗号化と複数経路を含む) と、`flush_packed_peer()` を通る N 対 1 (`unicast_bidir_n1`) の、UDP の DATA の送出のすべてです。TCP は、すでにまとめ送り (`send_tcp_batch()`) があり、対象外です。
- **範囲が広がる影響 (ソースで確認)**: N 対 1 の送信スレッドは、`pop_peer_mode()` で取り出したエントリを、`defer_entry_if_blocked()` で送出上限による保留を判定してから、`send_packed_peer_mode()` で送ります。`send_packed_peer_mode()` は、同じピア宛ての後続の単体エントリだけを 1 つの外側パケットへ詰め、`peers_mutex` を持ったまま、そのピアの `send_window_mutex` の下で封緘と送出を行います。分割されたメッセージの断片 (`POTR_FLAG_MORE_FRAG`) は、断片ごとに 1 回の周回で送ります。一括の送信を N 対 1 に入れるには、まとめる単位 (同じピア宛てに限るか、複数のピア宛てをまとめるか) を決める必要があります。[Q-014](#q-014-n-対-1-で一括の送信にまとめる単位) で確認します。
- N 対 1 の効果の見込みを示す測定はありません。受入の基準は、[Q-005](#q-005-bl-010-の性能の受入の基準) の推奨の注記のとおり、N 対 1 (`porter-bench` の `p2`、`p7`) について「変更の前より悪くならない」ことを確認に加えます。
- 範囲そのもの (この Q の判断対象) は、解決済みとします。

      see: https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-udp-socket-options

### Q-014 N 対 1 で一括の送信にまとめる単位

**Status**

解決済み

**Question**

N 対 1 (`unicast_bidir_n1`) の送出で、1 回の一括の送信にまとめる外側パケットの範囲を、どうしますか。

**Context**

- **経緯と背景**: [Q-003](#q-003-bl-010-を適用する通信種別と経路の範囲) の回答 (C) で、N 対 1 も一括の送信の対象になりました。
- **現状のコード** (`prod/libsrc/porter/thread/potr_send_thread.c`): 送信スレッドは、`pop_peer_mode()` で 1 エントリを取り出し、`defer_entry_if_blocked()` で宛先のピアが送出上限で止まっていれば保留し、そうでなければ `send_packed_peer_mode()` で送ります。`send_packed_peer_mode()` は、同じピア宛ての後続の単体エントリだけを 1 つの外側パケットへ詰め、`peers_mutex` を持ったまま、そのピアの `send_window_mutex` の下で、通番の付与、封緘、送出、送信ウィンドウへの登録を行います。ピアは、受信スレッド、ヘルス チェックのスレッド、`potr_peer_disconnect()` で解放される場合があり、ロックの外でピアのポインターを使いません。
- **各案の違い**:

```text
案 A (推奨): 同じピア宛てに続く外側パケットだけをまとめる
  - 分割されたメッセージの断片 (5,000 byte は 4 パケット) と、同じピアへの連続した送信が 1 回になる。
  - 1 回の一括の送信は、1 つのピアの send_window_mutex の下で完結し、ロックの順序は今と同じ。
  - 別のピア宛てのエントリが来た時点で、集めた分を送る。
```

```text
案 B: 複数のピア宛てを、1 回の一括の送信にまとめる
  - 小さい返信を多数のピアへ送る場合も、呼び出しの回数が減る。
  - 複数のピアの send_window_mutex を同時に持つか、ピアごとに通番の付与と封緘を済ませてから、
    ロックを外して送る設計が必要になる。ピアの解放との競合と、ピアごとの保留 (送出上限) との順序の設計が加わる。
  - 効果の見込みを示す測定はない。
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 同じピア宛てに続く外側パケットだけをまとめる
- [ ] B: 複数のピア宛てを 1 回にまとめる
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-25 20:59:35 JST

**Recommendation**

推奨: A  
優先した基準: ピアの寿命とロックの順序の、既存の安全性の設計を変えないこと。  
理由: BL-010 の事象は、1 つのメッセージが複数のパケットに分かれる場合の送出の回数で、案 A で N 対 1 にも同じ効果が届きます。案 B は、ピアの解放との競合という、過去の案件で SIGSEGV の調査の対象になった領域の設計を変えます。効果の根拠となる測定もないため、推奨しません。

**Related**

[Q-003](#q-003-bl-010-を適用する通信種別と経路の範囲)

**Assessment**

A を選択。推奨と同じです。補足はなく、矛盾はありません。N 対 1 では、同じピア宛てに続く外側パケットだけを 1 回の一括の送信にまとめ、別のピア宛てのエントリが来た時点で集めた分を送ります。1 回の一括の送信は、1 つのピアの `send_window_mutex` の下で完結し、ロックの順序 (`peers_mutex` → `peer->send_window_mutex` → `fc->mutex`) は変えません。
