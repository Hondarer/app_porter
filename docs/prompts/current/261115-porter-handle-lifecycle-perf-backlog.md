## BL-001 TCP の送信ソケットに TCP_NODELAY がなく約 40[ms] の停止が生じる

### 概要と問題点

- **現状の事象**: porter と cplat は、TCP ソケットに TCP_NODELAY を設定していません。Linux (WSL2) のループバックで、DATA と FIN が受信側へ届くまでに約 40[ms] かかる場合があります。Nagle アルゴリズムと遅延 ACK が重なった待ちと一致します。現行版の close は相手の FIN_ACK を待つため、Linux の TCP の close は毎回約 43[ms] かかりました (P4)。Linux の P5 では、ブロッキング送信と 4 スレッドの多くの条件で、通知遅延 p99 が約 42〜44[ms] でした。
- **本来あるべき姿**: 未確定です。小さいメッセージの遅延を優先して TCP_NODELAY を設定するか、送信をまとめる現状を維持するかを、利用条件に基づいて決める必要があります。

### 経緯と見送り理由

- **摘出契機**: 本案件の Linux での試行 (P4 と P5 の TCP) の調査で見つかりました (2026-11-15)。
- **今回の見送り理由**: 改修前版と現行版に共通の既存の挙動で、ハンドル寿命管理の改修による差ではないためです。本案件の目的は性能評価です。

### 影響範囲とリスク

- **影響対象**: TCP の通信種別 (POTR_TYPE_TCP、POTR_TYPE_TCP_BIDIR) の送達遅延と close の所要時間。
- **放置した場合のリスク**: 低頻度の小さいメッセージや close で、数十 [ms] の遅れが生じます。

### 推奨される対応策

- **恒久対応案**: TCP_NODELAY の採否を、遅延と送信効率の要求から判断します。採用する場合は、ソケットの作成箇所 (cplat または porter の TCP 接続の確立処理) で設定し、P4 と P5 を両 OS で測り直して効果を確認します。
- **参考情報**: 検証記録の「TCP 終了時エラーの切り分けと修正」「open/close 反復 (P4)」。

### 経緯と対処の更新

- 2026-11-15: 継続案件 `porter-reject-recovery` では対策せず、[261115-porter-reject-recovery-backlog.md](261115-porter-reject-recovery-backlog.md) の BL-001 へ転記しました。

## BL-002 UDP の受信ウィンドウが回復不能な欠落の後に進まなくなる

### 概要と問題点

- **現状の事象**: 受信コールバックを 1 件ごとに 1[ms] 待たせ、5000 バイトを間隔なしで送る負荷 (P3) で、受信側が「REJECT received (packet unrecoverable)」を記録した後、受信ウィンドウの基準通番が進まなくなりました。その後のパケットは「recv_window full (100%), dropping」ですべて破棄され、測定区間の 10000 件が 1 件も届きませんでした。Windows の現行版では 5 回中 4 回、Windows と Linux の改修前版では 5 回すべてで起きています。ログでは、基準通番が 831 のまま、受信通番だけが 43913 まで進んでいました。
- **本来あるべき姿**: 回復できない欠落を REJECT で確定した後は、受信ウィンドウがその通番を飛ばして進み、後続のパケットの受信を再開することです。

### 経緯と見送り理由

- **摘出契機**: 本案件の P3 の本測定 (2026-11-15) の結果の確認で見つかりました。
- **今回の見送り理由**: 改修前版でも同じ形で起きており、ハンドル寿命管理の改修とは別の問題です。修正には受信ウィンドウと再送制御の設計の確認が必要で、本案件の範囲外としました。

### 影響範囲とリスク

- **影響対象**: UDP の信頼性付き通信種別 (POTR_TYPE_UNICAST など、受信ウィンドウと NACK を使うもの) の受信側。`thread_recv_window.c` の REJECT 処理と基準通番の更新。
- **放置した場合のリスク**: 受信が一時的に追いつかないだけで、回復できない欠落の後に通信が事実上止まり、利用側には切断も通知されないまま全データが失われる可能性があります。

### 推奨される対応策

- **恒久対応案**: REJECT の受信 (または NACK の対象外の判定) で、受信ウィンドウの基準通番を欠落の次へ進める処理があるか、ある場合はなぜ進まないかを確認します。P3 の負荷を再現する結合試験を追加し、REJECT の後に受信が再開することを確認します。
- **参考情報**: 検証記録の「低速コールバック (P3)」。測定時のログは、Windows の `new-p3-b5000.err` (本案件の一時ディレクトリ。保存されていない場合があります) に、基準通番の停止が残っていました。

### 経緯と対処の更新

- 2026-11-15: 継続案件 `porter-reject-recovery` で対策しました。原因は、REJECT を受けても受信ウィンドウが 1 通番しか進まないこと、範囲外のパケットを捨てる際に NACK を送らないこと、REJECT の通番を確かめずに切断を通知することの 3 点でした。受信側は、自身の欠番に対する REJECT を受けた場合に切断を通知して受信の状態を破棄し、次に届いたパケットの通番から受信を再開するようにしました。受信ウィンドウより先の通番のパケットを捨てる際は、先頭の欠番の NACK を送ります。送受信の形式は変えていません。対処の詳細は `261115-porter-reject-recovery-design.md` (最終仕様) と、`docs/protocol.md` の「REJECT の役割」を参照してください。

## BL-003 小さいメッセージと圧縮送信で処理件数が低下し通知遅延が増える

### 概要と問題点

- **現状の事象**: 改修前版に比べて、現行版は次の条件で処理件数が下がり、通知遅延が増えました (5 回の中央値)。
    - UDP 64 バイト・通常・1 スレッド: 処理件数 Windows -34.5%、Linux -23.6%
    - UDP 64 バイト・圧縮・4 スレッド: 処理件数 Windows -26.5%、Linux -60.8%。通知遅延 p99 は約 8 倍
    - TCP 圧縮・4 スレッド: 処理件数 Windows -72.3% (64 バイト)、-61.4% (5000 バイト)
    - Linux の N:1 返信 (外部スレッド、64 バイト): 往復時間 約 1.5 倍、処理件数 -31.3%

    ブロッキング送信では、差は数 % 以内でした。
- **本来あるべき姿**: 未確定です。安全性と公開契約を維持したまま改善できる追加コストがあるかを特定し、許容するか改善するかを判断する必要があります。

### 経緯と見送り理由

- **摘出契機**: 本案件の P1、P2、P5 の本測定 (2026-11-15) で確認しました。
- **今回の見送り理由**: 本案件は測定と判断材料の提示が目的です。原因の特定には、プロファイラーなどを使った追加の調査が必要です。

### 影響範囲とリスク

- **影響対象**: 非ブロッキング送信の処理件数と通知遅延。特に圧縮を指定した複数スレッドの送信。
- **放置した場合のリスク**: 小さいメッセージを高頻度で送る用途や圧縮を多用する用途で、改修前より処理能力が下がります。

### 推奨される対応策

- **恒久対応案**: 圧縮・4 スレッドの条件でプロファイルを取り、通知スレッドの起床、通知キューへの受け渡し、圧縮と展開の各段階の時間とロックの競合を測ります。主因を特定してから、改善案と安全性への影響を比べます。
- **参考情報**: 検証記録の「UDP と TCP の遅延分布 (P1、P5)」「N:1 返信 (P2)」。
