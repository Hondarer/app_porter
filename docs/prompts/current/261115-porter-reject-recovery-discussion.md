## 調査結果 (BL-002 の原因)

コードを読んだ結果、BL-002 で受信が止まる原因は次の 3 点の組み合わせと判断しました。測定時のログ (基準通番 831 で停止、受信通番は 43913 まで進行) と矛盾しません。実機での再現による確認はまだ行っていません。

1 点目は、REJECT を受けても 1 通番しか進まないことです。`thread_recv_window_on_reject()` は `potr_internal_window_recv_skip()` を呼び、`next_seq` が REJECT の通番と一致する場合に限り、1 通番だけ飛ばします。送信側の保持範囲 (送信ウィンドウ、既定 16、最大 256) は送信の進行に合わせて古い通番から捨てるため、受信側が大きく遅れると、基準通番から送信側の保持範囲の先頭までの数万通番がすべて再送不能です。1 通番ごとに NACK と REJECT の往復が必要になり、事実上回復しません。

2 点目は、受信ウィンドウの範囲外のパケットを捨てる際に NACK を送らないことです。`thread_recv_window_accept_outer()` は `potr_internal_window_recv_push()` が失敗すると「recv_window full (100%), dropping」を記録して戻り、欠番の判定と NACK の送出に進みません。そのため、受信が止まった後の NACK は PING の受信時の走査とリオーダー待ちの期限切れに限られ、往復の間隔がさらに長くなります。

3 点目は、REJECT の通番が自分の欠番かどうかを確かめずに切断を通知することです。`thread_recv_window_on_reject()` は通番を確認せずに全経路を切断状態にします。送信側は REJECT を選択中グループの宛先 (マルチキャストではグループ アドレス) へ送るため、ある受信者の NACK に対する REJECT が、欠番のない他の受信者にも切断を通知させると読めます。また、同じ欠番に NACK を 200[ms] 以上の間隔で 2 回送った場合、2 回目の REJECT でも再び切断を通知します。

```text
thread_recv_window_on_reject():
    全経路を切断状態にする            <- 通番を確認しない (3 点目)
    potr_internal_window_recv_skip(ack_num)
        next_seq == ack_num のときだけ 1 通番進める (1 点目)
    slot_drain_recv_window()
```

一方、[機能仕様 メッセージ配送](../../functional-spec/delivery.md) の「切断の通知」は、「切断を通知した後、その相手に対する受信の状態は破棄されます。通信が再び確立した場合は、新しい通信として受信を開始します。」と定めています。現在の REJECT の処理は受信ウィンドウを残したまま 1 通番だけ進めるため、この記述と一致していません。

### Q-002 REJECT 受信後の受信状態の扱い

**Status**

解決済み

**Question**

自分の欠番に対する REJECT を受けた後、受信ウィンドウをどのように扱いますか。

**Context**

「調査結果」の 1 点目のとおり、現在は 1 通番ずつしか進まないため、受信側が大きく遅れると回復しません。対策には次の 3 案があります。

案 A は、REJECT を受けたら受信の状態を破棄し、次に届いたパケットの通番から受信を再開する方式です。RAW の通信種別がリオーダー待ちの期限切れで行う処理 (`thread_recv_window_check_reorder_timeout()`) と同じく、セッションを未知に戻し (`peer_session_known = 0`)、次の DATA または PING で受信ウィンドウを初期化します。機能仕様の「切断を通知した後、受信の状態は破棄」と一致し、送受信の形式を変えないため、改修前の版の送信側と組み合わせても効果があります。欠番より後で受信ウィンドウに保持済みのパケットは、利用側へ渡さずに捨てます。これらは切断の通知より後のデータで、機能仕様は切断後の回復を適用範囲外としています。

```text
案 A: REJECT(831) 受信
    -> 切断を通知、受信ウィンドウとフラグメント途中の状態と保留中の FIN を破棄
    -> 次に届いた DATA(43914) で受信ウィンドウを 43914 から初期化し、接続を通知して配信
```

案 B は、REJECT に送信側の保持範囲の先頭通番を載せ、受信側がその通番まで一括で飛ばす方式です。REJECT の `seq_num` は現在 0 固定で使っていないため格納できますが、通番 0 も有効値のため、有効を示す新しいフラグが必要です (FIN の `POTR_FLAG_FIN_TARGET_VALID` と同じ考え方)。受信ウィンドウに保持済みのパケットのうち先頭通番以降のものは渡せます。一方、送受信の形式 ([protocol.md](../../protocol.md)) と公開ヘッダーのフラグ定義を変え、改修前の版の送信側と組み合わせると効果がありません。
