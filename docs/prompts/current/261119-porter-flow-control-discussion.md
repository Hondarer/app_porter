# porter のフロー制御の導入の検討

ファイル名: `261119-porter-flow-control-discussion.md`

## 明確化のための確認項目

この文書の質問は、次の用語を使います。

| 用語 | 意味 |
| --- | --- |
| フロー制御 | 受信側の処理が追い付かないときに、受信側の要求で送信側が DATA の送出を止める仕組み |
| 通知キュー | 受信スレッドが受信済みデータを登録し、通知スレッドが利用側コールバックへ渡す待ち行列。ハンドルごとに 1 本あり、現在は容量の上限がありません |
| 占有量 | 通知キューにあり、まだコールバックから復帰していない DATA の量 |
| 容量 | 占有量の割合 (80%、60%) を計算する基準値。この案件で新設する設定値 |
| 抑制 | 送信側が DATA の送出を止めている状態 |
| 抑制の要求 / 解除 | 受信側が送信側へ伝える 2 種類の合図。占有量が容量の 80% を超えたら要求し、60% を下回ったら解除する |
| 1 対 N | `multicast` と `broadcast` (1 つの送信者と複数の受信者) |
| N 対 1 サーバー | `unicast_bidir_n1` の待ち受け側 (複数のピアと双方向に通信する) |

Table: 質問で使う用語

対話で決定済みの事項 (計測対象は通知キュー、対象は片方向 UDP の再送を行う通信種別・双方向 UDP・TCP、1 対 N は割合と台数で判定) は、簡易 ADR に記録しています。

### Q-001 通知キューの容量の単位

**Status**

解決済み

**Question**

通知キューの容量と占有量を、どの単位で数えますか。

**Context**

通知キューには容量の上限がなく、通知 1 件ごとに「管理情報 + データ長」の領域を確保します ([potr_notify.c](../../../prod/libsrc/porter/potr_notify.c))。80% と 60% を判定するには、基準になる容量を新しい設定値として定める必要があります。

1 件のメッセージは最大 65,535 バイト (`max_message_size` の既定値) まであり、大きさは用途によって大きく変わります。

```text
案 A (バイト数): 容量 = 1,048,576 [B] の場合
  100 [B] のメッセージ → 約 8,388 件で 80%
  60,000 [B] のメッセージ → 14 件で 80%

案 B (件数): 容量 = 1,000 [件] の場合
  100 [B] のメッセージ → 800 件 (80,000 [B]) で 80%
  60,000 [B] のメッセージ → 800 件 (48,000,000 [B]) で 80%
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) DATA のバイト数で数えます。CONNECTED などのデータを伴わない通知は占有量に含めません。
- [ ] B: DATA の通知件数 (メッセージ数) で数えます。
- [ ] C: バイト数と件数の両方に容量を設け、どちらかが 80% を超えたら抑制を要求します。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-19 20:31:38 JST (検討用 Markdown の保存時刻)

**Recommendation**

推奨: A  
理由: 抑えたい対象はメモリの使用量であり、通知キューが保持する領域は受信データ量に比例します ([api.md](../../api.md) の「通知継続不能のエラー イベント」)。件数では、メッセージの大きさによって同じ設定値のメモリ使用量が大きく変わります。

**Assessment**

A を選択。占有量は DATA のバイト数で数え、データを伴わない通知は含めません。他の回答との矛盾はありません。

### Q-002 N 対 1 サーバーでの占有量の集計単位

**Status**

解決済み

**Question**

N 対 1 サーバーでは、占有量をピアごとに数えますか、ハンドル全体で数えますか。

**Context**

通知キューはハンドルに 1 本です。N 対 1 サーバーでは、すべてのピアから受信したデータが同じ通知キューに並びます。  
片方向の受信者と 1 対 1 の通信種別では、相手が 1 つなので、この質問の影響はありません。

```text
容量 = 1 [MiB]、ピア P1 が大量に送信し、ピア P2 は少量だけ送信する場合

案 A (ピアごと):
  P1 の占有量が 80% を超える → P1 にだけ抑制を要求する
  P2 は抑制されない
  メモリの上限の目安 = 容量 × 接続中のピア数

案 B (ハンドル全体):
  全ピアの合計が 80% を超える → 全ピアに抑制を要求する
  P2 も送信を止められる
  メモリの上限の目安 = 容量
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) ピアごとに数え、80% を超えたピアにだけ抑制を要求します。
- [ ] B: ハンドル全体で数え、80% を超えたら接続中の全ピアに抑制を要求します。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足: ピアごとの場合は、ピアごとにバッファ利用量を管理して、ただし受信順にコールバックは処理されるという現状の仕様は満たすということで良いですか。問題なければ追加Q&Aは不要です。

回答者: Tetsuo Honda  
回答日時: 2026-11-19 20:31:38 JST (検討用 Markdown の保存時刻)

**Recommendation**

推奨: A  
理由: 送信量の多いピアだけを抑制でき、少量しか送らないピアの通信を止めません。N 対 1 サーバーの受信ウィンドウや通番もピアごとに独立しています ([protocol.md](../../protocol.md) の「unicast_bidir N:1 モードのピア識別」)。メモリの上限の目安が「容量 × ピア数」になる点が制約です。

**Assessment**

A を選択。補足の確認事項への回答は「そのとおり」です。通知キューはハンドルに 1 本のままで、コールバックは受信順に実行します。ピアごとに持つのは占有量の計数だけであり、通知の順序は変わりません。補足で追加の Q&A は不要とされたため、この Q は解決済みとします。

### Q-003 容量を超えた受信データの扱い

**Status**

解決済み

**Question**

抑制を要求した後も DATA が届き、占有量が容量の 100% を超えた場合、受信側は超えた分をどう扱いますか。

**Context**

抑制の要求が送信側へ届くまでの間に送出済みの DATA は、受信側へ届きます。UDP では、抑制の要求そのものが失われることもあります。そのため、80% で要求しても占有量が 100% を超える場合があります。

過去の案件 (261107 ハンドルの寿命) では、通知キューについて「メモリ使用量の固定上限は設けず」「通知キューが満杯という理由で I/O スレッドを空き待ちさせない」と決定しています ([261107-porter-handle-lifecycle-design.md](../past/261107-porter-handle-lifecycle-design.md) の「通知キューを動的に拡張し、I/O の空き待ちをなくします」)。

```text
案 A (受け入れ続ける):
  容量は割合を計算する基準値であり、上限ではない
  100% を超えても通知キューへ登録する。データは失われない
  抑制が効かない間は、メモリ使用量が容量を超えて増える

案 B (破棄する):
  100% を超えた DATA は通知キューへ登録せずに破棄する
  UDP: 破棄した通番は欠落になり、再送の要求で回復を試みる。保持範囲を外れると切断になる
  TCP: 下位の通信は再送しないため、破棄した時点でその通信を切断として扱う必要がある
```

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 受け入れ続けます。容量は割合の基準値とし、上限にはしません。
- [ ] B: 100% を超えた DATA を破棄します。
- [x] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足: 今までの仕様で言えば、これは切断条件のはずで DISCONNECT してよい。(そのあと自動回復するかどうかも含めて従来とおりの振る舞いとしてよい)

回答者: Tetsuo Honda  
回答日時: 2026-11-19 20:31:38 JST (検討用 Markdown の保存時刻)

**Recommendation**

推奨: A  
理由: 過去の決定 (固定上限を設けない、I/O スレッドを待たせない) と整合し、フロー制御の導入によってデータを失う場面を増やしません。メモリ使用量が容量を超える場合があることを、文書に記載する必要があります。

**Assessment**

C (その他) を選択。補足により、占有量が容量の 100% を超えた場合は、超えた DATA を破棄してその通信を切断として扱い、利用側へ切断を通知します。切断後の回復は従来の切断と同じ動作とします。切断の後も占有量が高いままの間に届く DATA の扱いは、従来の動作 (次に届いた DATA または PING で即時に再開) では切断と再開が繰り返されるため、[Q-025](#q-025-容量超過による切断の後に受信を再開する条件) で確認します。close との関係は [Q-026](#q-026-close-で送出した-data-が受信側の容量を超えた場合の扱い) で確認します。

### Q-005 抑制状態を伝えるパケット

**Status**

解決済み

**Question**

抑制の要求と解除を、どのパケットで受信側から送信側へ伝えますか。

**Context**

受信側から送信側へ戻る既存のパケットは、通信種別によって異なります。

| 通信種別 | 受信側から送信側へ戻る既存のパケット |
| --- | --- |
| 片方向 UDP (`unicast`、`multicast`、`broadcast`) | NACK、受信報告 (REPORT) |
| 双方向 UDP (`unicast_bidir`、`unicast_bidir_n1`) | NACK、PING |
| TCP (`tcp`、`tcp_bidir`) | PING、FIN_ACK |

Table: 受信側から送信側へ戻る既存のパケット

受信報告は、実効 `health_interval_ms` (既定 3,000 ms) ごとに送出し、`health_interval_ms` が 0 の構成では送出しません ([thread_recv_report.c](../../../prod/libsrc/porter/thread/thread_recv_report.c))。受信側は、受信報告と PING のペイロード長が 8 バイト (`POTR_MAX_PATH`) であることを検査しています ([receiver_report.c](../../../prod/libsrc/porter/protocol/receiver_report.c))。

```text
案 A (新しいパケット種別):
  flags に新しい種別 (例: POTR_FLAG_FLOW = 0x0800) を追加する
  ペイロードは 1 バイトの状態 (抑制の要求 / 解除) だけを持つ
  しきい値をまたいだ時点で即時に送出する
  NACK・受信報告と同じく、受信側の全経路から送信者へユニキャストで送出する
  保護 (暗号化と認証) は、同じ向きの既存パケット (受信報告、PING) と同じ鍵と方式にする
  対象の 3 系統 (片方向 UDP、双方向 UDP、TCP) で同じ形式を使う

案 B (既存パケットへの相乗り):
  片方向 UDP は受信報告、双方向 UDP と TCP は PING のペイロードを 1 バイト拡張する
  しきい値をまたいだ時点で、周期を待たずに受信報告または PING を追加で送出する
  health_interval_ms が 0 の構成での扱いを別に定める必要がある
  PING は「要求と応答」の対応を持つため、追加の送出が死活監視の判定に影響しないことの確認が必要になる
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 新しいパケット種別を追加し、対象の全通信種別で同じ形式を使います。
- [ ] B: 既存パケット (受信報告、PING) のペイロードを拡張します。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-19 20:31:38 JST (検討用 Markdown の保存時刻)

**Recommendation**

推奨: A  
理由: 死活監視の周期と設定 (`health_interval_ms`) から独立し、3 系統で同じ形式と同じ処理を使えます。既存の受信報告と PING の形式と意味を変えません。パケット種別が 1 つ増える点が制約です。

**Related**

[Q-006](#q-006-tcp-での実現方式)、[Q-007](#q-007-プロトコル-バージョンの更新)

**Assessment**

A を選択。新しいパケット種別を追加し、ペイロードは 1 バイトの状態、しきい値をまたいだ時点で即時に送出、受信側の全経路から送出、保護は同じ向きの既存パケットと同じ、という案 A の内容で確定します。

### Q-006 TCP での実現方式

**Status**

解決済み

**Question**

TCP (`tcp`、`tcp_bidir`) のフロー制御を、どの方式で実現しますか。

**Context**

TCP は下位の通信がフロー制御を持ちますが、porter の受信スレッドはソケットから読み続けて通知キューへ移します。そのため、利用側コールバックが遅くても下位のフロー制御は働かず、通知キューが増え続けます。

過去の案件 (261107 ハンドルの寿命) では、「長時間のコールバック実行中も、TCP の受信や制御パケットの処理など、送信完了に必要な処理を継続する」と決定しています。

```text
案 A (UDP と同じパケットで伝える):
  受信側は読み取りを続け、抑制の要求と解除をパケットで送信側へ伝える
  送信側の porter が DATA の送出を止める
  PING と FIN の処理は、抑制中も継続する

案 B (読み取りを止める):
  占有量が 80% を超えたら、受信スレッドがソケットの読み取りを止める
  下位のフロー制御が働き、送信側の書き込みが進まなくなる
  読み取りを止めている間は、同じ接続を流れる PING と FIN も読めない
  死活監視のタイムアウトと close の完了待ちに影響する
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) UDP と同じパケットで抑制の要求と解除を伝えます。
- [ ] B: 受信スレッドが読み取りを止め、下位のフロー制御に委ねます。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-19 20:31:38 JST (検討用 Markdown の保存時刻)

**Recommendation**

推奨: A  
理由: 抑制中も PING と FIN の処理が続くため、死活監視と close に影響しません。過去の決定とも整合し、UDP と同じ実装を使えます。

**Related**

[Q-005](#q-005-抑制状態を伝えるパケット)

**Assessment**

A を選択。TCP も UDP と同じパケットで伝え、受信側は読み取りを続けます。

### Q-007 プロトコル バージョンの更新

**Status**

解決済み

**Question**

フロー制御の導入に伴い、プロトコル バージョン (`POTR_PROTOCOL_VERSION`) を 2 から 3 へ上げますか。

**Context**

受信側は、`protocol_version` が自身の版と一致しないパケットを破棄します ([protocol.md](../../protocol.md) の「外側パケット」)。版を上げると、版 2 の porter と版 3 の porter は通信できなくなります。

```text
案 A (版を 3 へ上げる):
  対向側の両方を同時に更新する必要がある
  フロー制御を使わない構成でも、版 2 の相手とは通信できなくなる

案 B (版を 2 のままにする):
  版 2 の実装が新しいパケット種別を受信したときの動作を、先に確認する必要がある
  相手がフロー制御に対応しているかを、送受信の双方が判別できない
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 版を 3 へ上げます。
- [ ] B: 版を 2 のままにします。未知のパケット種別に対する版 2 の動作を確認したうえで、扱いを追加の質問で決めます。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

### Q-025 容量超過による切断の後に受信を再開する条件

**Status**

解決済み

**Question**

**Context**

[Q-003](#q-003-容量を超えた受信データの扱い) の回答により、占有量が容量の 100% を超えた場合は、超えた DATA を破棄し、その通信を切断として利用側へ通知します。回答は、切断後の回復を「従来どおり」としています。この Q は、[Q-003](#q-003-容量を超えた受信データの扱い) の回答を次のとおり理解したうえで、切断後の動作を確認するものです。

- 切断の時点で通知キューにある DATA は、そのまま順にコールバックへ渡します。その後に切断の通知が続きます。
- 切断の時点で、受信の状態 (受信ウィンドウの保持内容、フラグメント途中の状態) を破棄します。再送不能の通知 (REJECT) を受けたときと同じ扱いです。
- N 対 1 サーバーでは、容量を超えたピアだけを切断します。
- TCP では、その接続を切断します。

従来の切断 (再送不能の通知による切断) では、次に届いた DATA または PING を新しい通信として採用し、受信を再開します ([protocol.md](../../protocol.md) の「REJECT の役割」)。TCP の送信側は、`reconnect_interval_ms` (既定 5,000 ms) の間隔で再接続します。

容量を超えるのは、コールバックが遅く、抑制が効いていない (抑制の要求が届いていない、または送出済みの DATA が多い) 場合です。切断の直後も占有量は 100% の近くにあるため、従来の動作のままでは、次のようになります。

```text
案 C (従来どおり、次のパケットで即時に再開する) の場合の UDP の動作:
  占有量 100% 超 → DATA を破棄 → 切断を通知
  次の DATA が届く → 新しい通信として採用 → 接続を通知 → 占有量 100% 超 → 破棄 → 切断を通知
  送信側が送出を続ける間、パケットごとに接続と切断の通知が繰り返される
  接続と切断の通知は占有量に数えないため、通知キューが通知で増え続ける

案 A (解除のしきい値を下回るまで再開しない) の場合:
  占有量 100% 超 → DATA を破棄 → 切断を通知
  占有量が解除のしきい値 (既定 60%) を下回るまで:
    UDP: その相手からの DATA と PING を破棄し、新しい通信として採用しない
    TCP: その相手からの接続を受け付けた直後に閉じる
    抑制の要求は、占有量が解除のしきい値を下回るまで送り続ける
  下回った後に届いた DATA、PING、または接続から、従来どおり再開する
```

- [ ] B: 占有量が容量の 100% を下回ったら再開します。
- [ ] C: 従来どおり、次に届いたパケットまたは接続から即時に再開します。

**A (送出上限の通知) の内容**

- 受信側は、フロー制御パケットに「送出上限」(次に受信する通番 + 要求のしきい値までの残りを `max_payload` で割ったパケット数) を 4 byte で載せます。ペイロードは 1 byte から 5 byte になります。プロトコル バージョンは 3 のままです (3 はまだ公開していません)。
- 受信側が送出上限を送るのは、相手を新しい通信として採用したとき、解除のとき、および、前回知らせた範囲の半分を受信したときです。抑制の要求と、その周期的な再送は、今の仕様のまま残します。
- 送信側は、新しい DATA の通番が送出上限に達したら、次のフロー制御パケットが届くまで送出を止めます。再送、PING、FIN は止めません。

- 送出上限のパケットが失われた場合は、送信側が上限で止まり、有効期限 (既定 1000 ms) の経過後に送出を再開します。受信側は、上限以上の通番を受信したら上限を送り直します。

**A で防げないもの**

- 経路 5 (UDP の OS の受信バッファーあふれ) は対象外です。送出上限の範囲を OS の受信バッファーの大きさで絞ると防げますが、送出上限のパケットが DATA 数十パケットにつき 1 個に増え、指示の制約 (個別の ACK に近づけない) から外れるため、含めません。
- 圧縮した DATA は、展開後の大きさが `max_payload` を超えるため、送出上限だけでは占有量を抑えきれません。この場合は、今の仕様の抑制の要求が働きます。

- 1 対 N で、判定の条件 (既定で 2 台以上) に満たない台数の受信者だけが遅い場合は、今の仕様どおり、送信側は止まらず、遅い受信者が容量を超えて切断になります。

### Q-050 待ち合わせを指定しない UDP の連続送信で欠落が増えたことへの対処

**Question**

待ち合わせを指定しない送信が `POTR_ERR_FULL` を返すようになったことで、UDP の連続送信の欠落が増えた事象に、この案件でどう対処しますか。

**Context**

| 指標 | 変更前 (`main`) | 変更後 (`flow-control`) |
| --- | --- | --- |
| 届かなかった件数 (10,000 件中) | 0 (4 回とも) | 1,051、545、2,275、2,220 |
| `POTR_ERR_FULL` を受けて送り直した回数 | 0 (4 回とも) | 30,821、27,292、33,571、31,358 |

Table: 待ち合わせを指定しない UDP の連続送信の測定結果

`porter-test` の `burst` (待ち合わせを指定しない送信) でも、`unicast` で欠落と切断が繰り返されました。待ち合わせを指定した送信 (`POTR_SEND_BLOCKING`) では、どちらの確認でも欠落は起きていません。

原因は、次のとおりと推定しています (実測では確かめていません)。

- 変更後は、`POTR_ERR_FULL` が返ります。利用側が少し待って送り直す間に、送信スレッドが送信キューを空にします。利用側がまとめて登録し直すと、最大で `send_queue_depth` × `max_payload` (既定で約 1.4 MB) がかたまりで送出され、受信側の OS の受信バッファーをあふれさせます。欠落が送信側の再送用の保持範囲 (`window_size`、既定 16) を超えると、再送できずに切断になります。

- A: 動作は変えず、文書で注意を促します。`docs/api.md` と `docs/config.md` に、UDP で連続して送信する場合は待ち合わせを指定すること、待ち合わせを指定しない場合は `POTR_ERR_FULL` の後にまとめて送り直さないことを記載します。BL-005 の優先度を上げ、送信側の送出をならす対策を、次の案件として検討します。
- B: この案件で、送信スレッドが連続して送出する量を抑える対策を追加します。方式の検討 (何を基準に、どれだけ抑えるか) と実測が必要で、最終仕様の改版と、あらためての承認が必要です。フロー制御が無効の利用側の処理件数に影響する可能性があります。
- C: 待ち合わせを指定しない送信の動作を、変更前 (満杯のときは中で待つ) に戻します。欠落は変更前の水準に戻りますが、機能仕様の `POTR-DELIVERY-FUNC-009` との相違が復活し、[Q-016](#q-016-抑制中の送信要求の扱い)、[Q-017](#q-017-容量不足の要件と実装の相違の扱い)、[Q-028](#q-028-n-対-1-サーバーで抑制中のピア宛の送信要求の受け付け) の決定を改めることになります。

### Q-051 UDP の連続送信の欠落への対策の方式

**Status**

未回答

**Question**

UDP の連続送信で受信側の OS の受信バッファーがあふれる問題を、どの方式で対策しますか。

**Context**

[Q-050](#q-050-待ち合わせを指定しない-udp-の連続送信で欠落が増えたことへの対処) の回答 (この案件で対策する。方式は落ち着いて検討する) を受けて、実測を行いました。同じホストの Linux で、`porter-test` の送信側と受信側を別のプロセスとして起動し、`unicast`、フロー制御が無効、受信コールバックの遅延なしで、`burst` (1,000 byte × 6,000 件) を実行しています。OS の受信バッファーは既定 (212,992 byte) です。

**実測 1: 変更前のライブラリでも起きる**

| ライブラリ | 送信 | 所要時間 | 受信 | 切断 | OS が捨てたパケット |
| --- | --- | --- | --- | --- | --- |
| 変更前 (`main`) | 待ち合わせを指定しない | 144〜177 ms | 4,000 件まで、または完了せず | 10〜12 回 | 1,109〜3,458 |
| 変更後 | 待ち合わせを指定しない | 47 ms | 完了せず | 20 回 | 4,800 |
| 変更後 | 待ち合わせを指定する | 571 ms | 6,000 件 | 0 回 | 0 |

Table: 変更の前後での連続送信の結果

- 変更前のライブラリでも、欠落と切断が起きました。Q-050 の「変更で欠落が増えた」は、送信側と受信側が同じプロセスにある測定プログラム (`porter-bench`) の条件に限った結果で、別のプロセスでは変更前から起きています。残課題一覧の BL-005 は、この案件より前からある問題です。
- 待ち合わせを指定した送信は、送信の完了を 1 件ずつ待つため、送出の速さが約 10 分の 1 になり、欠落が起きません。
- 送信スレッドは、受信側が処理できる速さの数倍から 10 倍の速さで送出できます。そのため、送信側だけで「連続して送出する量」を決めても、受信側の速さを知らない限り、あふれを防げません。

**実測 2: 既存の設定では防げない**

| `send_queue_depth` | `window_size` | 待ち合わせを指定しない送信の結果 |
| --- | --- | --- |
| 1,024 (既定) | 16 (既定) | 完了せず、切断 20 回 |
| 64 | 16 | 完了せず、切断 2 回 |
| 16 | 16 | 6,000 件、切断 0 回 (所要 421 ms) |
| 1,024 | 256 (最大) | 完了せず、切断 2 回 |
| 128 | 256 | 完了せず、切断 8 回 |

Table: 既存の設定を変えた場合の結果

送信キューの深さを 16 まで下げると起きませんが、64 では起きます。再送用の保持範囲 (`window_size`) を最大にしても防げません。

**実測 3: 送出上限を OS の受信バッファーより小さくすると起きない**

この案件で実装した送出上限の通知 ([Q-039](#q-039-集中送出への対策の方式-再検討)) を使い、容量を小さく設定して、送出上限の幅 (受信側が処理を終えた通番から先に、送信側が送出してよいパケット数) を変えました。待ち合わせを指定しない送信です。

| 送出上限の幅 | 所要時間 | 受信 | 切断 | OS が捨てたパケット |
| --- | --- | --- | --- | --- |
| 約 57 パケット | 87〜98 ms | 6,000 件 (2 回とも) | 0 回 | 0 |
| 約 114 パケット | 10〜12 秒 | 約 5,030 件 | 28〜30 回 | 190〜215 |
| 約 228 パケット | 4〜8 秒 | 約 2,270 件 | 56〜62 回 | 1,877〜1,971 |

Table: 送出上限の幅を変えた場合の結果

OS の受信バッファー (212,992 byte) に入るのは、1,000 byte のパケットで 90 個前後です。送出上限の幅がそれより小さい場合は、欠落も切断もなく、待ち合わせを指定した送信の約 6 倍の速さ (約 65,000 件/s) で全件が届きました。幅が OS の受信バッファーを超えると、あふれます。

**選択肢**

- A (OS の受信バッファーに基づく送出上限): 受信側が、OS の受信バッファーの大きさ (ソケットから取得した実際の値) から送出上限の幅を計算し、通知キューの占有量から求めた許可数と比べて、小さいほうを知らせます。送信側の変更はありません (実装済みの送出上限に従うだけです)。送信側は受信側の処理に合わせて送出するため、時間や OS に依存しません。通知の頻度は、OS の受信バッファーが既定の Linux で、DATA 約 30 パケットにつき 1 個です (実測 3 では 6,000 件に対して約 200 個)。OS の受信バッファーを大きくすると、頻度は下がります。[Q-039](#q-039-集中送出への対策の方式-再検討) では、この頻度が個別の ACK に近づくとして見送りました。パケット 1 個あたりが OS の受信バッファーを使う量は OS によって異なるため、Windows での実測が必要です。
- B (送信側の連続送出の上限と休止): 送信スレッドが、一定数を送出するごとに一定時間休みます。受信側の変更も、通知の追加もありません。休む時間と数は、受信側が処理できる速さより遅くなるように利用側が設定する必要があり、既定値を決める根拠がありません。送出の速さに上限が生じ、待ちの最小単位が約 15 ms の Windows では、上限が大きく下がります。
- C (待ち合わせを指定しない送信を、送信の完了まで待たせる): 待ち合わせを指定した送信と同じ速さになります。欠落は起きませんが、送出の速さが約 10 分の 1 になり、待ち合わせを指定しない送信の意味がなくなります。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) OS の受信バッファーに基づく送出上限で対策する。
- [ ] B: 送信側の連続送出の上限と休止で対策する。
- [ ] C: 待ち合わせを指定しない送信を、送信の完了まで待たせる。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

理由: 実測 3 で、欠落と切断が起きず、送出の速さも保たれることを確かめました。受信側だけが知っている情報 (OS の受信バッファーの大きさと、自分の処理の進み具合) で送出を抑えるため、送信側が速い場合にも、受信側が遅い場合にも成り立ちます。実装済みの仕組みへの追加で済み、送信側と通信の形式は変わりません。

**Context**

フロー制御は、受信側が容量 (`flow_control_capacity`) を設定した場合だけ働き、既定では無効です ([Q-020](#q-020-有効化の方法と既定の状態))。実測 1 の欠落と切断は、フロー制御が無効の構成で起きています。

- A (容量を設定した受信側だけ): フロー制御を有効にした受信側が、通知キューと OS の受信バッファーの両方を守ります。既定の構成の動作は変わらず、通知も増えません。既定の構成では、UDP の連続送信の欠落は残ります。文書で、連続して送信する場合はフロー制御を有効にするよう案内します。

- [ ] A: 容量を設定した受信側だけに適用する。
- [ ] B: (推奨) 再送を行う UDP の受信側すべてに、既定で適用する。無効にする設定を設ける。
