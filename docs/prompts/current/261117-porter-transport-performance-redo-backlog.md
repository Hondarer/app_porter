## BL-001 小さいメッセージと圧縮送信で処理件数が低下し通知遅延が増える

### 概要と問題点

- **現状の事象**: ハンドル寿命管理の改修前の版に比べて、現行版は次の条件で処理件数が下がり、通知遅延が増えました (2026-11-15 の測定、5 回の中央値)。
    - UDP 64[B]・通常・1 スレッド: 処理件数 Windows -34.5%、Linux -23.6%
    - UDP 64[B]・圧縮・4 スレッド: 処理件数 Windows -26.5%、Linux -60.8%。通知遅延の p99 は約 8 倍
    - TCP 圧縮・4 スレッド: 処理件数 Windows -72.3% (64[B])、-61.4% (5000[B])
    - Linux の N:1 返信 (外部スレッド、64[B]): 往復時間 約 1.5 倍、処理件数 -31.3%
- **本来あるべき姿**: 未確定です。安全性と公開契約を維持したまま減らせる追加のコストがあるかを特定し、許容するか改善するかを判断する必要があります。

### 経緯と見送り理由

- **摘出契機**: `261115-porter-reject-recovery-backlog.md` の BL-002 からの引き継ぎです。
- **今回の見送り理由**: この案件の対象を TCP の約 40[ms] の停止に絞ったためです (検討用 Markdown の Q-001 A)。原因は未特定で、製品の改修は未着手です。

### 影響範囲とリスク

- **影響対象**: 非ブロッキング送信の処理件数と通知遅延。特に、圧縮を指定した複数スレッドの送信。
- **放置した場合のリスク**: 小さいメッセージを高頻度で送る用途や、圧縮を多用する用途で、改修前より処理能力が下がります。

### 推奨される対応策

- **恒久対応案**: 圧縮・4 スレッドの条件でプロファイルを取り、通知スレッドの起床、通知キューへの受け渡し、圧縮と展開の各段階の時間とロックの競合を測ります。主因を特定してから、改善案と安全性への影響を比べます。TCP の条件は、この案件の変更 (`TCP_NODELAY` とまとめ送り) で数値が変わったため、基準を測り直してください。
- **参考情報**: `261115-porter-reject-recovery-backlog.md` の BL-002 (旧案件での調査の経緯を含む)。

## BL-002 Linux の 5000[B]・ブロッキング・1 スレッドの TCP 送信で処理件数が対策前より約 17% 低い

### 概要と問題点

- **現状の事象**: Linux (WSL) のループバックで、5000[B] のメッセージをブロッキング送信・1 スレッドで送る条件の処理件数が、`TCP_NODELAY` を有効にする前の 14,455[msg/s] から 11,953[msg/s] へ 17.3% 下がりました (5 回の中央値。5 回の最小どうしでは 20.3%)。同じ条件の通知遅延は短くなっています (p50 が 556.7[µs] から 96.2[µs])。
- **本来あるべき姿**: 未確定です。対策前は、OS が複数のメッセージをまとめて送り出すことで処理件数が高かったという見方がありますが、推測で未検証です。

### 経緯と見送り理由

- **摘出契機**: この案件の性能の測定 (2026-11-17) で確認しました。
- **今回の見送り理由**: ブロッキング送信・1 スレッドでは、送信キューに同時に 1 メッセージしか入らないため、待ち時間を足さずにまとめる方法がありません。ユーザーが既知の特性として残すと決めました (検討用 Markdown の Q-007 A)。

### 影響範囲とリスク

- **影響対象**: Linux で、1 パケットに収まらない大きさのメッセージを、1 スレッドからブロッキング送信で連続して送る用途。
- **放置した場合のリスク**: この用途の処理件数が、対策前より約 17% 低いままになります。4 スレッドの条件では、対策前を 12.2% 上回ります。

### 推奨される対応策

- **恒久対応案**: 1 メッセージあたりのセグメント数 (対策前 0.25、対策後 0.5〜0.9) と、送信の呼び出しから完了の通知までの時間の内訳を測り、差の原因を確かめます。原因が OS のまとめ送りの有無である場合は、処理件数と遅延のどちらを優先するかの判断が必要です。
- **参考情報**: `prod/libsrc/porter/thread/potr_send_thread.c` の `tcp_flush_packets()`。

- **現状の事象**: Windows の TCP の圧縮の条件で、同じ版でも測定ごとに処理件数の中央値が大きく変わります。たとえば、64[B]・圧縮・4 スレッドの対策前の版は、2 回の測定で 39,992[msg/s] と 113,603[msg/s] でした。この条件では、版の差と測定の変動を区別できません。
- **本来あるべき姿**: 同じ版の測定が、版の比較に使える程度に再現することです。

### 経緯と見送り理由

- **摘出契機**: この案件の Windows の測定 (2026-11-17) で確認しました。
- **今回の見送り理由**: 圧縮送信の処理件数は BL-001 の対象で、この案件の範囲外です。原因は調べていません。

### 影響範囲とリスク

- **影響対象**: Windows の圧縮送信の性能の評価。
- **放置した場合のリスク**: BL-001 の調査で、改善の効果を判定できません。

### 推奨される対応策

- **恒久対応案**: BL-001 の調査の最初に、同じ版を繰り返し測って変動の幅と要因 (実行の順序、スレッドの配置、測定時間) を確かめ、測定の方法を決めます。
- **参考情報**: 検討用 Markdown の「Windows の結果」と「未解決の事項」。
