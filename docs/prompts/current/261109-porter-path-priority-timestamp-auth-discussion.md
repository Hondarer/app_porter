## 技術レビューで判明した制約

版 2 の技術レビューで、質問の判断に影響する次の事実を確認しました。  
いずれも方針を決めたものではなく、関連する質問の背景として扱います。

### 送信時刻と暗号の nonce

暗号化を有効にした場合、porter はヘッダー全体を改ざん検出の対象 (AAD) にし、nonce (同じ鍵で一度だけ使う値) を `session_id`、`flags`、`seq_num` から作ります。  
AES-GCM は、同じ鍵と nonce で異なる内容や異なるヘッダーを保護すると、改ざん検出用の内部鍵を推定される危険があります ([NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final))。

送信時刻をヘッダーに入れると、同じ `seq_num` のパケットでもヘッダーが送出ごとに変わる場合があります。  
経路ごとの時刻取得 ([Q-012](#q-012-時刻を採取する単位) の A)、再送時の時刻更新 ([Q-013](#q-013-再送時の時刻) の A)、および DATA を送らない間に `seq_num` が変わらない PING の定周期送信が該当します。  
このため、時刻の追加には nonce の構成変更が必要です。判断は [Q-023](#q-023-暗号の-nonce-の構成) で確認します。

同じ構造は現行版にも潜在しています。  
PING は `seq_num` に送信側の `next_seq` を使い、通番を消費しません。DATA を送らない間に送る PING は同じ nonce を使い続けます。  
一方、PING のペイロードは経路の受信状態であり、送出時点で変わり得ます。このため、同じ鍵と nonce で異なる内容を保護する場合があります。  
この事象は [残課題一覧](261109-porter-path-priority-timestamp-auth-backlog.md) の BL-001 に記録しました。

### グループ切り替えの所要時間

経路の不達は、ヘルス チェックのタイムアウトで検出します。  
既定値は UDP が 10,000 ミリ秒、TCP が 31,000 ミリ秒です ([公開定数](../../../prod/include/porter/porter_const.h))。  
検出までの間、データは不達のグループへ送出され続けます。

その間のデータの扱いは通信種別で異なります。  
UDP の通常モードでは、受信側の NACK に対して送信ウィンドウに残るデータを再送できます。  
UDP の RAW モードは再送しません。TCP は NACK を使わないため、不達となった接続の送信バッファーにあるデータは porter からは回復できません。

### 受信側のグループ依存

受信側は、全経路から届いたパケットを `seq_num` で重複排除します ([プロトコル仕様](../../protocol.md))。  
このため、受信側が全経路で受信を続ける限り、どのグループで送るかを送信側だけで決める構成が可能です。  
この場合、両端のグループ設定の不一致はワイヤー上の矛盾になりません。判断は [Q-025](#q-025-グループ選択を判断する端) で確認します。

### ヘッダー長と MTU

NTP 64 ビット形式の実時刻 8 バイトと単調増加時刻 8 バイトを加えると、ヘッダーは 56 バイトになります。  
[Q-023](#q-023-暗号の-nonce-の構成) の A で送出通番 8 バイトを加えると 64 バイトです。  
ペイロード上限 1,400 バイトを維持した場合、IPv4 と UDP のヘッダー 28 バイトを加えて最大 1,492 バイトとなり、一般的な Ethernet の MTU 1,500 バイトに収まります。  
VPN などのトンネルを通る経路では MTU が小さくなるため、ペイロード上限の扱いを別途確認します。

### origin の取り込みで判明した前提の変化

porter の `1b24a89` (TCP の DATA を CONNECTED 前の破棄や送信失敗で失わない) により、TCP の送受信の規則が次のように変わりました ([プロトコル仕様](../../protocol.md) の TCP マルチパスの節)。

- 送信スレッドは、各通番を少なくとも 1 つの path へ必ず書き込みます。送信バッファーに空きがない path は、他の path へ書き込めた場合に限って飛ばします。
- 受信側は、ウィンドウ先頭より先の通番を受け取った場合、受信していない通番があるとしてストリームを切断します。
- TCP の送信スレッドは、path の経路状態が相手へ通知済みの値と異なる場合、DATA の前に PING を書き込みます。

1 点目と 2 点目により、TCP で優先グループを切り替えると、不達の検出前に旧グループだけへ書き込んだ通番が届かず、新グループで受け取った次の通番で受信側がストリームを切断します。  
[Q-009](#q-009-グループ切り替え時の未達データ) の A (既存の再送契約に従い、TCP の欠落を許容) は取り込み前の規則を前提にしていたため、[Q-050](#q-050-tcp-のグループ切り替え時の欠番) で確認します。  
3 点目により PING の送出が増えるため、[残課題一覧](261109-porter-path-priority-timestamp-auth-backlog.md) の BL-001 (PING の nonce 重複) が起きる機会も増えます。BL-001 は [Q-023](#q-023-暗号の-nonce-の構成) の A で解消する予定です。

### Q-010 実時刻の表現

**Status**

解決済み

**Question**

**Context**

RFC 8877 は、NTP 64 ビット形式と、PTP (高精度時刻同期プロトコル) の切り詰め形式などを示しています。  
NTP 64 ビットは 1900 年起点の秒部 32 ビットと小数部 32 ビットで、時刻の基準は UTC です。2036 年に秒部が周回するため、時代 (era) の識別が必要です。

既存のセッション開始時刻は POSIX 秒 64 ビットとナノ秒 32 ビットです。

OS の実時刻は UTC 基準のため、NTP 形式へは定数の加算と小数部の変換で変換できます。  
PTP 形式へ変換するには、UTC と TAI の差 (現在 37 秒) を OS から取得するか、設定で与える必要があります。  
NTP 形式の時代は、同じヘッダーにある 64 ビットのセッション開始時刻 (`session_tv_sec`) から一意に決められます。送信時刻とセッション開始時刻の差が約 68 年未満であることが条件です。

送信時刻をヘッダーへ加えるにあたり、暗号の nonce をどう構成しますか。

**Context**

現行の nonce は `session_id` (4 バイト)、`flags` (2 バイト)、`seq_num` または `ack_num` (4 バイト)、0 埋め (2 バイト) の 12 バイトです。  
ヘッダー全体を改ざん検出の対象にしているため、同じ `seq_num` で時刻だけが異なるパケットを送ると、同じ鍵と nonce で異なるヘッダーを保護することになります。  
AES-GCM では、これにより改ざん検出用の内部鍵を推定され、偽造パケットを受理する危険が生じます ([送信時刻と暗号の nonce](#送信時刻と暗号の-nonce))。

各案を採用した場合の nonce は次のとおりです。

```text
A: session_id (4) + tx_counter (8)                      ... 送出ごとに増える送出通番
B: session_id (4) + flags (2) + seq_or_ack (4) + 0 (2)  ... 現行どおり。時刻は seq_num ごとに固定
C: session_id (4) + flags (2) + seq_or_ack (4) + 0 (2)  ... 現行どおり。時刻を AAD から除外
```

A は、パケットを送出するたびに 1 増える 64 ビットの送出通番をヘッダーに加え、nonce を `seq_num` から切り離します。ヘッダーは 8 バイト増えます。複製、再送、PING のいずれでも nonce が重複しません。  
B は、時刻を `seq_num` の採番時に 1 回だけ取得し、複製と再送で変えません。PING は `seq_num` を消費しないため、PING にも独立した採番を設ける変更が別に必要です。  
C は、時刻を改ざん検出の対象外にします。時刻の書き換えを検出できず、[通信保護仕様](../../functional-spec/security.md) の `POTR-SECURITY-QUAL-002` (秘匿しない項目の改ざん検出) に反します。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 送出ごとに増える 64 ビットの送出通番をヘッダーに加え、nonce に使う
- [ ] B: 時刻を `seq_num` ごとに固定し、PING に独立した採番を加える
- [ ] C: 時刻を改ざん検出の対象外にする
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

### Q-024 証明書の組み込み位置

**Status**

解決済み

**Question**

証明書を、porter の通信のどの段階で使いますか。

**Context**

porter は経路ごとに同じパケットを複製し、受信側が `seq_num` で重複を除きます。  
証明書をどこで使うかにより、この仕組み、ワイヤー形式、経路数に比例する負荷が変わります。

A は、経路ごとに TLS (TCP) または DTLS (UDP) の通信路を作り、その中で porter のパケットを送ります。最大 8 経路で 8 回のハンドシェイクと 8 個の暗号状態を持ち、既存の AES-256-GCM による保護とは二重になります。一対多と片方向には適用できません。  
B は、TLS 1.3 などの標準のハンドシェイクを 1 回行って相手の証明書を検証し、その結果から [RFC 8446 7.5 節](https://www.rfc-editor.org/rfc/rfc8446.html#section-7.5) の鍵導出機能 (exporter) でセッション鍵を導出します。導出した鍵を既存のパケット保護に使うため、全経路で同じ鍵を共有し、重複排除とワイヤー形式を維持できます。ハンドシェイクを行う経路と、経路切り替え時や再接続時の扱いの設計が必要です。一対多と片方向には適用できません。  
C は、送信者がパケットごとにデジタル署名を付けます。応答のない片方向や一対多でも送信者を認証できます。署名の長さ (Ed25519 で 64 バイト) と署名処理の負荷が送出ごとに加わり、秘匿には別の鍵が必要です。

B では、セッションごとに一時的な鍵交換 (ECDHE) を行うため、証明書の秘密鍵が漏えいしても過去の通信は解読されません (前方秘匿性)。  
これは現行仕様が適用範囲外としている「鍵が漏えいした場合における、過去の通信の秘匿性の維持」を満たします。

**Answer**

- [ ] A: 経路ごとに TLS または DTLS の通信路を作る
- [x] B: (推奨) 標準のハンドシェイクで認証と鍵確立を行い、導出した鍵を既存のパケット保護に使う
- [ ] C: パケットごとにデジタル署名を付ける
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

### Q-056 OpenSSL のアセンブラー実装

**Status**

解決済み

**Question**

`app/openssl` で、OpenSSL のアセンブラー実装を有効にしますか。

**Context**

最終仕様の初版は、アセンブラーを使わない構成 (`no-asm`) を既定にしていました。2026-11-09 の対話でユーザーから次の指摘がありました。「アセンブラーが高速化に資するなら、検討の余地はある。現在のビルド システムでアセンブラー対応が可能なら採用すべき」。

高速化への寄与について、確認した事実と見込みは次のとおりです。

- OpenSSL のアセンブラー実装には、CPU の AES 命令などを使う AES-GCM の高速な実装が含まれます。`no-asm` では C の実装だけになり、AES-GCM の速度が大きく下がる見込みです。具体的な倍率は測定していません。
- Linux では、cplat のデータ保護 (AES-256-GCM) が `app/openssl` の libcrypto を使うことになるため ([Q-051](#q-051-linux-で使う-openssl))、`no-asm` にすると、システムの OpenSSL を使う現行より暗号処理が遅くなる可能性があります。
- Windows では、cplat のデータ保護は OS 標準の CNG を使うため、アセンブラーの有無の影響はハンドシェイクだけです。ハンドシェイクは接続時と再接続時に限られます。

ビルド システムでの対応可否は次のとおりです。

- makefw には、アセンブラーのソースをコンパイルする規則がありません。ただし、OpenSSL のアセンブラーは OpenSSL 自身のビルド (Configure と make/nmake) がアセンブルします。`app/openssl` が makefw から OpenSSL のビルドを呼び出す構成であれば、makefw にアセンブラーの規則を追加する必要はありません。
- Linux では、GCC とともに入る GNU アセンブラーを使います。
- Windows の 64 ビット版では、OpenSSL のアセンブラーのビルドに NASM が必要です。この作業環境には NASM がありません (`ml64` はあります)。Perl は Git 付属のものだけが見つかりました。OpenSSL の Windows 向けの手順書が求める Perl の種類と、NASM の必要な版は、`app/openssl` の作業で手順書を確認します。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) Linux と Windows の両方で有効にし、Windows のビルド環境 (開発環境と CI) に NASM を追加する
- [ ] B: Linux だけ有効にし、Windows は `no-asm` とする
- [ ] C: 両方とも `no-asm` とする
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

### Q-057 libssl などの mock の配置

**Status**

解決済み

**Question**

porter の証明書方式の単体テストで使う、libssl と証明書関連 (X509、PEM、BIO など) の OpenSSL の関数の mock を、どこに置きますか。

**Context**

最終仕様の第 4 版は、「porter のテストに OpenSSL の関数への mock を用意する。既存の第三者共有ライブラリ向けの mock の作り方に従う」としていました ([Q-054](#q-054-porter-からの-openssl-の直接利用) の Assessment)。

その後、第三者管理ライブラリの名前変更の案件 ([最終仕様](../../../../general/docs/prompts/current/261111-third-party-lib-rename-design.md)、2026-11-11 承認) で、OpenSSL の mock の方式が次のように決まりました ([app/openssl の README](../../../../openssl/README.md) の「単体テスト用のモック」)。

- mock は `app/openssl` の `mock_openssl` が提供します (testfw から移管済み)。
- テスト対象のソースが取り込む `<openssl/evp.h>` などを、`app/openssl/test/include_override/openssl/` の差し替えヘッダーで置き換え、関数の呼び出しをマクロで `mock_<関数名>` へ置き換えます。makefw は、依存先 app の `test/include_override/` をテスト対象のコンパイルに自動で追加します。
- 利用側のテストは `mock_openssl` だけをリンクし、実ライブラリを同時にリンクしません。mock は実行時に `libcrypto_app` を読み込み、実関数へ委譲します。
- 置き換える関数は、ワークスペースの app が使う関数だけです。現在は EVP と RAND の 17 個です。libssl の mock は、その時点で libssl を使う app がなかったため対象外とされました。

porter は、ハンドシェイクと証明書の検証で、libssl の関数 (`SSL_CTX_new()`、`SSL_do_handshake()`、`SSL_export_keying_material()` など) と、libcrypto の証明書関連の関数 (`PEM_read_bio_X509()`、`X509_STORE_add_cert()`、`BIO_new()` など) を新たに使います。  
上記の方式では、mock のない関数をテスト対象が呼ぶと、テストのリンクが未解決になります。失敗を注入しない正常系のテストでも、使う関数をすべて mock に加える必要があります。

```text
  libsrc/mock_openssl_ssl/...        ← porter 独自の mock ライブラリ

```
