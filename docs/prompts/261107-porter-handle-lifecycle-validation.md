## TCP の DATA 消失の修正

直接原因は、相手端が CONNECTED になる前に DATA が届き、受信側で破棄される競合でした。  
送信スレッドが DATA の前に最新の経路状態を同じ path へ書き込むよう修正し、TCP の送信失敗と受信の欠番も黙って破棄しない動作にしました。  
Linux (WSL Oracle Linux 8) で次の結果を確認しました。

- 対象の結合試験を 300 回連続で実行し、すべて成功しました。
- DATA 前の経路状態の通知だけを一時的に無効にした版では、300 回中 7 回失敗しました。
- ハンドル並行操作の結合試験 6 件を 40 回連続で実行し、すべて成功しました。
- 追加した単体試験 (送信スレッド 4 件、送信キュー 1 件、送信 API 1 件、受信スレッド 2 件) を含む 4 スイートが成功しました。
- 製品とテストのビルドで、内容のある `.warn` ファイルはありません。

## 性能比較

比較元は porter のコミット `9e55a0ce2291f54d7c25f6cf4ebf8a123f14ddca`、比較先は今回の変更です。  
両方の製品ソースを Windows/MSVC の同一条件 (`/O2 /MD /std:c17`) でビルドしました。  
測定プログラムはセッション用一時ディレクトリ `porter-lifecycle-benchmark` の `bounded.cc` です。  
UDP のループバックで、64 / 5000 バイト、通常 / 圧縮 / ブロッキング / 圧縮とブロッキングの組み合わせ、  
1 スレッド・1 ハンドル / 4 スレッド・1 ハンドル / 4 スレッド・4 ハンドルを各 3 回測定しました。  
各スレッドは 1000 件送信し、4 件ごとに受信完了を待ちます。同時未完了数は最大 16 件です。

両版とも計 216000 件の送受信が完了しました。これは未完了数を制限した負荷での比較であり、最大送信能力の測定ではありません。

- 64 バイトの処理件数の変化は -20.5% から +1.7% でした。
- 5000 バイトの変化は -10.6% から +2.0% でした。24 条件中の値は比較表に保存しています。
- プロセス CPU 時間の合計は 21281250 から 22125000 マイクロ秒となり、約 4.0% 増加しました。Windows の計時粒度の影響を含みます。
- porter 内の動的確保呼び出しは 108168 回から 108257 回となりました。cplat 内部の確保は計測対象外です。
- 通知ノードを再利用し、通知待ちリストの取り出しと回収をまとめ、空のキューへの追加時だけ通知スレッドを起こす方式に調整しました。
- 通知データの追加コピーは、受信件数と長さから計算すると DATA だけで 546912000 バイトです。実測したコピー回数ではありません。

小さいメッセージではハンドル検証と通知スレッドへの受け渡しの負担が相対的に大きくなります。  
同一プロセス内の測定であり、ネットワークを介した実運用の性能を保証する値ではありません。  
無制限に送る予備測定では両版で受信欠落が変動したため、性能比較には使用していません。  
TCP の予備測定では両版で終了時エラーが発生したため、上記の比較は UDP に限定しています。
