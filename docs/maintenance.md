# 実装の保守と未解決事項

実装を調べる入口は [アーキテクチャー](architecture.md)、動作の時系列は [通信シーケンス](sequence.md) を参照してください。  
この文書には、構造変更で維持する境界と、追加の検証が必要な事項を記載します。

## 責務を分割するときの境界

- サービス開始は、資源の所有と失敗時の解放を `potr_service_open.c` に集約します。経路準備側が確保したソケットもコンテキストに格納します。
- 受信パケットの認証と送信元照合は `thread_recv_validate.c` が担当します。呼び出し側の検証順序を維持し、未認証のパケットでピアを作成しないようにします。
- セッション採用は `thread_recv_session.c` が担当します。1:1 と TCP の FIN は採用後に処理し、N:1 の FIN は session triplet で特定したピアに対して直接処理します。
- FIN の判定と発火は `thread_recv_fin.c` が担当します。呼び出し側が `recv_window_mutex` を保持している場合は、発火の前に解放します。
- 再送と順序整列は `thread_recv_window.c` が担当します。1:1 と N:1 は受信状態ビュー経由で NACK、REJECT、ウィンドウ投入を共有します。
- 構成済みスロットへのパケット振り分けは `thread_recv_dispatch.c` が担当します。1:1 の FIN は採用後に処理し、N:1 の FIN は採用せずに処理します。NACK 再送は N:1 のみ行い、1:1 は送信処理側が担当します。
- 私有ヘッダーには、同じディレクトリの別ファイルから呼び出す関数のみを宣言します。分割のために公開 API を増やしません。

フラグメント結合、展開、DATA 配信は `thread_recv_slot.c` が担当します。  
セッション採用と FIN 制御は受信状態の更新として切り出し済みです。  
再送と順序整列は受信ループから分離済みです。ループ側に公開するのは、外側パケットの投入、REJECT、NACK 再送、PING 欠番走査、リオーダー期限切れの入口だけです。  
N:1 は現時点ではリオーダー待機を開始しません。欠番は即時に NACK を送出します。  
N:1 の NACK 重複抑制は、1:1 と同じ時間窓でピアごとのバッファーを使用します。  
受信ループに残る個別処理は、ピア検索と mutex、および TCP ストリームのフレーム読み取りです。

## TCP マルチパスの受信バッファー共有への対策

Linux の実ソケットを使用する回帰試験で、修正前の共有受信領域に起因する不具合を再現しました。  
試験は `test/src/integration/porterSendRecvTest/tcpMultipathTest.cc` にあります。

`interleaved_headers_preserve_packets` は、一方の経路をヘッダー読み取り直後に停止し、他方の経路へ異なる長さと内容の DATA を送信します。  
修正前は先行ヘッダーが上書きされ、期待する DATA が配信されませんでした。  
`encrypted_compressed_reply_preserves_callback_data` では、展開済みデータを受け取るコールバックから圧縮返信すると、コールバック中の受信データが書き換わることを確認しました。

修正後は TCP の読み取り先を経路別に確保し、暗号化・圧縮と復号・展開の領域を送受信で分離しています。  
読み取り完了後から配信完了までを受信処理ロックで保護し、ウィンドウ内の領域再利用とフラグメント結合・展開を直列化しています。  
ブロッキング受信とスレッド終了待ちでは、このロックを保持しません。  
所有権と同期の構成は [TCP 受信フロー](architecture.md#tcp-受信フロー) を参照してください。

暗号化・圧縮・フラグメント化を組み合わせた全バイト照合、別経路が受信待ちの場合の処理継続、コールバック中のデータ寿命も回帰試験に含めます。  
通常の暗号化・圧縮フラグメント試験は修正前も成功しており、それだけでは競合の再現を確認できません。  
読み取りの停止位置を制御する試験は Linux の動的シンボル解決を使用します。  
Windows/MSVC での実行は未確認です。

## 機能仕様の整備状況

[機能仕様](functional-spec/README.md) は 10 カテゴリを配置済みです。  
全カテゴリについて、機能別の振る舞い、適用範囲外、前提と制約を記載しています。  
選択の指針は、複数の方式から 1 つを選択する必要があるカテゴリに設けています。

実装の振る舞いと機能仕様が一致しない場合は、どちらの誤りかを先に判断してください。  
機能仕様が実装を追認する形での変更は行いません。

既存の [アーキテクチャー](architecture.md)、[プロトコル仕様](protocol.md)、[構成ファイル仕様](config.md) は機能仕様より下流の文書です。  
これらを根拠として機能仕様を記載せず、利用側から観測できる結果へ置き換えて記載します。

## 局所検証

porter 直下で `make`、`make test`、宣言や Doxygen 出力を変更した場合は `make doxy` を実行します。  
通信処理の変更時には、結合テスト `test/src/integration/porterSendRecvTest/bin/porterSendRecvTest` が実行されたことを確認します。  
このテストは別プロセスの `porter-test` を起動するため、ビルドの差分判定だけで省略された場合は実行ファイルを直接起動します。

Linux では porter と cplat に加え、cjson、zlib、testfw の共有ライブラリを探索できる環境が必要です。  
ビルド後は内容のある `.warn` を確認し、Windows/MSVC の未実行結果を Linux/GCC の結果と混同しないでください。
