# 実装の保守と未解決事項

実装を調べる入口は [アーキテクチャー](architecture.md)、動作の時系列は [通信シーケンス](sequence.md) を参照してください。  
この文書には、構造変更で維持する境界と、追加の検証が必要な事項を記載します。

## 責務を分割するときの境界

- サービス開始は、資源の所有と失敗時の解放を `potr_service_open.c` に集約します。経路準備側が確保したソケットもコンテキストへ格納します。
- 受信パケットの認証と送信元照合は `thread_recv_validate.c` が担当します。呼び出し側の検証順序を維持し、未認証のパケットでピアを作成しないようにします。
- 私有ヘッダーには、同じディレクトリの別ファイルから呼ぶ関数だけを宣言します。分割のために公開 API を増やしません。

フラグメント結合、展開、DATA 配信は `thread_recv_slot.c` が担当します。  
受信ループ、セッション採用、FIN と再送は、引き続き `potr_recv_thread.c` に含まれます。  
次の分割では、受信状態を更新する処理を先にまとめ、ループ側へ個別の状態操作関数を多数公開しない構成を検討します。

## TCP マルチパスの受信バッファー共有

コード上で競合の可能性を確認していますが、同時受信による破損の再現試験は未実施です。

[`potr_recv_thread.c`](../prod/libsrc/porter/thread/potr_recv_thread.c) の `potr_internal_tcp_recv_thread_start()` は、経路ごとに受信スレッドを起動します。  
各 `tcp_recv_thread_func()` は同じ `ctx->recv_buf` を読み取り先に使い、ソケット読み取りからパケット解析までを共通のロックで保護していません。  
複数経路から同時に受信すると、一方が解析している内容をもう一方が上書きする可能性があります。

同じコンテキストの復号バッファーと展開バッファーにも、並行使用の確認が必要です。  
修正前に、複数経路へ異なる内容を同時送信する試験を追加し、暗号化、圧縮、フラグメント化を含めて受信内容を照合してください。  
経路別バッファーと受信状態の同期は別の問題として設計し、ブロッキング受信中に他の経路を止めないようにします。

## 局所検証

porter 直下で `make`、`make test`、宣言や Doxygen 出力を変えた場合は `make doxy` を実行します。  
通信処理の変更時には、結合テスト `test/src/integration/porterSendRecvTest/bin/porterSendRecvTest` が実行されたことを確認します。  
このテストは別プロセスの `porter-test` を起動するため、ビルドの差分判定だけで省略された場合は実行ファイルを直接起動します。

Linux では porter と cplat に加え、cjson、zlib、testfw の共有ライブラリを探索できる環境が必要です。  
ビルド後は内容のある `.warn` を確認し、Windows/MSVC の未実行結果を Linux/GCC の結果と混同しないでください。
