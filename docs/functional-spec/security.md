# 通信保護 (security) 機能仕様

## 概要

通信保護機能は、事前に共有した鍵または証明書を用いた相互認証によって確立した鍵を用い、メッセージの内容の秘匿、改ざんの検出、およびリプレイの防止を行います。

保護の有効と無効、および認証方式 (事前共有鍵方式または証明書方式) は、サービスごとの構成で選択します。  
保護を有効にした場合も、利用側の送信と受信の手順は変わりません。

## 解決する課題

通信の内容は、経路上で読み取られたり、書き換えられたり、過去の通信を再送 (リプレイ) されたりすることがあります。  
利用側が独自に暗号化を行うと、鍵の管理、改ざんの検出、形式の互換性の維持をそれぞれ実装することになります。

秘匿と改ざんの検出を別々に実装した場合、内容は読み取れなくても制御に関わる項目の書き換えを検出できないことがあります。  
また、事前共有鍵をそのまま使い続ける構成では、相手の個体認証や過去の通信の秘匿性 (前方秘匿性) を確保できません。

さらに、保護を有効にした構成へ保護されていないメッセージが到達した場合、これを受理すると保護は回避されます。

通信保護機能は、秘匿、改ざんの検出、相互認証、前方秘匿性、リプレイの防止をあわせて担い、保護の有無と方式を構成の選択に置き換えます。

## 保護の適用と方式の選択

サービスごとに、保護の有効と無効、および方式 (事前共有鍵方式または証明書方式) を構成で選択します。  
保護を有効にすると、メッセージの内容は暗号化されて送出され、同じサービスの中で保護の有無や方式は混在しません。

証明書方式を選択した場合、通信の暗号化は必須であり、平文の通信は受理されません。  
事前共有鍵方式で保護を有効にした構成でも、保護されていないメッセージは受理されません。

## 保護の範囲とリプレイの防止

秘匿の対象は、メッセージの内容です。  
送信元、宛先、大きさ、送信の時刻など、内容以外の情報は秘匿されません。

制御に関わる項目は、秘匿の対象ではありませんが、改ざん検出の対象です。  
このため、内容を読み取れない相手による項目の書き換えを検出できます。

保護されたすべてのパケット送出では、セッションの送出ごとに 1 ずつ増える通番など、送出ごとに一意な値を暗号保護に用います。  
疎通を確認するためのメッセージ、経路ごとの複製、再送、受信報告を含むすべての送出が対象であり、同じ鍵で同じ値を再利用しません。  
送出通番が上限に達した場合は、そのセッションを閉じます。

受信側は、送信元のセッションごとに直近 256 個の送出通番を記録します。  
記録済みまたは記録範囲より古い送出通番のパケットを受信した場合は、復号の後に破棄し、リプレイを防止します。  
経路ごとの複製は送出ごとに異なる送出通番を持つため、この記録と干渉しません。

## 改ざんの検出

受信したメッセージは、内容の復元とあわせて改ざんの有無が検証されます。  
検証に失敗したメッセージは破棄され、受信状態は変更されません。

破棄したメッセージは、欠落としても重複としても扱われません。  
このため、改ざんされたメッセージの到着によって再送の要求が発生することはありません。

## 事前共有鍵方式の鍵指定

事前共有鍵方式では、鍵を構成で 2 つの方法のいずれかによって指定します。

| 指定の方法 | 内容 |
|---|---|
| 語句から導出する | 任意の長さの語句を指定し、porter が固定の方法で鍵を導出する |
| 値として指定する | 鍵の値をそのまま指定する |

Table: 暗号鍵の指定方法と内容

語句から導出する場合、同じ語句からは常に同じ鍵が得られます。  
通信する双方が同じ語句または同じ値を用いることで、保護された通信が成立します。

## 証明書方式の相互認証と受理条件

証明書方式では、すべての通信種別で通信の両端が互いの証明書を検証する相互認証を行います。  
受信側も自端の証明書と秘密鍵を保持します。

相手の証明書は、次のいずれか一方を満たす場合に受理します。

- 信頼する CA から発行された証明書チェーンを検証でき、有効期限内であり、失効リストで失効しておらず、証明書の対象名 (DNS 名または URI) が構成で指定された相手名のいずれかと一致する
- 直接登録された相手の証明書と一致し、有効期限内である

証明書、秘密鍵、失効リストは、サービスを開く際に 1 回だけ読み込みます。  
更新を反映するには、サービスを開き直します。

## 証明書方式の鍵の確立と前方秘匿性

証明書方式では、一時的な鍵交換と認証付き暗号を用いてセッションごとの鍵を確立し、鍵の漏えいに対して過去の通信の秘匿性 (前方秘匿性) を確保します。  
ハンドシェイクで導出した鍵は、送信方向ごとに異なる鍵を割り当て、すべての経路で共通に使用します。

接続を伴う通信種別では、最初に接続した経路でハンドシェイクを行い、後から接続した経路ではハンドシェイクを行いません。  
接続を伴わない通信種別では、全経路へハンドシェイクを送出し、最初に完了したものを採用します。  
全経路が切断して再接続した場合は、ハンドシェイクからやり直します。

## 一対多の証明書方式とグループ鍵

片方向の通信種別 (一対多を含む) では、各受信者が送信者のユニキャストの所在に対してハンドシェイクを行います。  
このため、送信側の待ち受けポートは 0 以外に固定します。

送信者はセッションごとにグループ鍵を生成し、受信者の証明書を検証した後、ハンドシェイクで導出した受信者ごとの鍵でグループ鍵を暗号化して配布します。  
送信側からのデータと疎通を確認するためのメッセージはグループ鍵で保護し、受信側からの再送の要求と受信報告は受信者ごとの鍵で保護します。

グループ鍵は、送信者のセッションを開き直すまで変更しません。

## 認証前のパケットと認証失敗時の振る舞い

証明書方式では、ハンドシェイクが完了するまでハンドシェイク以外のメッセージを受理せず破棄します。  
認証前のメッセージによって、経路状態、受信状態、およびセッション状態は変更されません。

相手の証明書の検証に失敗した場合、その相手との通信を確立せず、理由を診断出力へ記録します。  
再試行は、接続を伴う通信種別では再接続間隔、それ以外の通信種別では死活監視間隔の周期で行います。実効の死活監視間隔が 0 の場合でも、データグラム型の認証の再試行はデータグラム型の既定の監視間隔で行います。  
一対多の通信種別では、認証に失敗した受信者を除いて、他の受信者との通信を継続します。

## 適用範囲外

- 事前共有鍵方式における、鍵の配布、保管、更新、および失効
- 証明書方式において、認証後にセッションを継続したままの鍵の更新
- 事前共有鍵方式において、鍵が漏えいした場合の過去の通信の秘匿性の維持
- 事前共有鍵方式における、鍵の所持の確認を超える通信相手の個体の認証
- 一対多の証明書方式において、グループ鍵を共有する受信者による送信者のなりすましの防止
- 通信の相手、時刻、量など、内容以外の情報の秘匿
- 語句の強度の評価、および弱い語句の拒否
- 保護の失敗回数に基づく送信元の遮断

## 前提と制約

保護の成立は、通信する双方が同じ保護の有無および方式を用いていることを前提とします。  
一方だけが保護を有効にした場合や、異なる方式を指定した場合は、通信は成立しません。

事前共有鍵方式の保護の強さは、利用側が指定した語句または値の強度に依存します。  
鍵は構成から与えられ、通信の途中では変更されないため、鍵が漏えいした場合は過去および将来の通信の秘匿性は維持されません。  
また、同じ鍵を持つ相手はいずれも正当な相手として扱われます。

証明書方式では、返送経路を用いてハンドシェイクを行うため、片方向や疎通の監視を行わない構成を含めて返送経路が存在することを前提とします。  
返送経路のないネットワークでは証明書方式を使用できません。  
また、片方向の証明書方式で送信側を開く場合、待ち受けポートを 0 以外に固定します。

保護は、通信の内容を対象とします。  
通信の相手、時刻、量は、保護を有効にした場合も観測できます。

## 選択の指針

保護の有無と方式は、経路の性質、相手認証の要否、および返送経路の有無に応じて選択します。

| 状況 | 選択する保護と方式 |
|---|---|
| 経路が第三者から隔離されていない、または内容の秘匿が必要である | 保護を有効にする |
| 相手の個体認証と前方秘匿性が必要であり、返送経路がある | 証明書方式 |
| 返送経路のない片方向通信である、または事前共有鍵で運用を簡素にしたい | 事前共有鍵方式 |
| 隔離された経路で、送出する量と処理時間を優先する | 保護を無効にする |

Table: 状況に応じた通信保護設定の選択指針

送信元の限定だけでは、送信元を偽装した通信を排除できません。  
偽装の排除が必要な場合は、送信元の限定ではなく保護を有効にします。
